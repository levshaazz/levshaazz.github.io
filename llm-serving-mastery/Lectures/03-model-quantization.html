01 / 07

Map the number

Every saved bit introduces a reconstruction rule.

Start with one scalar; then expose why groups and kernels change the real model.

FP16/BF16 and INT4 make different promises

Representation

Floating point

Sign, exponent and fraction encode a wide dynamic range with non-uniform spacing. BF16 and FP16 both use 16 bits but distribute them differently.

Integer quantization

A limited codebook uses an explicit scale (and sometimes zero-point) to map real values into discrete codes. Spacing and clipping are chosen by calibration.

Do not conflate FP8 with INT8, or NF4 with uniform signed INT4. The later method section distinguishes these.

Scale converts codes back into numbers

Symmetric integer toy model
\(q=\operatorname{clip}(\operatorname{round}(x/s),q_{\min},q_{\max})\)
\(\hat{x}=s\,q\)
Here \(s>0\); signed 4-bit codes span −8…7. Real schemes may use zero-points, learned scales or non-uniform codebooks.
Point out two distinct errors: rounding within range and clipping outside it. This is a teaching model, not NF4.

Rounding and clipping are different failure modes

Where error enters
QUANTIZATION ERROR
\(e=x-\hat{x}\)

Inside the representable interval, rounding perturbs a value by a fraction of a step. Beyond the interval, clipping discards magnitude; the error can be much larger.

Ask which error a single large activation outlier creates under a shared scale.

Worked: 1.83 with a quarter-unit scale

Signed INT4 illustration
\(q=\operatorname{round}(1.83/0.25)=7\)
\(\hat{x}=7(0.25)=1.75\)
Absolute reconstruction error: \(|1.83-1.75|=0.08\). Units match the original scalar; this says nothing yet about task quality.
7 is the maximum signed INT4 code. At this boundary, the next larger input can clip.

Worked: 2.25 clips to the same code

Same scale, different mechanism
\(\operatorname{round}(2.25/0.25)=9\rightarrow q=7\)
\(\hat{x}=1.75\)
Absolute error is \(0.50\), more than six times the previous 0.08. Larger scale could cover the outlier but coarsen ordinary values.
This illustrates why the calibration objective needs a representative distribution, not only the minimum and maximum.

One scale is cheap; one scale can be crude

Granularity

Per tensor

One mapping spans many values. Small metadata, but one outlier can expand the range for all channels.

Per channel / group

Different mappings protect local ranges. More scale metadata and layout constraints; the runtime must apply those scales in its kernels.

Use one high-magnitude channel as a thought experiment. The best granularity is a hardware-and-quality choice.

A representative distribution chooses the scale

Calibration
CHOICE, NOT CONSTANT
What values should matter most?

Min–max coverage protects extremes but may waste codes on rare outliers. Error minimization can favor common values while clipping tails. A production choice needs task-representative samples and held-out validation.

Do not calibrate on the hidden judge set. A calibration corpus is training-like data; quality evaluation must remain held out.

“Four bits” does not mean “four times smaller”

Common shortcut
Missing terms

Payload is only one part of a live GPU process.

Scales, zero-points, unquantized layers, padding, KV cache, activations, allocator reserves, workspaces and kernel code all consume memory.
The relative payload from 16 to 4 bits is 4×. The full process often is not. Quantify the difference later.

W4A16 is mainly a weight-format promise

Weight-only
W4A16
4-bit stored weights, 16-bit activations

The kernel may unpack and dequantize weight tiles as it computes. Lower weight traffic can help decode, but dequantization, tile layout and launch overhead can erase the gain on some shapes.

A storage format is not necessarily the arithmetic dtype. Inspect the actual kernel path and matrix shape.

W8A8 changes both operands

Weight–activation
W8A8
8-bit weights and activations

Activation scales may be static from calibration or dynamic at runtime. A supported low-precision matrix kernel can improve compute throughput, but conversion and scale handling are real work.

NVIDIA FP8 W8A8 and integer INT8 W8A8 differ in range, arithmetic and support. The label alone is insufficient.

Weight compression does not shrink KV automatically

Reuse Topic 02
\(M_{KV}=2LH_{kv}d_{head}b_{KV}T\)
\(T\) is live tokens, \(b_{KV}\) bytes per element. Changing weight bits leaves this term unchanged unless the serving engine also changes KV dtype.
Use 64×768 live tokens as a concrete test. The KV term is capacity; attention traffic needs separate analysis.

KV quantization trades context headroom for fidelity

Separate candidate

Capacity

Moving a 2-byte KV element to 1 byte halves the logical payload for the same token count and shape.

Risk

Attention reads reconstructed history repeatedly. Long-context quality, scaling policy and engine support need separate validation.

The logical half does not imply half of total VRAM. Long-context tasks must be in the quality set.

Failure: “loads” does not mean “accelerates”

Production scenario A

Detection

Cold load takes longer; prefill and decode timing regress. Logs show conversion; profiler shows dequantize or generic kernels instead of the expected path.

Mitigation

Batch size changes the value of weight compression

Phase-specific effect
REUSE
One copy of weights, many token rows

At decode batch 1, weight traffic can dominate. With more live rows, one weight tile serves more arithmetic. Dequantization cost, cache reuse and scheduler behavior move the crossover.

Connect to Topic 02 roofline, but do not assert that all decode is bandwidth-bound.

Low-bit storage is not necessarily low-bit GEMM

Common shortcut
W4A16

“The GPU multiplies two 4-bit operands.”

Weights are stored in four-bit form; activations remain 16-bit. Kernels may unpack/dequantize before or during the matrix multiply.
Use this to distinguish W4A16 from W4A4 and to make students inspect kernels rather than names.

Count all bytes

Compressed payload is a lower bound on process memory.

The next three computations use a hypothetical 3.0B dense model; none are measured runtime values.

Worked: 3B parameters at FP16

Hypothetical dense model
\(3.0\times10^9\text{ parameters}\times2\text{ B}=6.0\text{ GB}\)
GB is decimal: \(6.0\times10^9\) bytes ≈ 5.59 GiB. This is weights only, not a full loaded process.
The model is deliberately round for transparent arithmetic; actual files have embeddings, metadata and possibly tied weights.

Worked: ideal four-bit payload

Same parameter count
\(3.0\times10^9\times4/8=1.50\text{ GB}\)
The payload ratio is 4:1 against FP16. It omits scales, zeros, unquantized modules, packing, allocator state and KV.
This is the only place a four-times statement is exactly valid without more conditions.

Worked: groups add metadata

128 weights per FP16 scale
\((3.0\times10^9/128)\times2=46.875\text{ MB}\)
Payload + these scales = 1.546875 GB, ≈1.441 GiB. This still excludes zero-points, padding, higher-precision layers and workspace.
If the group size halves, scale count doubles. If a zero-point is stored too, add its actual encoded size rather than guessing.

Not every module is quantized

Checkpoint reality

Often treated separately

Embeddings, normalization, output head and selected sensitive projections may stay in higher precision depending on the scheme and runtime.

Accounting consequence

Count bytes from the actual state/config and measure allocated/reserved GPU memory after load. Do not multiply total parameter count by one bit width blindly.

Which layers remain high precision is a property of the artifact, not a universal rule.

Worked: 16 GiB is not 16 GiB for weights

Illustrative budget
\(16-2.00-1.69=12.31\text{ GiB}\)
After an illustrative 2 GiB runtime reserve and 1.69 GiB logical KV, 12.31 GiB remains for weights and other live tensors. Neither reserve is a measured constant.
The 3B FP16 toy weighs ≈5.59 GiB and fits here. Quantization needs a workload reason; a larger model or more live tokens changes the answer.

A nominal format may carry alignment overhead

Physical layout

What the math counts

Exactly four bits per dense weight plus the specified scale bytes.

What a runtime allocates

Packed tiles, padding to group and kernel shape, temporary converted weights, cache buffers and memory pools. Inspect the artifact and process peak.

A shape padded from a non-multiple of 128 to the next group is an easy worked counterexample to the ideal payload.

Fit is not “one successful load”

Operational reserve
ADMISSION
Leave margin for live variance

Prompt lengths, batching, allocator fragmentation and runtime workspaces change peak demand. A candidate that starts with almost no free VRAM can fail at the intended concurrency.

Separate load-fit from service-fit. Check the target 64-client workload, not only one empty model process.

04 / 07

Calibrate and deploy

Same bit width, different optimization and kernel contracts.

PTQ and QAT are different workflows; the lab performs a bounded post-training load-time quantization.

When is the quantizer chosen?

Workflow

Post-training quantization

Start with a trained checkpoint, choose scales/codes on calibration data, then validate held-out tasks. Usually cheaper than retraining.

Quantization-aware training

Expose the model to quantization effects during training/fine-tuning. Can recover quality but adds data, compute and training risk.

Neither route removes the need to test the exact runtime artifact on the target device.

Calibration data is a design choice

Representativeness
PTQ INPUT
Match the deployment distribution

Code, math, structured outputs, long context and languages may activate different channels. A tiny generic sample can choose scales that look good on average but fail a critical bucket.

Keep calibration and evaluation separate. No private hidden judge prompts enter calibration.

AWQ protects activation-important channels

Weight-only PTQ
AWQ
Use activation statistics to find salient weight channels

AWQ searches an equivalent channel-scaling transformation to reduce low-bit weight error where activations make it matter. It does not require backpropagation in the original method.

Primary source: Lin et al., AWQ, https://arxiv.org/abs/2306.00978. Do not describe AWQ as simply “keep 1% FP16 weights”; its efficient path uses scaling.

GPTQ corrects weight quantization error sequentially

Weight-only PTQ
GPTQ
Approximate second-order information guides the update

Quantizing one group perturbs outputs; GPTQ uses an approximate curvature/error model to adjust remaining weights. The exact artifact and kernel still determine serving behavior.

Primary source: Frantar et al., GPTQ, https://arxiv.org/abs/2210.17323. Avoid promising the paper's reported speedup on this course GPU.

Eight bits can mean different arithmetic

Format semantics

FP8

Floating-point sign, exponent and mantissa, commonly E4M3 for inference with explicit scaling. Range and spacing are non-uniform.

INT8

Integer codes with scale/zero mapping. Often paired with activation calibration or dynamic scales. Kernel and output accumulation matter.

NVIDIA format definitions: https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/quantized-types-schemes.html. Support is version-specific.

NVFP4 has a different scale hierarchy

Hardware-specific format
NVFP4
FP4 code + block scale

NVIDIA describes four-bit floating-point values with fine-grained block scaling; activation quantization is dynamic in its TensorRT scheme. Hardware and runtime support must be verified for this exact deployment.

Source: NVIDIA quantization schemes. Do not tell T4 students to expect native NVFP4 acceleration.
