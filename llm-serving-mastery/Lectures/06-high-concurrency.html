The same service, two very different days

Topic 06 · draft · bounded examples

Fine at 8 users

Ticket labels arrive in about a second; nothing queues; every reply lands inside the product deadline.

Broken at 128

Timeouts, retried and duplicated tickets, a queue that grows faster than it drains — with the same model, same GPU, same code.

Ask what ran out. The wrong answers come first: the GPU is not suddenly slow, Python did not get slower, and a bigger server is a purchase, not a diagnosis. Concurrency changed which resource binds first.

TTFT and TPOT are defined on these client-side monotonic clocks. Waiting before first token and service time are different physical things; a missing first-content timestamp is not zero. Never subtract an unrelated server wall clock to infer a queue.

Split the request into wait, prefill and decode

Topic 06 · draft · bounded examples
$$T_{\mathrm{total}} = \underbrace{W_q + P}_{\mathrm{TTFT}} + n_{\mathrm{tok}}\cdot\mathrm{TPOT}$$
\(W_q\)secondsQueue wait before first attention to this request
\(P\)secondsPrefill: one full pass over the prompt
\(n_{\mathrm{tok}}\)tokensGenerated tokens after the first
\(\mathrm{TPOT}\)s / tokenTime per output token under load
Invented example: 0.45 s wait + 0.25 s prefill + 31 × 15 ms = 1.17 s total.
Client-observed clocks only; server-side step boundaries are not visible here.
Under load W_q and TPOT move first: prefill P is roughly prompt-shaped. This decomposition tells the student WHERE to look when latency grows — which of the three terms doubled decides the diagnosis.

Why throughput grows before anything saturates

Topic 06 · draft · bounded examples
Declared arithmetic: 6.2 GiB FP16 weights read once per forward pass; weight bytes per generated token = 6.2 GiB / (N × 32).

Weight traffic per token collapses with batch size

Topic 06 · draft · bounded examples
$$b(N) = \frac{B_w}{N \cdot n_{\mathrm{tok}}}$$
\(B_w\)bytes / passAll weights read every forward pass
\(N\)requestsRequests sharing that pass (the batch)
\(b(N)\)bytes / tokenWeight traffic per generated token
N=1: 198.4 MiB/token → N=64: 3.1 MiB/token — a 64× arithmetic saving.
Weight traffic only: bandwidth, kernel efficiency and KV cost are not modeled.
This is the mechanism behind the rising part of the saturation curve: more concurrent clients mean larger batches and cheaper tokens — until a different resource stops cooperating. It is not yet a speedup claim.

Two finite resources, two different failures

Topic 06 · draft · bounded examples

Compute

SM occupancy and batch compute: prefill of a new request is a full extra pass — it competes with every resident decode.

KV memory

36 KiB per retained position per request: grows with context and clients until admission or preemption stops it.

Throughput curves die from one of these two ceilings. The experiment exists to tell them apart: a compute knee shows TPOT growth; a memory knee shows admissions blocked and preemption recompute. Same graph, different mechanism, different fix.

The KV bill for one request

Topic 06 · draft · bounded examples
$$\beta = 2\,L\,H_{\mathrm{KV}}\,d\,b = 36\,\mathrm{KiB}$$
\(L\)36 layersEvery layer keeps its own K and V
\(H_{\mathrm{KV}}\)2 headsGQA: KV heads, not query heads
\(d\)128 featuresHead width from hidden 2048 ÷ 16 query heads
\(b\)2 bytesExplicit FP16 elements
Per position: 2 × 36 × 2 × 128 × 2 = 36,864 bytes; a 2048-token context costs ≈ 72 MiB.
Ideal payload arithmetic — excludes page tails, tables and workspaces.
GQA is why this number is small: 16 query heads share 2 KV heads. Students compute this before the lab and compare it with the measured knee; the gap is engineering, not arithmetic.

Weights plus KV must fit one 15.36 GiB T4

Topic 06 · draft · bounded examples
Declared arithmetic: (15360 − 6350) MiB ÷ 72 MiB ≈ 125 simultaneous 2048-token requests — an upper bound, not scheduler policy.

Closed-loop clients do not fix demand

Topic 06 · draft · bounded examples
$$\lambda_{\mathrm{closed}} \approx \frac{C}{R + Z}$$
\(C\)clientsContinuously active population
\(R\)secondsMean residence: arrival to terminal
\(Z\)secondsMean think time before the next send
Invented: 8 / 0.25 s = 32 req/s offered; double the residence → 16 req/s.
Stable population and negligible think time assumed; not measured Qwen capacity.
Little’s law in its closed-loop form: a FIXED client count delivers FALLING demand as the service slows. That is why waves are defined by concurrency, not requests-per-second — and why comparing offered and completed rates exposes queue growth.

Define the knee operationally

Topic 06 · draft · bounded examples
$$k^{\star} = \max\{k : S(k)/S(k^{-}) - 1 \geq \gamma\}$$
\(k\)clientsWave concurrency, sorted
\(S(k)\)tokens / sCompleted throughput at wave k
\(\gamma\)fractionMinimum relative gain that still counts (lab: 0.5)
\(k^{-}\)clientsThe previous wave
On the illustrative curve: 32→64 gains fall below 50% — the knee sits at the last strong doubling.
A threshold choice, not physics: a different γ can move the knee by one wave, and the lab says so.
The definition is deliberately falsifiable and boring: students implement detect_knee, then defend or attack the threshold. The predicted-vs-measured comparison names which resource actually bound.

Stretch: a second application arrives

Topic 06 · draft · bounded examples

Interference, measured honestly

The document classifier B shares the server; A and B are reported separately, never averaged into one bar.

One protection

An in-flight cap K ∈ {1, 2, 4, 8, 16} limits B. Dev pair → freeze K with a forecast → one distinct held-out pair.

Same model, two system prompts: this is NOT tenant isolation and not two replicas — the limitation is stated, not hidden. The lab’s mock shows the protocol; only the owner GPU run shows real interference.

Development first; the held-out pair is not another tuner
