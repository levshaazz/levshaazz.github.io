Works on my machine is a contract breach

Topic 09 · draft v2

What you own now

The Topic 08 gateway validates, queues with honest 429s, maps errors, cancels. But it lived on whatever Python and pip state the host had.

What changes

The app becomes an immutable image with pinned dependencies. An image is a layered blueprint; a container is an ordinary process on your machine running that blueprint in isolation — same kernel, no virtual machine.

Frame the transition: Topic 08 built the API contract; Topic 09 makes it a production unit — fast to build, small to ship, quick to recover. Zero-Docker students get a five-minute on-ramp two slides ahead; the official <a href="https://www.docker.com/resources/what-container">what-is-a-container</a> explainer covers the pictures.

Three hosts, one answer: the image

Topic 09 · draft v2

The drift

Host A: Python 3.10, old fastapi. Host B: 3.12, fresh install. Host C: a stale venv. Same code, three different services — maybe three different bugs. In production those hosts are pods, and they drift the same way.

The admission

"It worked yesterday" is not reproducibility. A floating latest tag is a deferred dependency break. The image freezes the world: one blueprint, identical kitchens everywhere.

The motif of the topic: the image is the blueprint of a mobile kitchen; the container is the working kitchen; layers are its modules; a fleet is a park of identical kitchens. Ask which of the three hosts is the real one — answer: none, the image is.

First container in five minutes

Topic 09 · draft v2

If Docker is new to you

docker run hello-world pulls a tiny image and runs it. Then the daily four: docker ps (what runs), docker logs (what it says), docker inspect (what it is), docker images (what you own).

What a container is

An ordinary process on your machine, isolated: its own filesystem (the layers), its own name, bounded resources — one Linux kernel, no virtual machine. That is why starts and restarts are measured in seconds.

The on-ramp for novices; everyone else catches up on the journal discipline: every command in the lab lands in results/. The lab installs Docker Desktop (macOS/Windows) or Engine (Linux) — one-time setup, checked by `docker info` in the how-to block.

Build speed is two different caches

Topic 09 · draft v2

Layer cache

An instruction re-runs only if its inputs changed. The tooling layer caches forever; the pinned fetch layer caches until the commit pin moves; the compile layer rebuilds on any source edit. Unchanged rebuild: seconds.

Cache mount (ccache)

RUN --mount=type=cache keeps object files OUTSIDE the layers. It survives compile-layer invalidation: patch one line and the rebuild pays minutes, not the full compile. Content cache, not instruction cache.

The two caches are the core of the build-speed block. Students routinely conflate them; the lab measures both on a REAL llama.cpp compile and asks which effect survived which invalidation. docker build needs BuildKit for cache mounts (default in modern Docker).

The tooling layer talks to the network

Topic 09 · draft v2

The trap, caught for real

The first Dockerfile draft omitted ca-certificates. apt worked fine — it speaks plain HTTP to Ubuntu mirrors. Then git fetch died: "server certificate verification failed. CAfile: none".

The rule

The tooling layer is a contract with the network: list everything the build will talk to. HTTPS needs certificates; pinned git fetch needs git + TLS. A missing package fails not where you look, but where the build first touches the wire.

This happened while building THIS lab on THIS topic — the honest story beats a synthetic one. Ask: why did apt succeed while git failed? Because http and https are different contracts. The fixed line is in the student Dockerfile (level B TODO).

The size of an image is the sum of its layers

Topic 09 · draft v2
$$size(\mathrm{image}) \;=\; \sum_{k} size(\mathrm{layer}_k)$$
\(layer_k\)bytesone Dockerfile instruction's filesystem delta
\(size(image)\)MBwhat every pull and every node pays
Course record: 150 MB from-source runtime + 0 baked weights; 1.18 GB upstream base; +491 MB if baked.
Metadata layers (LABEL, HEALTHCHECK, USER) weigh 0 B — pins and probes change everything and cost nothing.
The only formula of the block, and it is arithmetic. docker history is the ledger that proves it. The point is the second column of the bake/mount/download table: weights dominate, so the delivery decision IS the size decision.

The incident: a pod with a wrong limit

Topic 09 · draft v2

The setup

A replica is capped at --memory 400m. Its resident appetite is ~760 MB (491 MB weights + KV cache + buffers). Prediction BEFORE the run: what will the kernel do when the process touches a page past the wall?

The production stakes

This is the daily reality of pods: requests/limits set by humans, models loaded by machines. When the limit is below residency, the story below repeats on every deploy. In the lab you write the prediction into the journal first.

Predict-before-measure, the course spine from Topics 06–07, now on an ops incident. The lab freezes INCIDENT_PREDICTION before the crash. Ask students for the mechanism, not the verdict: who kills the process — the app, the runtime, or the kernel?

OOMKill is the kernel, not the app

Topic 09 · draft v2

What you see

Exit code 137 = 128 + 9 (SIGKILL). No Python traceback, no exception — the strongest possible termination, delivered from outside the process.

What proves it

docker inspect answers "OOMKilled": true, and the log tail ends mid-model-load. Cause → evidence → fix: the discipline of the diagnose-exit TODO (level C).

Why 137 and not 1: exit code 1 is an application decision; 137 is 128+n for signal n — the kernel killed the process. The lab drills the full diagnosis ladder: 137/OOM, 1/tag drift, 125/daemon, 127/executable not found.

Read the evidence, then size the fix

Topic 09 · draft v2

The diagnosis ladder

137 + OOMKilled → cgroup limit; 1 + "manifest unknown" → tag drift; 125 → daemon refused the flags; 127 → executable not found. The journal keeps cause, evidence, fix for every drill.

The fix is sizing, not hope

Limit = resident × headroom (~1.5×). Take resident from docker stats, not from vibes: 762 MiB measured → 1200 m limit. A limit is admission control — the honest wall from Topic 08's queue, now in memory.

The anti-superstition rule: a change without a named mechanism is not an improvement. Students fill SIZING with the measured resident number before the fix cell runs — the same freeze-then-measure discipline as build-plan.json.

Security defaults, not security options

Topic 09 · draft v2

What v1 sets by default

Digest pin (byte-exact), non-root uid (smaller blast radius), HEALTHCHECK (the daemon knows), memory limit (admission control). Every one is a line in the Dockerfile, and every one is a default the fleet inherits.

What the server warns about

The real log from this lab: "no API key is set and CORS allows all origins". Production adds auth, TLS and network policy — Topic 11 territory. Defaults inside the image; policies around it.

The llama-server warning is quoted from the actual incident logs — honest evidence beats a checklist. Ask: which of these defaults would have saved the OOM pod? None — that is why limits exist as a separate admission control.

SBOM and the supply chain (stretch)

Topic 09 · draft v2

The inventory

SBOM lists every package inside the image: OS libs, binaries, versions. One image — one document. docker scout sbom or the sbom plugin; the lab saves the inventory when the tool exists and prints an honest skip when it does not.

The three risks

A floating base tag changes bytes under your feet; unpinned sources and weights are a lottery; layers remember everything — a file deleted in layer 9 still lives in layer 8, and so does a secret.

Stretch for fast students. The digest pin from the build block and the LLAMACPP_SHA pin are the working counter-examples. Ask: which of the three risks does a digest pin NOT solve? Layer memory — deletion is not rewriting history.
