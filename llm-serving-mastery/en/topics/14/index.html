Adapters & multi-tenancy: LoRA economics

One frozen base serves many tenants through 0.22 MB LoRA adapters. The rank arithmetic prices the sliver; a declared 2 ms swap cost makes routing a two-sided ledger (switches against waits); affinity windows bound the trade; per-tenant p95 applies the T13 discipline at tenant grain. AdapterSim reproduces every dial row; the star challenge tunes the window under declared lines.

Learning outcomes

  1. Compute LoRA adapter size: params = 2 · r · (d_in + d_out) · targets, bytes at fp16 — and why the A/B pair is inside r × (d_in + d_out).
  2. Count order-dependent swaps on a tenant stream and explain why the swap count is a policy output, not a load fact.
  3. Route with affinity windows: group arrivals by tenant in first-appearance order, price both sides (swaps and waits).
  4. Compute per-tenant p95 by nearest-rank over the tenant's own journal slice — never one global number.
  5. Argue the adapter boundary: what changes (the tenant delta) versus what stays shared (the base contract).
  6. Run AdapterSim end to end and reconcile the simulator against a hand-walked routing decision.

Acceptance checklist

  • adapter_params one-liner matches quiz q1; the A/B factor is not doubled
  • count_swaps on the deck stream = 5; grouped = 1; the waiting side is priced
  • affinity_batches groups by first appearance; window slices preserve arrival order
  • tenant p95 uses nearest-rank over the tenant's own slice, never one global number
  • AdapterSim reproduces every dial row (W=1: 5/0; W=3: 2/2; W=6: 1/4)
