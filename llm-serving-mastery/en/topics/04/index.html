Learning outcomes

  1. Trace an SDK request through frontend, template, engine and GPU worker.
  2. Pin and verify served model identity and tokenizer revision.
  3. Reassemble split UTF-8 and SSE records and distinguish content, finish, usage, DONE, cancellation and incomplete EOF.
  4. Calculate context/KV admission bounds and diagnose validation, transport and worker failures.

Acceptance checklist

  • The pinned local snapshot starts with a bounded GPU budget and stops cleanly.
  • `/v1/models` advertises the name sent by the client.
  • Non-streamed and streamed chat both succeed; raw bytes replay to the same content, finish reason, usage and `[DONE]`.
  • Wrong-model and over-context requests fail clearly.
  • CPU fixture playback is not a live GPU service result; interrupting the runner must clean up its owned server group.
  • Single-request client times are not called p95 or a concurrency benchmark.

Open the primary sources

  • WHATWG · parsing server-sent events — UTF-8, line endings, multiline data, comments and blank-line dispatch. The application-level finish/DONE contract is separate from SSE framing and browser EventSource reconnection.
  • vLLM / PagedAttention — Paged KV state and the serving-system design trade-off.
  • Pinned Qwen2.5-3B configuration — Layer, KV-head, and head-dimension inputs to the worked KV calculation.
  • Pinned Qwen2.5-0.5B-Instruct configuration — Pinned model dimensions for the teaching notebooks; use the recorded runtime and actual selected attention path.
  • vLLM OpenAI-compatible server — Routes, model identity, and chat-template behavior; check version-specific caveats.
  • vLLM serve CLI — Serve flags and bounded startup settings; recorded run values are in course evidence.

Experiments and recorded evidence

  • Trace the request path — Where could impossible work be rejected before entering an unbounded queue?
  • Budget live KV tokens — Why can logical KV payload fit while a real service still runs out of memory?
