Mini-Infrathon: contract, controller, journal

The final week of the course: you design a bounded optimization contract, write controller rules that reject contract violations, and orchestrate your own coding agent (or run the loop yourself) on one admission-policy task. The graded artifacts are the supervision artifacts — not the agent’s raw output.

What happens this week

  • The week opens after Topics 13–15: you already own the admission policy (Lab 08), the hash-chained journal (Lab 09), the multi-GPU scale story (Lab 10) and the controller vocabulary (Labs 11–12).
  • You give the agent ONE file and ONE task; everything else this week is supervision.
  • The submission is four artifacts — texts and diffs. Nothing needs to run on the reviewer’s machine.
  • The manual-supervision track (no agent) is a full pass: the same artifacts 1–2, your own run journal, and a section “how I would change the contract for an agent”.

The W/P/E/R/T contract

Download the template, fill all five fields, commit it as capstone/CONTRACT.md in your submission repository.

FieldWhat to fill in
W — workspaceRepository/branch; the single file or function being optimized (e.g. the Lab 08 gateway admission policy: runtime/gateway/app.py, the admit() function); the agent’s boundary of change: this file ONLY — touching tests, thresholds, the journal or the evaluator rejects the whole submission.
P — public testsWhat correctness means (e.g. 200 on a slot pass, 429 on overflow, honest Retry-After, queue ≤ limit invariant); determinism (fixed seed); an honest list of what the tests do NOT check.
E — private evaluationThe load profile (derived from real layer-2 run journals; the seed is declared before the run; the file is unavailable to the agent); the metric without a ceiling: M = … (formula); why M cannot be hacked without improving the system.
R — resourcesYour CPU or the layer-2 gateway (127.0.0.1:8760), no GPU; explicit limits (≤ N requests per tick, ≤ 200 ticks per run).
T — budget and stop ruleWall-clock ≤ … h for the week; ≤ … submissions (each = a commit + an M measurement on E through the evaluator); stop: “plateau of ≥ k submissions without improving M” or budget exhausted — “the agent says it is done” is NOT a stop criterion.

Three questions every metric must answer

  1. What happens to M under an “improvement” that breaks the SLA?
  2. Which system parameters the agent CANNOT touch, and why that is fair (capacities come from the hardware, not from the policy code)?
  3. How do you verify that the measured commit is exactly the submitted one (byte-for-byte, no cache)?

The controller: three barriers

Turn the three barriers into checkable rules. Examples of well-formed rules:

  • A submission is rejected if git diff --stat touches anything other than the declared file (task violations).
  • M is recomputed from scratch on a clean copy of the commit; an evaluator-cache hit in the journal annuls the submission (unreliable testing).
  • The optimization continues until the stop rule from T fires; “the model believes the task is solved” statements are ignored (premature completion).

Automatic zero regardless of the sum

  • A capstone submission lands in a round-N leaderboard scoring.
  • The agent changed tests, thresholds or the journal.
  • The journal is non-deterministic: the same commit produces different M values.
  • There is no agent/student declaration.
