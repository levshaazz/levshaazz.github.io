Chapter 01: Modern LLM inference systems & production challenges

A working endpoint is not yet a working service. Follow one request from the client clock to the GPU and back; at every boundary, ask what can wait, fail, or remain allocated after the client disappears. Reading route The measured 64-client incident From aggregate to raw requests Ownership, clocks and the queue The pinned single-request trace Metrics and denominator traps Capacity models, deadlines and overload Arrival clocks and missing observations Architecture, routing and rollout From the chapter to your submitted artifacts Exercises and answer reasoning Before starting: the vocabulary you will actually use You need Python, a basic understanding of an HTTP request/response, and the idea that a language model chooses a next token from a probability distribution. You do not need CUDA programming or Kubernetes to follow this chapter. A token is an ID in a tokenizer vocabulary, not necessarily a word or character. A sequence is one request's ordered input and generated tokens. A worker is the process or logical execution owner that runs model work; a replica is another independently serviceable model instance, which may itself use more than one GPU. We start with one worker on one GPU. Prefill processes the known input and prepares attention state and next-token logits. Decode repeatedly advances the generated sequence. The KV cache retains attention keys and values from prior positions so the model need not recompute those projections at every step. It is not a cache of complete answers. Admission decides whether new work may enter; scheduling chooses which already eligible work advances. A queue stores waiting work; it does not provide extra compute. These are different responsibilities even if one Python process implements all of them. A service-level objective (SLO) names a desired observable outcome over a declared population and window, such as “at least 99% of attempts complete within five seconds.” A deadline is the last acceptable completion time for a particular request. A timeout is an observer's decision to stop waiting; it does not automatically stop remote computation. Throughput counts completed work per time; goodput narrows that work to what the stated contract considers useful. The exact course T4 token-goodput definition is given below. Never assume a paper, benchmark and product use the same definition just because they share a metric name. For a first reading, follow the measured incident, the request path, the clocks and the worked load examples; then answer exercises 1–4 before opening their reasoning. On a second pass, follow the architecture decisions and produce your own boundary trace. Each measured number names its run; constructed examples teach a calculation without pretending to be additional GPU evidence. The 64-client incident On a Tesla T4, the course sent 64 simultaneous chat requests in each of three waves to two serving paths using the same pinned Qwen2.5-1.5B-Instruct model in FP16. Each path received 192 attempts with a 60-second client timeout. The serialized baseline timed out on 154 attempts; vLLM timed out on none. Among successful attempts, p95 time to first token was 53.251 seconds for the baseline and 0.523 seconds for vLLM. The protocol and raw request records show both denominators. A percentile calculated only from the 38 baseline successes must never conceal the 154 failures. The useful explanation is not “the GPU is faster.” The baseline held a single generation lock: an asynchronous HTTP frontend could accept sockets while generation remained serial. The lesson is to draw the gateway, admission decision, waiting queue, scheduler, worker, and response stream separately. The same experiment does not establish universal vLLM speed, a production SLO, or performance on another device. Two experiments, not one blended story We will use two measured records throughout this chapter. The first is the Tesla T4 burst comparison above: the pinned 1.5B model, FP16, eight fixed prompts, at most 128 output tokens, simultaneous closed-loop waves of 1, 8, 32 and 64 clients, three repeats at each point, and a 60-second client timeout. The intentionally simple pipeline had a single lock around generation. vLLM ran the same request interface and model revision, but the two runtimes did not promise identical hidden defaults or cold-start behavior. The second record is a much smaller Topic 01 exercise on an RTX 5070 Ti: one pinned 0.5B model request and a separate streaming-proxy request. They answer different questions. One is a burst-system demonstration; the other teaches how to name clocks at a request boundary. It would be tempting to take the first request's 0.036-second first text chunk on the newer GPU and combine it with the T4's 64-client throughput to announce a wonderfully fast serving system. That would cross models, devices, runtimes, workload shapes and observers. We will instead keep a ledger: which run, which population, which clock, which successful work, and which failure produced each number. That habit matters more than memorizing either number. Worked calculation: 154 failures are not a footnote At 64 clients there are three waves, so the denominator is 64 × 3 = 192 attempts per server. For the serialized baseline, 192 − 154 = 38 complete requests. The failure fraction is 154 / 192 = 0.80208… , or 80.2% to one decimal place. The completion fraction is 19.8%. The reported 53.251-second p95 TTFT is therefore computed among only those 38 completions. It is not a percentile for the full attempted population. Replacing each missing TTFT with 60 seconds would manufacture a different statistic, not repair this one: the historical client reset ttft to null on any failed attempt, including failure after content had arrived. Missing TTFT therefore means not retained , not “no token arrived.” A 60-second timeout does not establish the first-content time. At one client, the median goodput ratio is only about 3.3×, and the first serialized wave was cold. A single headline speed-up hides the shape of the work. To locate that work, we need owner-side traces and release events. This is where a performance table turns into an architecture question. Who owns the wait? Client and edge: capture the request start, deadline, route, model name, and first visible content. A 200 status or open port proves little about completion. Admission: check estimated tokens, tenant policy, queue depth, and remaining deadline. An explicit early rejection can be more honest than letting impossible work time out. Scheduler: decide which live sequences advance. Scheduling changes both first-token wait and the decode cadence of requests already accepted. Orca studies iteration-level scheduling; vLLM/PagedAttention addresses efficient request-state management. Worker: tokenize, prefill, decode, sample, and free KV state on completion or cancellation. A disconnect that only closes the socket can leave costly GPU work alive. Instrument each ownership boundary with an event and a release event. If the client sees a slow first chunk, its single timestamp cannot prove whether queueing, prefill, or a buffering proxy is responsible. Compare owner-recorded span durations; do not subtract wall clocks on unsynchronized hosts. The separation is logical; a runtime may co-locate several stages. A request handler is not the serving system Imagine a frontend that can parse 64 JSON bodies concurrently and immediately places each on an asynchronous task. If all those tasks call a generator protected by one lock, there is still only one active generation. An HTTP health check can stay green, TCP connections can stay open, and GPU memory can appear allocated while almost every client waits. “The API is async” describes the outer boundary; it says nothing about how many model sequences make progress. The measured T4 pipeline intentionally exposed precisely this failure mode. Calling it a general Transformers defect would be unfair: a different server could batch requests or use a different scheduler. At each boundary ask a sharper question. What is the unit that enters—request, prompt token, sequence, decode step? What resource is scarce—CPU tokenization, queue slot, VRAM, bandwidth, kernel launches, or client deadline? Who chooses the next unit of work, and who notices cancellation? The answer often changes within one request. Prefill may be large parallel work; decode is a sequence of dependent steps. The queue can grow while the device is busy, or even while the device is underused because the CPU is failing to feed it. A system diagram is useful only when it makes those alternatives testable. The client clock and the engine clock A client can time an entire exchange from the moment it sends a request until it receives the terminal response. An engine can separately time admission wait, tokenization, prefill, individual decode steps and cleanup. These spans do not automatically add up across machines: timestamp origins may differ, retries may overlap, and proxy buffering may delay delivery after the engine produced output. Prefer a common trace ID, monotonic durations measured by each owner, and explicit event boundaries. If you have only client timings, report only client timings; do not pretend to know that the GPU was slow. TTFT depends on the declared start and what counts as first output. A first nonempty text chunk is not necessarily the first model token; proxy buffering can shift the client event without changing prefill. Three ways to get a slow first token Consider three hypothetical traces with the same two-second client-observed first-content time. In trace A, admission waits 1.8 seconds and prefill takes 0.1 seconds. In B, admission is immediate but a long prompt spends 1.8 seconds in prefill. In C, queue and prefill each take 0.1 seconds, followed by 1.8 seconds of delivery/buffering. They have approximately the same client symptom and very different remedies. Queue tuning may help A; prompt or prefill optimization may help B; transport configuration is the right layer for C. To distinguish them, record gateway receive, admission, engine start, first engine output and first client-visible content with a shared request ID. If clocks are not synchronized, compare durations within an owner or emit causal parent/child spans; do not subtract raw wall timestamps from different hosts. A useful incident report says “the time is in the queue” only after that separation is visible. A waiting queue is a policy decision A queue can be valuable: a short burst need not become a rejection if the service has headroom before deadlines expire. But a queue that accepts more work than can be completed converts overload into late failures. It also consumes memory for request objects and may hold client connections. An admission policy should therefore know the request's deadline and a conservative estimate of the work still ahead. A request with a 2,048-token prompt and 512-token output cap is not the same size as one with 64 and 32 tokens; counting only sockets hides that difference. Why 56 chunks cannot be reported as 56 tokens The pinned Topic 01 record says 43 input tokens and 63 output tokens. Its streaming proxy counted 56 nonempty text chunks. A transport chunk is a delivery unit; a token is a tokenizer unit; a visible character sequence may span either boundary. The first nonempty chunk may contain several tokens, part of a token's displayed spelling, or text after buffering. It is therefore accurate to report “first nonempty text chunk at 0.036 seconds in one streaming proxy run.” It is not accurate to rename that number TTFT under a token-observer definition, nor to calculate ITL by dividing the remainder by 55 chunk gaps. The raw sanitized result keeps the fields distinct. The 4.51-second model load is another boundary. Including it in a cold client request might be valid if that is how the service is deployed; excluding it is valid for a warm steady-state question. Mixing one cold request with warm requests and calling the result a single latency distribution makes both questions harder to answer. Record at least the model load, warmup state, tokenizer and model revision, input/output counts, request start and finish, and the observer of first output. On the instructor machine, the teaching notebook deliberately separates load and request timing. Prefill and decode are different service demands Given a known prompt, prefill can process its positions in parallel and populate initial key/value state. Decode cannot know output token t+1 until it has computed the logits and sampled or selected token t . Different requests can share a decode iteration, but each individual output chain remains sequential. This is why a request's input and output lengths matter separately. A long input and short output can concentrate work near the first token; a short input and long output can occupy the scheduler for many iterations. Topic 02 turns that intuition into phase shapes and measured phase timings. The model still needs request state after the first token. KV cache grows with retained context, and a new decode step reads prior state. A server that accepts many live requests without accounting for tokens can hit a memory limit even if its request-count limit looks conservative. PagedAttention addresses allocation and sharing of KV blocks; it does not make KV cost zero. Nor can an iteration-level scheduler solve an overloaded input rate by itself: if demand persistently exceeds the service's attainable completed-work rate, some combination of waiting, shedding, scaling or deadline failure remains necessary. A metric is a population plus a clock TTFT, inter-token latency, end-to-end time and throughput are not interchangeable views of one stopwatch. In a streaming service, TTFT might start at client send and end at first visible token; an engine-side first-token time starts later and ends before transport. An ITL is one interval between adjacent tokens for one stream. Mean time per output token averages a set of such gaps; averaging again across requests requires a declared weighting rule. End-to-end latency includes the entire completion or a declared termination. Successful-output goodput counts delivered work over complete wall time; raw generation-token rate can be higher while customers receive little. Every dashboard should state those boundaries. From a clock to a capacity hypothesis For a worked model, not this measured GPU run , suppose stable arrivals average 8 requests per second and average time in the system is 0.5 seconds. Little’s Law gives average in-flight work L = λW = 8 × 0.5 = 4 requests. This is a consistency check, not a safe queue-size setting. It says nothing about a burst of 64 simultaneous arrivals, long-tail service time, output-length mix, or whether the GPU can hold their KV states. The original Little’s Law result assumes a stable system; overload violates the intuition people often attach to the average. For a capacity experiment, fix the model revision, input/output distribution, timeout, arrival process, and scoring contract. Run increasing load, then report successful-output goodput, successful-request TTFT and end-to-end distributions, rejects, timeouts, and resource headroom side by side. Worked calculation: Little’s Law cannot size a burst queue Consider the illustrative stable system just described: λ = 8 completed requests/s and mean end-to-end time W = 0.5 s . The mean number of requests in the system is L = λW = 4 . The units cancel correctly: requests/second times seconds leaves requests. Residence time has units of seconds, not seconds per request; the average is taken over requests, but that does not add a denominator to its physical unit. This is a statement about a steady average over a stable population. If a 64-request wave arrives at one instant, L = 4 does not mean only four requests can be present or that 60 should be rejected. It means the chosen average rate and delay cannot coexist with some other long-run mean concurrency without changing the workload or measurement boundary. Now construct a second illustrative system whose sustainable completion rate is only six requests per second while arrivals average eight requests per second. The backlog grows by roughly two requests each second until admission or traffic changes; there is no stable finite mean waiting time to plug into the same comforting equation. Little's Law itself is not wrong—the steady-state premise is missing. In production, look for a bounded observation window, a stable arrival/completion balance and explicit abandoned requests before using the law as a consistency check. The original Little result gives the theory; a queue-capacity setting requires workload tails and deadlines that the equation does not supply. Averages erase arrival shape; open-loop steady traffic and simultaneous closed-loop waves must not be treated as interchangeable tests. Worked decision: can this request still meet its deadline? Suppose a fictional API promises a five-second client deadline. An arriving request has already spent 0.2 seconds in transit and validation. The queue estimator predicts 3.9 seconds of wait, and the workload-specific service estimate is 1.4 seconds. The optimistic finish is 0.2 + 3.9 + 1.4 = 5.5 s , exceeding the deadline before the worker starts. Admitting it merely to time out later consumes a connection and possibly compute that could serve feasible work. A bounded, explicit reject can be better for both the user and neighboring requests—if the contract says what the rejection means and the client can back off. The estimates here are illustrative ; they are not calibrated from our GPU run. Such a decision needs a margin because service-time estimates are uncertain and output lengths vary. A short output cap may fit when a long one does not. A server may choose priority, fairness, a per-tenant queue, or a hard reject, but each policy has costs: rejecting too aggressively wastes spare capacity; admitting too freely hides overload behind late timeouts. For a real policy, record prediction error by request shape and compare outcomes around the decision boundary. The important separation is between capacity (can the system execute eventually?), deadline feasibility (can it execute in time?), and admission fairness (which tenant receives scarce time?). Cancellation is a resource release protocol When a client disconnects, the edge may detect it before the scheduler does. If the worker continues decoding, it still consumes GPU time and retains KV for tokens no user will read. A correct cancellation path must convey the request identity to every owner, remove or mark queued work, stop future decode steps when safe, release KV blocks and record whether the client saw a partial answer. Some work already in flight cannot be undone instantly, so “cancelled” should refer to a declared point in the lifecycle, not a magical rollback of completed kernels. Think of a 60-second timeout in the T4 run. From the client record alone we know the attempt failed its deadline. We do not know exactly how much GPU work occurred before cancellation or how promptly memory was reclaimed. The run's naive server log and vLLM log are available for investigation, but the reported goodput deliberately counts only completed output. A production cancellation experiment would instrument disconnect, scheduler removal and memory release as separate events. It would also probe what happens if a stream disconnects after some visible chunks: the answer is partial, not completed. A retry can be a second arrival, not a second chance At overload, clients often retry after a timeout. If the first request is still queued or generating, a blind retry adds more demand and can worsen the original problem. For an illustrative 100-request burst where 40 time out and all 40 immediately retry once, the server receives 140 attempts for only 100 original user intents. If half of those retries time out again and retry once more, attempts rise to 160. Counting attempts without a stable idempotency key can make traffic look like user growth rather than policy amplification. A backoff with jitter and a retry budget can reduce synchronization; a server still needs to surface explicit overload and honor cancellation. For text generation, retry semantics are not trivial. A stochastic response may differ on each run, and the client may have received partial text before losing the connection. The service must say whether retrying with the same request ID resumes, repeats, or creates a new generation. The simple T4 benchmark did not exercise this protocol. The chapter introduces it because a serving architecture that omits retries can appear healthy in a benchmark and collapse under real client behavior. Fan-out moves the queue you forgot to draw A user-visible request may call a router, retrieval system, safety classifier, main generator and post-processor. If they run sequentially, their delays accumulate; if some run in parallel, the slowest required branch gates completion. A local GPU benchmark measures only one piece. Consider an illustrative endpoint with 40 ms routing, 90 ms retrieval, 600 ms generation and 30 ms validation in sequence: the minimum component sum is 760 ms before network overhead and queueing. If generation is streamed but the post-processor buffers the entire answer, the client may see no early chunks despite a fast engine-side first token. When diagnosing a bad SLO, first draw the critical path and owner spans, then choose which component to profile. Fan-out can also multiply failure probability. If a response requires all of three independent branches that each succeed 99% of the time, the idealized joint success is 0.99³ ≈ 97.0% . Independence is an assumption, and shared infrastructure failures make it optimistic. A faster successful p95 with more failures is not automatically an improvement. Who owns the arrival clock? An open-loop generator schedules arrivals independently of whether earlier requests have finished. For example, it intends to send at 0, 1, 2, 3 and 4 seconds. A closed-loop user sends, waits for a response or timeout, optionally thinks, and then sends again. Both are legitimate models. An interactive user who reads each answer is naturally closed loop. An externally driven stream of incoming jobs can continue arriving while the service slows and is better represented by an independent arrival schedule. Choosing one is a statement about the question, not a contest between good and bad benchmarks. For a stable closed-loop population of N users, mean response time R seconds and mean think time Z seconds, completed cycles per second are approximately X = N / (R + Z) . With 32 users, R = 0.8 s and Z = 0.2 s , the rate is 32 requests/s. If response time grows to 3.8 seconds while the users still wait before sending, the offered rate falls to eight requests/s. The server did not gain capacity; the test population slowed its own demand. “Concurrency 32” by itself therefore does not specify requests per second, token demand, a burst pattern or a sustained service objective. The T4 experiment sends a finite simultaneous wave and waits for its outcomes. It is not the steady closed-loop population in that equation, and it is not an open-loop capacity experiment. To reproduce its meaning, preserve the wave protocol. To ask a new question about sustained independent arrivals, write a new protocol with a target schedule, duration, token mix, timeout and generator capacity. Record intended arrival times as well as actual sends: a saturated load generator can silently change the workload even when the server has spare capacity. A missing request is not a fast request Suppose the intended workload is one request per second. At time zero the service stalls for four seconds. A blocking single-client test waits and next sends at time four. It has no samples for the requests intended at times one, two and three. If it summarizes only the responses it happened to issue, the histogram answers a different question from “what happens to arrivals that keep coming during the stall?” This mismatch is called coordinated omission : the act of waiting coordinates the measurement schedule with the delay being measured. Keep three events for a scheduled request: scheduled_send , actual_send and terminal , measured on the generator's monotonic clock. Then actual_send − scheduled_send is generator scheduling lag, terminal − actual_send is observed exchange duration, and terminal − scheduled_send includes lag relative to the intended workload. Why a little less headroom can mean a lot more waiting For background, see MIT’s M/M/1 teaching note . A useful analytical counterexample is the M/M/1 queue : Poisson arrivals at rate λ , independent exponential service times with mean 1/μ , one server, an unbounded FIFO waiting room and a stable load λ &lt; μ . The two M symbols denote memoryless arrival and service processes. This is a model of waiting, not a claim that batched GPU inference has exponential service or one-request-at-a-time execution. Under those assumptions, utilization is ρ = λ/μ , mean response time is W = 1/(μ − λ) , and mean queue wait is Wq = W − 1/μ . At μ = 10 requests/s , mean service is 0.1 seconds. At arrivals of five requests/s, response is 0.2 seconds and queue wait is 0.1 seconds. At nine requests/s, response is one second and queue wait is 0.9 seconds. At 9.5 requests/s, response is two seconds and queue wait is 1.9 seconds. The service did not become twenty times slower; waiting now dominates residence. These are means , not p95 values. A real inference service violates several assumptions: service depends on input and output lengths, requests share iterations, caching changes work, finite queues reject, and memory pressure can force preemption. Use the model to reject the intuition that “95% busy is almost the same as 50% busy,” not to derive a production queue limit. Validate an operating envelope empirically. If a load sweep produces passing points at 2, 4 and 6 requests/s and failing points at 8 and 10, then six is the last tested passing point . The exact boundary between six and eight remains unresolved. Attach an error budget and sampling plan to the boundary. Zero observed failures in 192 attempts is not proof that the true failure probability is zero. If attempts were independent with a fixed failure probability, the probability of observing none would be (1 − p)^192 ; setting this to 0.05 gives a one-sided 95% upper bound of about 1.55%. The “rule of three” approximation gives 3/192 ≈ 1.56% . Shared burst failures violate independence, so even that simple calculation should not be sold as a production guarantee. It explains why a short clean demo cannot validate a stringent reliability SLO. Choose a topology from the constraint, not the fashion Start with the simplest architecture that has an owner for each required guarantee. An offline worker consumes a backlog and writes completed results; it may prioritize total completion time and retryable checkpoints over interactive latency. A single interactive engine exposes a streaming endpoint and owns its admission, scheduling and local state. A gateway plus replica pool introduces routing, health and capacity distribution. These are logical shapes: a gateway can begin in the same process, and a worker may later be split across processes or devices. Every new boundary also introduces failure, observability and state-transfer obligations. For a nightly document-labeling job with no interactive deadline, adding a streaming gateway does not solve the dominant problem. A bounded job queue, durable output IDs and restartable progress may matter more. For a small interactive assistant that fits on one GPU, a single engine plus a clear API contract can be the best first baseline. For independently arriving tenants whose combined load exceeds one worker, a replica pool can supply capacity, but only if routing and admission avoid concentrating work on one replica. Requests are not equal-sized routing units Imagine two identical workers each reporting two queued requests. Worker A has two 128-token prompts; worker B has two 4,096-token prompts. When separating prefill and decode might help Prefill and decode have different work shapes and can interfere with each other's latency. Separating them into specialized workers offers independent scaling and scheduling, but it creates a KV-state transfer boundary. The decode worker cannot continue from a prompt it has not computed unless the necessary state is available. The DistServe paper studies this disaggregated design. It is an architectural option, not a default speedup for every model, GPU or network. A useful first calculation is a transfer lower bound: transfer seconds ≥ state bytes / effective bytes per second . If a constructed request needs 1 GiB of state and the effective link delivers 25 GiB/s, payload transfer alone takes at least 40 ms. At 5 GiB/s, it takes 200 ms. Treating both as “GPU inference” hides the shapes, bytes, and timing boundary that an optimization must actually change. They are a good puzzle: if one global “tokens per second” number explained inference, these two phase responses would be hard to describe. The answer begins with the dependency graph. The prompt is known up front. Output tokens are not. Inside each GPU operation there may be enormous parallelism, but the next output token still depends on the previous one. That serial axis changes how much work can be batched and reused. It also changes what a profiler snapshot means: a kernel may be efficient and still sit inside a service dominated by sequential steps, launches, waiting, or data movement. From text to a tensor: what actually enters the GPU? Imagine a document assistant receiving a question and a long retrieved passage. Before the decoder sees anything, a chat template may add role delimiters and control tokens, and a tokenizer maps the resulting byte/text sequence to integer IDs. A token can represent part of a word, punctuation, whitespace or a special marker. Counting words is therefore not an acceptable substitute for measuring tokenized length. The lab deliberately bypasses a realistic chat workload: it repeats a short token-ID pattern to produce exactly 128 or 4,096 positions. That makes the shape experiment reproducible, but it does not test retrieval quality, useful answer length or semantic diversity. The input tensor has a batch axis and a sequence-position axis, conventionally written [B,S] . Its elements are integer indices, not semantic vectors. An embedding table with vocabulary size V and hidden width d selects one floating-point vector per ID, creating [B,S,d] . For an illustrative B=2,S=128,d=896 , that is 2×128×896=229,376 values. At two bytes per value it occupies 458,752 bytes, or 448 KiB, for this tensor alone. It does not count the embedding table, all later activations or KV state. The same symbol “B” sometimes means bytes in systems writing and batch size in model equations; this chapter writes units explicitly to keep those meanings separate. One decoder block: projections, mixing and a residual path The hidden representation entering a block is transformed by normalization, attention and a feed-forward network, with residual connections preserving a path from the block input to its output. In the pinned Qwen2 family, the model's own implementation and configuration—not a generic transformer cartoon—determine normalization, rotary position handling, projection widths and grouped-query heads. For the performance argument, three questions matter at each operation: what are the dimensions, which values must be fetched, and which earlier result must already exist? A dense projection multiplies token rows by a weight matrix; attention mixes information across allowed positions; the feed-forward portion performs more per-position dense work. These are different sources of arithmetic and traffic. Write a projection as [M,d] × [d,d_out] → [M,d_out] . Flattening batch and newly processed positions yields M=B×S in a full prefill. With eight sequences of 512 prompt positions, M=4,096 . In the next ordinary decode iteration, the same eight sequences contribute one new position each, so M=8 . The retained 512-position history belongs in attention's K/V axis; it does not turn the new-query projection back into a 4,096-row projection. This is the concrete meaning of “same model, different workload.” A model filename alone leaves out the most important dimensions of the kernel problem. After the final block, a vocabulary projection creates logits—unnormalized scores, one per vocabulary entry. Softmax converts them to a probability distribution; greedy decoding simply selects the largest score, whereas sampling uses a declared stochastic rule. For toy scores [2,1,0] , softmax is approximately [0.665,0.245,0.090] , and greedy selection chooses the first item. These toy values do not describe Qwen's real output. Once that token ID is chosen, it becomes an input to the next forward. This data dependence is the serial link; it is not a claim that one token requires only one operation or that the GPU lacks parallel work inside that forward. The first token is not a decode forward Keep a tiny ledger before writing a timer. With prompt IDs x1…x4 , prefill computes their K/V and logits for choosing y1 . Immediately after the choice, the cache contains four positions, not five: choosing an ID does not compute its hidden states. Feeding y1 back creates its K/V and permits choosing y2 ; the cache now has five positions. Feeding y2 back permits choosing y3 ; the cache has six. The lab checks this invariant at runtime: after selecting O outputs, retained length is P+O−1 . A conservative serving capacity plan may reserve P+O positions, but should say that it is a budget rather than a tensor observation. Likewise, a 128-output answer has 127 post-first gaps. If their arithmetic mean is 22 ms, their total is exactly 127×22=2,794 ms . Adding the actual first-token interval gives a larger completion interval. If 22 ms were only the median gap, multiplication would not reconstruct the total. A small set of slow gaps could leave the median unchanged while making completion much later. The lab's mean decode step interval is total decode wall time divided by O−1 ; it is not a distribution of individually timestamped token events, and it is not a client streaming ITL measurement. The serial token axis At decode step t , the model cannot choose token t+1 until logits for t exist. Work within a step can be massively parallel, and multiple sequences can be batched, but the output-token dependency remains. Prefill instead processes many known prompt positions together. Thus long input with short output and short input with long output can stress different parts of the same GPU. FlashAttention is a concrete example of optimizing attention through IO-aware tiling; it is not a claim that all service delay lives inside that kernel. A pair-count is not a wall-time model In a simplified dense causal attention calculation, a prompt of length P has on the order of P²/2 valid query–key pairs. Increasing P from 128 to 4,096 multiplies that attention pair count by roughly (4096/128)² = 1024 . Yet the measured prefill medians above changed by only about 6.68×. There is no paradox. Attention scores are one component of a transformer layer; projections and feed-forward work scale differently, fixed overheads matter, the GPU can exploit larger shapes differently, and IO-aware kernels avoid materializing the full score matrix in slow memory. Pair count is a mathematical work term, not a prediction of service milliseconds. The first output is selected from the prefill logits, so O generated outputs require D=O−1 subsequent decode forwards. At decode query j=1…D , the current input token adds its own K/V and attends P+j positions. Summing per-head query–key pairs gives DP+D(D+1)/2 . With O=256 , D=255 : a 512-token prompt gives 255×512+255×256/2=163,200 pairs; a 4,096-token prompt gives 1,077,120 , exactly 6.6× as many. These are decode-only pair counts per head, not prefill work, HBM bytes, or a 6.6× wall-time prediction. Changing the definition of a “step” without changing the summation is an off-by-one error, not a harmless notation choice. Batching changes the effective machine problem At batch one, each decode step produces one new token for one sequence. If several sequences advance together, the same model weights may be used for multiple token computations in the iteration. That can increase useful work per weight byte moved, but it also raises live KV demand and may lengthen an individual request's decode cadence. “Higher aggregate tokens/s” and “better per-user latency” are distinct outcomes. A scheduler must trade first-token wait, fairness, ongoing stream smoothness and memory headroom. The single-request phase table cannot tell us where a multi-request optimum lies; it intentionally isolates component behavior before queueing and scheduling are added back. A fusion example with bytes, not marketing language Take three elementwise functions over N values. An unfused implementation reads input X, writes intermediate A, reads A, writes intermediate B, reads B and writes output Y. Ignoring cache effects, this is six transfers of N elements. If one fused kernel keeps the intermediates local, it may need only the initial read and final write: two transfers. At N=1,048,576 FP16 elements, the useful payload is 12 MiB versus 4 MiB. The mathematical result and operation count can be essentially unchanged while the data movement and launch count shrink. That accounting does not promise a threefold time reduction. Perhaps the original intermediates already hit in cache; perhaps the fused kernel uses too many registers; perhaps arithmetic dominates; perhaps launch savings matter more than traffic. Capacity, bandwidth, latency—and allocator behavior A capacity bottleneck means the required live objects cannot coexist in available memory, or cannot do so with safe headroom. It appears as admission rejection, allocation failure, paging or a runtime's lower-than-expected active-sequence limit. A bandwidth bottleneck means useful work is limited by the rate of moving bytes at a chosen level; the program can fit perfectly and still spend most device time waiting for data. A latency bottleneck concerns dependent fetches whose waits are not hidden by enough independent work; fitting the tensors and having high aggregate bandwidth do not remove those dependencies. A separate fragmentation or reservation problem means logical payload calculations understate allocator behavior and reusable pools. Calling all these mechanisms “VRAM bottleneck” conceals the remedy. Weight quantization could improve capacity but slow a kernel; better batching could improve weight reuse but raise KV capacity pressure; changing allocator settings could alter reservation without changing the mathematical work. Use the right observation for each claim. For capacity, collect peak allocated and reserved memory under the target live-token mix and count failures. For bandwidth, profile actual traffic and execution at the memory level in question and compare with a relevant achieved bandwidth—not only a vendor peak. For fragmentation, inspect allocation patterns over repeated arrivals/cancellations and the runtime's block management. A one-number GPU dashboard cannot identify which mechanism is responsible. This distinction sets up the quantization trade-off in Chapter 03: smaller representation is one possible lever, not a diagnosis by itself. Parallel processing of prompt tokens that builds initial KV state and produces the first-token logits.

Why one order at a time wastes the stove

Why one order at a time wastes the stove Every decode step reads all the weights $$ t_{\text{step}} \;\gtrsim\; \frac{\text{bytes of weights}}{\text{memory bandwidth}} \;=\; \frac{8\ \text{GB}}{896\ \text{GB/s}} \;\approx\; 9\ \text{ms} $$ B = 1 One token per step for one request → ≤ ~110 tokens/s , no matter how fast the math units are. B = 64 The same weight read serves 64 requests → ceiling ~64× higher , until compute or memory runs out. ⇒ Batching is cheap in weight traffic during decode. Compute, KV traffic and scheduling still grow. Example: a 4B-parameter model in BF16 = 8 GB of weights; the judge GPU (RTX 5070 Ti) has about 896 GB/s of memory bandwidth. To produce one token, the GPU has to stream every weight from memory once: ≈ 9 ms. So a single request is capped near 110 tokens/s — the arithmetic units sit mostly idle, waiting for memory. If 64 requests decode in the same step, the weight traffic can be amortized across the batch. That does not make batching free: matrix compute, KV-cache reads and writes, scheduling work and memory capacity all grow, and the workload eventually becomes compute-bound or runs out of KV cache. This is a lower bound on step time and an upper bound on speed — real numbers are lower. Topic 2 does this properly (roofline, arithmetic intensity).
