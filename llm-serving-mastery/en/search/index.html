A request handler is not the serving system Imagine a frontend that can parse 64 JSON bodies concurrently and immediately places each on an asynchronous task. If all those tasks call a generator protected by one lock, there is still only one active generation. An HTTP health check can stay green, TCP connections can stay open, and GPU memory can appear allocated while almost every client waits. “The API is async” describes the outer boundary; it says nothing about how many model sequences make progress. The measured T4 pipeline intentionally exposed precisely this failure mode. Calling it a general Transformers defect would be unfair: a different server could batch requests or use a different scheduler. At each boundary ask a sharper question. What is the unit that enters—request, prompt token, sequence, decode step? What resource is scarce—CPU tokenization, queue slot, VRAM, bandwidth, kernel launches, or client deadline? Who chooses the next unit of work, and who notices cancellation? The answer often changes within one request. Prefill may be large parallel work; decode is a sequence of dependent steps. The queue can grow while the device is busy, or even while the device is underused because the CPU is failing to feed it. A system diagram is useful only when it makes those alternatives testable. The client clock and the engine clock A client can time an entire exchange from the moment it sends a request until it receives the terminal response. An engine can separately time admission wait, tokenization, prefill, individual decode steps and cleanup. These spans do not automatically add up across machines: timestamp origins may differ, retries may overlap, and proxy buffering may delay delivery after the engine produced output. Prefer a common trace ID, monotonic durations measured by each owner, and explicit event boundaries. If you have only client timings, report only client timings; do not pretend to know that the GPU was slow. Three ways to get a slow first token Consider three hypothetical traces with the same two-second client-observed first-content time. In trace A, admission waits 1.8 seconds and prefill takes 0.1 seconds. In B, admission is immediate but a long prompt spends 1.8 seconds in prefill. A waiting queue is a policy decision A queue can be valuable: a short burst need not become a rejection if the service has headroom before deadlines expire. But a queue that accepts more work than can be completed converts overload into late failures. It also consumes memory for request objects and may hold client connections. An admission policy should therefore know the request's deadline and a conservative estimate of the work still ahead. A request with a 2,048-token prompt and 512-token output cap is not the same size as one with 64 and 32 tokens; counting only sockets hides that difference. Prefill and decode are different service demands Given a known prompt, prefill can process its positions in parallel and populate initial key/value state. Decode cannot know output token t+1 until it has computed the logits and sampled or selected token t . Different requests can share a decode iteration, but each individual output chain remains sequential. This is why a request's input and output lengths matter separately. A long input and short output can concentrate work near the first token; a short input and long output can occupy the scheduler for many iterations. Topic 02 turns that intuition into phase shapes and measured phase timings. The model still needs request state after the first token. KV cache grows with retained context, and a new decode step reads prior state. A server that accepts many live requests without accounting for tokens can hit a memory limit even if its request-count limit looks conservative. PagedAttention addresses allocation and sharing of KV blocks; it does not make KV cost zero. Nor can an iteration-level scheduler solve an overloaded input rate by itself: if demand persistently exceeds the service's attainable completed-work rate, some combination of waiting, shedding, scaling or deadline failure remains necessary. From a clock to a capacity hypothesis For a worked model, not this measured GPU run , suppose stable arrivals average 8 requests per second and average time in the system is 0.5 seconds. Little’s Law gives average in-flight work L = λW = 8 × 0.5 = 4 requests. This is a consistency check, not a safe queue-size setting. It says nothing about a burst of 64 simultaneous arrivals, long-tail service time, output-length mix, or whether the GPU can hold their KV states. The original Little’s Law result assumes a stable system; overload violates the intuition people often attach to the average. For a capacity experiment, fix the model revision, input/output distribution, timeout, arrival process, and scoring contract. Run increasing load, then report successful-output goodput, successful-request TTFT and end-to-end distributions, rejects, timeouts, and resource headroom side by side. Worked calculation: Little’s Law cannot size a burst queue Consider the illustrative stable system just described: λ = 8 completed requests/s and mean end-to-end time W = 0.5 s/request . The mean number of requests in the system is L = λW = 4 . The units cancel correctly: requests/second times seconds/request leaves requests. This is a statement about a steady average over a stable population. If a 64-request wave arrives at one instant, L = 4 does not mean only four requests can be present or that 60 should be rejected. It means the chosen average rate and delay cannot coexist with some other long-run mean concurrency without changing the workload or measurement boundary. Now construct a second illustrative system whose sustainable completion rate is only six requests per second while arrivals average eight requests per second. The backlog grows by roughly two requests each second until admission or traffic changes; there is no stable finite mean waiting time to plug into the same comforting equation. Little's Law itself is not wrong—the steady-state premise is missing. In production, look for a bounded observation window, a stable arrival/completion balance and explicit abandoned requests before using the law as a consistency check. The original Little result gives the theory; a queue-capacity setting requires workload tails and deadlines that the equation does not supply. Suppose a fictional API promises a five-second client deadline. An arriving request has already spent 0.2 seconds in transit and validation. The queue estimator predicts 3.9 seconds of wait, and the workload-specific service estimate is 1.4 seconds. Admitting it merely to time out later consumes a connection and possibly compute that could serve feasible work. A bounded, explicit reject can be better for both the user and neighboring requests—if the contract says what the rejection means and the client can back off. A short output cap may fit when a long one does not. A server may choose priority, fairness, a per-tenant queue, or a hard reject, but each policy has costs: rejecting too aggressively wastes spare capacity; admitting too freely hides overload behind late timeouts. Cancellation is a resource release protocol When a client disconnects, the edge may detect it before the scheduler does. If the worker continues decoding, it still consumes GPU time and retains KV for tokens no user will read. A correct cancellation path must convey the request identity to every owner, remove or mark queued work, stop future decode steps when safe, release KV blocks and record whether the client saw a partial answer. Some work already in flight cannot be undone instantly, so “cancelled” should refer to a declared point in the lifecycle, not a magical rollback of completed kernels. Think of a 60-second timeout in the T4 run. From the client record alone we know the attempt failed its deadline. We do not know exactly how much GPU work occurred before cancellation or how promptly memory was reclaimed. The run's naive server log and vLLM log are available for investigation, but the reported goodput deliberately counts only completed output. A production cancellation experiment would instrument disconnect, scheduler removal and memory release as separate events. It would also probe what happens if a stream disconnects after some visible chunks: the answer is partial, not completed. A retry can be a second arrival, not a second chance At overload, clients often retry after a timeout. If the first request is still queued or generating, a blind retry adds more demand and can worsen the original problem. For an illustrative 100-request burst where 40 time out and all 40 immediately retry once, the server receives 140 attempts for only 100 original user intents. If half of those retries time out again and retry once more, attempts rise to 160. Counting attempts without a stable idempotency key can make traffic look like user growth rather than policy amplification. A backoff with jitter and a retry budget can reduce synchronization; a server still needs to surface explicit overload and honor cancellation. For text generation, retry semantics are not trivial. A stochastic response may differ on each run, and the client may have received partial text before losing the connection. The service must say whether retrying with the same request ID resumes, repeats, or creates a new generation. The simple T4 benchmark did not exercise this protocol. The chapter introduces it because a serving architecture that omits retries can appear healthy in a benchmark and collapse under real client behavior. Fan-out moves the queue you forgot to draw A user-visible request may call a router, retrieval system, safety classifier, main generator and post-processor. If they run sequentially, their delays accumulate; if some run in parallel, the slowest required branch gates completion. A local GPU benchmark measures only one piece. Consider an illustrative endpoint with 40 ms routing, 90 ms retrieval, 600 ms generation and 30 ms validation in sequence: the minimum component sum is 760 ms before network overhead and queueing. If generation is streamed but the post-processor buffers the entire answer, the client may see no early chunks despite a fast engine-side first token. When diagnosing a bad SLO, first draw the critical path and owner spans, then choose which component to profile. Fan-out can also multiply failure probability. If a response requires all of three independent branches that each succeed 99% of the time, the idealized joint success is 0.99³ ≈ 97.0% . Independence is an assumption, and shared infrastructure failures make it optimistic. The example does not describe the course service; it shows why a generator-only success rate is not automatically an API success rate. A real service report should name which dependencies were included in the request's success definition. The prompt is known up front. Output tokens are not. Inside each GPU operation there may be enormous parallelism, but the next output token still depends on the previous one. That serial axis changes how much work can be batched and reused. It also changes what a profiler snapshot means: a kernel may be efficient and still sit inside a service dominated by sequential steps, launches, waiting, or data movement. The serial token axis At decode step t , the model cannot choose token t+1 until logits for t exist. Work within a step can be massively parallel, and multiple sequences can be batched, but the output-token dependency remains. Prefill instead processes many known prompt positions together. Thus long input with short output and short input with long output can stress different parts of the same GPU. A pair-count is not a wall-time model In a simplified dense causal attention calculation, a prompt of length P has on the order of P²/2 valid query–key pairs. Pair count is a mathematical work term, not a prediction of service milliseconds. For a single decode step after P prompt tokens and t prior output tokens, attention must refer to about P+t past positions in the simple full-context model. Across O output steps, the cumulative attention-length term is about O×P + O(O−1)/2 . Batching changes the effective machine problem At batch one, each decode step produces one new token for one sequence. If several sequences advance together, the same model weights may be used for multiple token computations in the iteration. That can increase useful work per weight byte moved, but it also raises live KV demand and may lengthen an individual request's decode cadence. “Higher aggregate tokens/s” and “better per-user latency” are distinct outcomes. A scheduler must trade first-token wait, fairness, ongoing stream smoothness and memory headroom. The single-request phase table cannot tell us where a multi-request optimum lies; it intentionally isolates component behavior before queueing and scheduling are added back. Three different meanings of “memory bottleneck” A capacity bottleneck means the required live objects cannot coexist in available memory, or cannot do so with safe headroom. It appears as admission rejection, allocation failure, paging or a runtime's lower-than-expected active-sequence limit. Chapter 03: Model quantization for production

Quantization is a deployment candidate, not a free speed switch. A smaller weight representation can release memory while making a small model slower or changing a strict output format. Decide with a paired experiment, not a bit-count slogan. Reading route The decision before the bit width Representation and metadata Pinned FP16/NF4 evidence Strict quality contracts A conditional deployment decision Exercises and answer reasoning The decision before the bit width Imagine the owner of a single-GPU API says, “The model barely fits; switch to four bits and we will serve twice as many users.” That proposal contains at least four separate claims. The weight payload might shrink. The full process reservation might or might not shrink. The actual kernel path might be faster or slower at the intended batch shape. And the output might still satisfy the product's exact-format and semantic quality rules. A useful quantization experiment must test all four without moving the workload or changing the success denominator after seeing results. The Topic 03 instructor run offers a deliberately small counterexample: on one RTX 5070 Ti and pinned 0.5B model, FP16 and bitsandbytes NF4 both ran, but lower-bit weights did not make the tested path faster or reduce reserved memory. This is not a failure of quantization as a field. It is a reminder that “four bits” names a storage representation, while a deployed request experiences a chain of packing, dequantization or quantized kernels, temporary tensors, KV, scheduling and output checks. A format that is excellent for a larger matrix or a different batch can be poor for a tiny batch-one model. We will keep the decision conditional rather than promoting one small smoke test into a general leaderboard. A candidate format must pass four different gates Kernel supported on this GPU and release? → Memory weights + KV + runtime peak? → Quality hard contracts and held-out tasks? → Service goodput, tails, failures, cost? A smaller checkpoint passes no downstream gate automatically. The actual format, kernel and hardware are part of the candidate's identity. What gets smaller? A scalar integer quantizer maps a value to a code and a reconstruction rule, often with a scale shared by a group of values. The code may clip outliers; the scale and zero point (where applicable) also occupy memory. For an illustrative 3-billion-parameter model, four data bits per parameter are 1.5 billion bytes before metadata. If one FP16 scale serves each group of 128 parameters, scales add approximately 3,000,000,000 / 128 × 2 = 46.875 MB . That is neither the full model file nor live GPU memory: embeddings, non-quantized modules, allocator state, activations, and KV cache remain. Likewise, W4A16, W8A8, FP8, NF4, and quantized KV are not interchangeable names. They change different tensors and may require different kernels or devices. AWQ uses activation awareness to protect salient weight channels; GPTQ uses approximate second-order information to compensate weight quantization. Neither name describes the bitsandbytes NF4 path in this course’s small paired lab. Check the vLLM quantization support documentation against the installed release and actual GPU before making a kernel-speed claim. Worked scalar example: clipping is a quality decision For an illustrative symmetric signed four-bit quantizer, choose representable integer codes from −7 to +7 and a scale s = 0.2 . Reconstruct with q × s , and map an input value by rounding x/s then clipping to the code range. A weight x = 0.86 maps to round(4.3) = 4 and reconstructs as 0.8, error −0.06. A weight x = 1.8 wants code 9 but clips to 7 and reconstructs as 1.4, error −0.4. These are invented weights, not observed Qwen weights. The example isolates why outliers and scale choice matter: the same bit width can have different error profiles. Grouping weights gives each group its own scale, often reducing error at the cost of metadata and implementation complexity. Failed requests divided by all attempted requests under the declared workload and timeout.

Why one order at a time wastes the stove

Why one order at a time wastes the stove Every decode step reads all the weights $$ t_{\text{step}} \;\gtrsim\; \frac{\text{bytes of weights}}{\text{memory bandwidth}} \;=\; \frac{8\ \text{GB}}{896\ \text{GB/s}} \;\approx\; 9\ \text{ms} $$ B = 1 One token per step for one request → ≤ ~110 tokens/s , no matter how fast the math units are. B = 64 The same weight read serves 64 requests → ceiling ~64× higher , until compute or memory runs out. ⇒ Batching is cheap in weight traffic during decode. Compute, KV traffic and scheduling still grow. Example: a 4B-parameter model in BF16 = 8 GB of weights; the judge GPU (RTX 5070 Ti) has about 896 GB/s of memory bandwidth. To produce one token, the GPU has to stream every weight from memory once: ≈ 9 ms. So a single request is capped near 110 tokens/s — the arithmetic units sit mostly idle, waiting for memory. If 64 requests decode in the same step, the weight traffic can be amortized across the batch. That does not make batching free: matrix compute, KV-cache reads and writes, scheduling work and memory capacity all grow, and the workload eventually becomes compute-bound or runs out of KV cache. This is a lower bound on step time and an upper bound on speed — real numbers are lower. Topic 2 does this properly (roofline, arithmetic intensity).
