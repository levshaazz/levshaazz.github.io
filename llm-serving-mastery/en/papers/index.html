Documentation

GKE · Tuning the HPA to run inference on GPUs (Google Cloud blog)

The Google Cloud post "Save on GPUs: Smarter autoscaling for your GKE inferencing workloads": the choice of scaling signal for an inference HPA. GPU utilization is a poor metric because the GPU duty cycle does not track the load the server actually sees, while the server's queue size and batch size do — queue size for throughput, batch size for latency. Policy and vocabulary only; the post's thresholds and curves are not reproduced.

KEDA · event-driven autoscaling and scale-to-zero

Event-driven autoscaling as a second road to the HPA: KEDA scales a workload on the number of events waiting to be processed, works alongside the Horizontal Pod Autoscaler instead of replacing it, and scales down to zero. The course takes the vocabulary and pairs it with its own cold-start caveat.

vLLM production-stack · autoscaling with KEDA and KV-cache-aware routing

The production plumbing the course names but does not run: autoscaling driven by KEDA from Prometheus metrics with an HPA underneath, and a router that sends each request to the instance with the highest KV cache hit rate. Documentation

GKE · Overview of inference best practices on GKE

The overview's autoscaling rule in its own words: "KV cache utilization (for example, vllm:gpu_cache_usage_perc): this metric is often the best indicator of impending latency spikes." The HPA scales on metrics from the inference server rather than CPU or memory — KV cache utilization or the running batch for latency, queue size for throughput — and a minimum number of replicas is always set. Policy and vocabulary only; the metric names are the page's examples, not values the course measures.
