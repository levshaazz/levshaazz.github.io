PagedAttention & continuous batching

One Qwen ticket classifier: distinguish shared weights from request KV, account independent block tails, implement iteration refill and compare offline engine bursts without confusing speed with task quality.

One classifier and several unfinished requests

The application is the support-ticket router from Topic 04. “I forgot my password and cannot sign in to my account.” should go to access. “I can log in, but clicking Export crashes the application.” should go to bug. These are handwritten teaching cases, not a representative customer population. The gold label describes the desired answer; it does not establish what Qwen will predict. A useful serving change must preserve evidence about wrong answers rather than counting any completed string as a successful classification.

Suppose a short ticket arrives while another request has a longer context or continues generating. The weights are shared, but the requests have different histories, stopping conditions and arrival times. Three questions follow. Where does each request's computed history live? Which request can execute next? What measurement could support a claim that the complete service improved? Paged KV placement, iteration scheduling and comparative measurement answer those questions separately. None, by itself, improves the classifier's understanding of the ticket.

The required engineering actions are deliberately small: account for independently rounded KV capacity; select arrived requests for available decode slots; inspect a controlled pipeline/vLLM comparison. A driver, server launcher or timing utility is supplied infrastructure, not the student's primary intellectual work. The supplied GPU comparison passed technical rehearsal with instructor solutions; this chapter does not publish new speed results.

A local vocabulary for the investigation

Prefill is a forward computation over the rendered prompt positions. Decode consumes the latest selected ID to compute the next prediction. A forward is one evaluation of model operations, not necessarily one client request. EOS is a configured end-of-sequence ID that can stop generation before the cap. A backend is the implementation executing attention or the larger inference stack.

A pool is reserved reusable storage. A token budget limits scheduled positions in an iteration, not users or bytes. Preemption suspends some work when resources are needed elsewhere; recomputation rebuilds lost intermediate history from retained IDs. Topic 02 explains K/V and autoregression in more detail; Topic 04 explains the distinction between model output quality and service execution.

What the named model stores

The pinned Qwen2.5-0.5B-Instruct configuration has 24 decoder layers, hidden width 896, 14 query heads, 2 KV heads and head width 64. Grouped-query attention lets seven query heads use each KV head. The cache stores the keys and values, not fourteen independent copies just because fourteen query heads exist.

For one layer and one request, a logical key tensor has axes [KV head, retained position, head feature], with lengths [2, S, 64]. The value tensor has the same logical shape. “Position” is a place in the actual rendered model input or computed generation history; it is not a word, character, client or vocabulary index. During ordinary decode one new input position produces new K/V at each layer. These logical shapes do not specify whether a backend stores physical memory in head-major or position-major order.

The first generated ID is selected from the prompt's forward pass. That selected ID acquires its own KV only when a later forward consumes it. A stop token may never be consumed in another forward. Consequently prompt length plus output cap is a conservative planning quantity, not necessarily the exact live cache length at a chosen instant. Allocator lookahead and block rounding are additional implementation choices.

With FP16 keys and values, multiply two objects, 24 layers, 2 KV heads, 64 features and 2 bytes per element. The result is 12,288 bytes, or 12 KiB, per retained position across all layers. The first factor 2 counts K and V; the final factor 2 counts bytes per scalar. Confusing those factors makes later calculations hard to audit. Using fourteen query heads instead of two KV heads overcounts this payload by seven.

This is not the total memory of a running model. It excludes weights, temporary tensors, block tables, alignment, allocator reservations and any extra precision metadata. Changing the weight representation to four bits does not automatically change this FP16 KV formula. Model weights and per-request state are different objects.

A physical block is a storage unit

For the main arithmetic example, one block has sixteen position slots. Request lengths 17, 31 and 33 therefore need 2, 2 and 3 independent blocks. Total capacity is 7 × 16 = 112 positions for 81 live positions. There are 31 unused tail positions: 15 for the first request, 1 for the second and 15 for the third. At 12 KiB per position the live payload is 972 KiB, while ideal block capacity is 1,344 KiB. The difference, 372 KiB, is unused tail capacity under these assumptions, not a measured change in nvidia-smi.

Why not round the total 81 positions once? That would produce six blocks with 96 slots. It assumes that one request can fill another request's unfinished tail. That is a different ownership policy from the independent block tables in this example. The accounting function must round each independent request first, then sum. A zero-length request uses zero blocks in the toy. Empty input produces zero totals, not an exception or an invented placeholder page.

For simple growing full-attention sequences without sharing, at most one block per request is partly live. That observation explains why unused capacity is bounded in this model. It is not a statement that all serving memory is fragmentation-free. Metadata, reserved pools, prefix sharing, sliding-window attention, speculative lookahead and hybrid cache groups need their own accounting. A KV page is also not a CUDA thread block: one concerns stored positions, the other groups GPU execution threads.

How attention finds noncontiguous history

A request presents a logically ordered sequence, but its storage need not occupy one contiguous run of physical blocks. The block table maps each logical block index to a physical block in the pool. In the separate tiny diagram below, block size is four, not sixteen. A has six positions: logical block 0 maps to physical 3 and logical block 1 to physical 0. B has three positions in physical 2. Physical IDs are invented pool indices, not token IDs, device addresses or observations of a real allocation.

For logical position 5 and block size 4, integer division identifies logical block 1; the remainder identifies offset 1. A's table maps that block to physical 0, so the read uses offset 1 in physical 0 for A's corresponding K/V head and feature. The unused offsets must not become extra context. The live length and causal/mask policy determine which positions are legal. The physical memory layout within a block is backend dependent.

Finishing A can release its references while B continues. If a physical page has another live owner, it must not be overwritten. Prefix caching introduces an additional distinction: an unreferenced cached page may be evictable while still retaining useful bytes. An engine can keep the whole pool allocated and reuse free blocks internally. Logical release need not reduce device-level allocated memory. This is why a flat nvidia-smi curve cannot prove that completed requests were never released.

Paged storage cannot change the attention equation

Consider a deliberately tiny head with one feature. Query is 1; keys are 1, 2, 3, 4 and the paired values are 10, 20, 30, 40. All four keys are legal for this final query. The usual square-root head-width factor is 1 because the toy dimension is 1. Real Qwen heads have width 64 and retain positional and masking rules. The scalar helper applies a stable softmax by subtracting the maximum score before exponentiating.

The global weights are approximately 0.032059, 0.087144, 0.236883 and 0.643914. They sum to 1; their weighted value sum is 34.926527. Suppose the first two K/V pairs occupy one page and the last two another. Normalizing each page separately produces 17.310586 and 37.310586. Averaging those outputs gives 27.310586, not 34.926527.

The failure is the denominator. The correct attention gives pages different total probability mass according to all scores together; the wrong average gives each page half the mass regardless of its scores. Implementations may compute partial statistics and combine them stably without materializing the whole attention matrix, but their combined result must preserve global normalization. “The values are stored on separate pages” is not a license to define separate attentions.

Here is the missing merge step. Let a page's stable unnormalized mass be Zp=∑j∈peqkj−mZ_p=\sum_{j\in p}e^{qk_j-m}Zp​=∑j∈p​eqkj​−m, with the same global score maximum mmm. Its local output is ypy_pyp​. Then y=(Z1y1+Z2y2)/(Z1+Z2)y=(Z_1y_1+Z_2y_2)/(Z_1+Z_2)y=(Z1​y1​+Z2​y2​)/(Z1​+Z2​). For this example the normalized page masses are 0.119203 and 0.880797. The merge is 0.119203 × 17.310586 + 0.880797 × 37.310586 ≈ 34.926527. Equal masses 0.5/0.5 instead produce 27.310586. Real kernels may retain different local maxima and rescale partial statistics before merging; this shared-maximum toy explains the invariant, not their full algorithm.

There is a second useful counterexample. For this full-context final query, jointly permuting correctly paired keys and values leaves the sum unchanged. Merely drawing pages in a different order does not establish numerical damage. Reading B's page as A's history, breaking key/value pairing, or applying the wrong mask/position rule are genuine different errors. A teaching diagram must identify which error it actually demonstrates.

Change the block size without changing the population

Keep lengths 17, 31 and 33 and the same scalar dtype. Size 8 needs 12 blocks and 96 slots, with 15 unused positions. Size 16 needs 7 blocks and 112 slots, with 31 unused. Size 32 needs 4 blocks and 128 slots, with 47 unused. The logical payload remains 81 positions in every case. The interactive comparison changes one assumption while the print view retains all three alternatives.

Smaller blocks waste less tail capacity here, but require more table entries and may interact differently with kernel access patterns and supported backend layouts. This example does not establish an optimal real-engine block size. It also does not prove that every allocation with smaller blocks will have lower measured total GPU memory. A sound conclusion names the narrower quantity: “For these three independent lengths, the ideal unused tail capacity decreased.” Kernel speed, metadata and pool reservation remain unmeasured.

The batch can outlive its short member

Now hold memory placement aside and examine scheduling. Two decode slots are available. A, B and C arrive at tick 0 with 5, 1 and 1 decode steps. D arrives at tick 2 with 2 steps. Each active request executes one step during [t,t+1), and any completion releases its slot at t+1. Prefill costs zero only in this toy; no memory gate or preemption exists. The given lengths generate stopping events, not a promise that a real scheduler knows future output length.

Static mode admits one cohort, A and B, and does not refill until that cohort empties. B completes at 1, while A continues through 5. C remains queued despite the empty second slot. At 5, C and D enter the next cohort; C completes at 6 and D at 7. A request-level batch can finish its short member early without admitting a new member. That distinction is lost when “static batching” is described as if every member completed simultaneously.

Continuous mode evaluates membership at each iteration boundary. After B finishes, C enters at 1 and finishes at 2. D is then eligible by arrival time and enters at 2; it finishes at 4. A still finishes at 5. Independent requests share work; A's five dependent decode steps are not predicted simultaneously. Continuous batching changes membership, not autoregression.

Read the trace without inventing milliseconds

The completion ticks for A/B/C/D are 5/1/6/7 in static mode and 5/1/2/4 in continuous mode. Residence time subtracts arrival. D's static residence is 7 − 2 = 5, not 7; its continuous residence is 4 − 2 = 2. Averaging all four requests gives 4.25 versus 2.5 ticks. Makespan is 7 versus 5 ticks. Idle slot-ticks are 5 versus 1: two slots times total elapsed ticks, minus the same 9 useful request steps. None of these numbers is a measured GPU metric.

Completion here means the end of the request's invented decode work, not the arrival of a client-visible response from the pipeline API.

The unit-time assumption does essential work. Actual iteration duration depends on active tensor shapes, prompt/decode work, memory traffic, kernels and framework overhead. A hypothetical continuous iteration cost twice as high would make 5 × 2 exceed 7 × 1. That counterexample is not an observed vLLM slowdown; it demonstrates why the shortest logical trace alone cannot establish a wall-time improvement. Nor are active slots equal to measured GPU SM utilization.

A useful prediction is consequently conditional: replacing empty cohort slots can admit work earlier, but the resulting task completion and cost must be measured under a specified workload. The lab asks for that prediction before the observation. It does not force the student to declare that vLLM must win.

Where the real V1 scheduler differs

The pinned 0.30.0 tuning guide describes chunked prefill and a scheduled-token budget. A sequence limit, client concurrency, token budget and KV capacity constrain different objects. For simple arithmetic, three ordinary decode positions consume 3 of a 256-token budget, leaving 253 for a 300-position prefill. This is an explanatory budget example, not a logged execution of the current scheduler.

Inspect the actual scheduler source and KV manager when interpreting behavior. Already-running work, chunk eligibility, capacity and recomputation make the decode-only model incomplete. A waiting request can be blocked by one limit even if another resource appears available. Increasing a sequence limit is not equivalent to increasing the token budget or allocating more KV capacity.

The Paged Attention design page explicitly labels its kernel description historical. It is valuable for learning the original mechanism, not a claim that every current attention backend executes that exact kernel. Likewise the original paper's speed ratios belong to its evaluated systems and workloads, not a guaranteed multiplier for this notebook. A versioned explanation preserves that boundary.

What a controlled pipeline/vLLM measurement can prove

The moderate-load comparison keeps the pinned model revision, dtype, rendered token IDs, case population, stopping/cap policy and warmup fixed. The student changes the submitted offline burst cohort from 1 to 4, not HTTP client concurrency. Prefix caching is explicitly disabled in the control rather than silently rewarding repeated common input. Request strings alone do not prove equal inputs: chat templates, special tokens and tokenization must be checked. Greedy decoding also does not guarantee identical outputs across numerical implementations.

Greedy is not a complete generation profile. The pinned Qwen generation configuration includes repetition penalty 1.1. This notebook explicitly sets it to 1.0 in both engines; otherwise pipeline inheritance could create a different logit transformation from vLLM. Natural stopping uses the configured EOS IDs, and native returned tensors are preserved separately from the selected completion IDs. Matched settings reduce confounders but do not promise bitwise-equivalent kernels or identical literal labels.

This offline workload submits at most four tickets per call with a fixed sequence limit 4. A subsequent burst begins after the previous call finishes. There is no fifth queued request to enter a newly released slot inside a call. Thus the measured experiment does not empirically establish the continuous-refill event in the A/B/C/D toy. Refill is the mechanism exercise; this experiment checks the complete stacks on a bounded burst population.

A pipeline/vLLM comparison changes a complete stack, including kernels, packing, framework overhead, cache policy and scheduling. It can support a bounded system comparison for the declared workload. It cannot isolate the causal contribution of PagedAttention. A mechanism ablation would require a supported controlled change inside an otherwise fixed implementation. Do not describe an end-to-end speed ratio as if every changed component had been identified.

Clock boundaries must be equally explicit. Cohort throughput is completed requests divided by the elapsed cohort interval. Individual end-to-end latency requires individual request arrival/completion clocks. A final non-streaming response does not expose first-content arrival and cannot supply TTFT. Output-ID rates need a declared treatment of stop IDs and generated work. Differences in actual output length are data to inspect, not something to erase after seeing timings.

Count every attempted request when evaluating task quality. Failure, incomplete output, invalid label and valid-but-wrong label are distinct outcomes. A fast stack that drops hard requests has not automatically become better. Three repeats give raw spread and a limited comparison, not a stable p95. High-concurrency overload and open-loop traffic belong to Topic 06; this topic first establishes a usable moderate-load protocol.

The supplied reducer retains twelve rows: two engines×two sizes×three repetitions. Each row processes the same twelve tickets and reports 12/∑cTc12/\sum_c T_c12/∑c​Tc​ attempted predictions per synchronized library second, where TcT_cTc​ is one cohort wall interval in seconds. It is not the average reciprocal of individual request latency. A separate quality matrix includes an invalid-label column; literal engine disagreements are not silently repaired.

Before installation, the student writes a rate prediction, a quality expectation, a concrete classroom acceptance/refusal rule based on correct/12, invalid/12 and the pipeline control, and a falsifier. Save the notebook before inference and do not rewrite the prediction after seeing results. This is a methodological requirement: the notebook does not automatically lock the prediction variable. After measurements, the engineering note must state a choice or refusal, actual rates and quality counts, an alternative stack explanation, and the next untested requirement. A fast but inaccurate twelve-ticket smoke test does not support production deployment. An incomplete engine attempt has no fabricated complete throughput row.

Worked checks and limits

  1. Why does 17 need two blocks at size 16? The seventeenth retained position cannot fit the first sixteen slots; independent ownership requires another block.
  2. Does a smaller block reduce live KV payload? Not for unchanged model, dtype and 81 positions. It changes tail capacity and table granularity.
  3. Why is D's static residence 5, not 7? Its arrival is tick 2; completion is 7. The interval belonging to D begins at 2.
  4. Can a complete request have the wrong class? Yes. Transport completion, valid-label format and correct meaning need separate checks.
  5. Does continuous batching prove lower wall time? The toy proves earlier admissions under equal iteration cost. The real costs and quality require a fresh controlled run.
  6. Does a flat device-memory curve prove no release? No. A pool can retain allocation while internal live ownership decreases.

The central decision is not “PagedAttention good” or “vLLM fast”. It is whether a particular controlled intervention improved the declared system outcome, under documented conditions, without hiding quality failures or replacing measurement with a drawing.
