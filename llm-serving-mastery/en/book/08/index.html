Production inference APIs: FastAPI + vLLM

One thin FastAPI gateway in front of the frozen engine: request validation with hard caps, request identity, bounded-queue admission with honest 429s, client-disconnect cancellation, an error map that never returns 200-with-error-body, one structured output, and /metrics counters — the whole contract exercisable on free CPU against a declared mock engine.

From a Python profile to a public promise

Topic 07 left you with a frozen production profile: --max-num-seqs 32, a saturation curve, a tail, a rollback plan. It is a good profile. It is also an internal component — a stranger with an HTTP client cannot import it, cannot call it, and does not care that it exists. The moment your engine accepts work from someone else's code, a new kind of question appears: what stands between a request you did not write and a profile you froze?

The answer is one thin gateway, and this chapter builds it in front of the pinned engine. The engineering virtues are the course virtues in a new uniform. Predict before you build: the contract prediction table is frozen before any gateway code runs. A working artifact early: by the fifth executable cell a real HTTP round trip answers, on a mock engine whose knobs are declared on their face. Errors are data: two failure drills fire on demand and leave journal proof. And a frozen promise beats a post-hoc story: the gateway's SLO and rejection policy are written down before the waves arrive to test them.

The course motif for the topic is the pass — order, receipt, serving window. A request enters, gets a name, is either being cooked or honestly refused, and every stage of that journey leaves a receipt you can read later. HTTP 200 is not success; it is only an answer that was sent. A cancelled generation still costs tokens. An unbounded queue is not capacity — it is latency hidden from the pager. Each of these sentences becomes a mechanism you build, drill, and journal in this chapter.

The profile behind the door

Nothing in this chapter re-opens the Topic 07 decision. The engine behind the gateway runs the frozen profile, and the gateway treats the engine as an opaque queue: it does not tune knobs, it does not inspect batches, it admits, forwards, and maps outcomes. This division of labor is deliberate. Tuning is a laboratory activity with a frozen workload; serving is a contract with strangers. Mixing them is how teams end up re-deriving the saturation knee in production traffic at 3 a.m.

The pass also inherits the course taxonomy. Validation at the door is the planning discipline from Topic 06 — reject what you cannot serve before it occupies capacity. Admission control is the bounded queue from the saturation lab. A client disconnect is the preemption story: abandoned work must stop consuming. Honest errors are the terminal-outcome taxonomy wearing status codes. You have built each mechanism once already; the gateway is where they learn to speak HTTP.

One boundary is declared up front. The core lab runs on free CPU against a MockEngine — an async in-process worker with declared latency knobs (0.15 s to the first token, 0.02 s per token, a concurrency ceiling mirroring the frozen profile). Its numbers are synthetic by construction, and every figure that carries them says so. A live vLLM behind the same gateway is an owner-run demonstration with retained evidence, never a student requirement, and no mock number is ever quoted as an engine measurement.

One pass, four decisions

The gateway is small enough to draw and should be. A request arrives; the gateway mints an id; validation checks the public caps; admission decides between a service slot, a bounded wait, and a refusal; the engine generates; the error map turns whatever happened into one honest code; the journal keeps the receipt. Five stages, four decisions that a human designed.

The map is the review artifact of the topic. Any proposed gateway change — a new header, a retry policy, a queue resize — must name the stage it touches and the decision it changes. A change that cannot name its stage is decoration, and decoration in front of a GPU budget is how incidents are born. The figure also carries the second half of the contract: the request id travels the whole pass and reappears in all four records a human may read at night — the reply header, the engine journal, the error body, the metrics.

The contract: caps at the door

The request schema is a promise with named ceilings: a required prompt of at most 512 characters, a max_tokens between 1 and 64, an optional schema for structured replies. The ceilings are public — documented, versioned, and quoted in every refusal. This is not bureaucracy. A client that knows the ceiling can fix its own request without burning a round trip; a client that discovers the ceiling by experiment is paying for your documentation in GPU time.

Validation at the door is admission control performed before the queue. A malformed or oversized request must not consume even a waiting slot, because the slot it would consume is capacity that an admissible request — one the gateway could actually serve on time — now cannot. The lab's first student function is the frozen contract prediction, and the gate itself — admission — is its first coded mechanism; the frozen prediction table asks for the refusal code of each probe before any of it runs.

The same block introduces /health: liveness plus in-flight count, read by probes, by the daemon, and by the on-call. There is no private health route and no hidden truth. A service whose health endpoint lies is a service whose pager lies, one incident later.

The id that travels

Every request gets an id at the door — before validation, before admission, before anything can go wrong. The id then appears in four places: the reply header the client correlates, the engine journal that proves what the generation did, the body of every error, and the metrics snapshot. Four places is not generosity; it is the minimum set that makes the other promises checkable.

Without the journal id, a cancellation claim is unprovable — you cannot show the generation stopped. Without the id in error bodies, a 3 a.m. failure is a stack trace with no request attached. Without ids in metrics, waste and refusal patterns cannot be attributed to clients at all. Identity is what converts logs into evidence, and evidence is the currency every later section pays in.

The queue economy

An unbounded queue is latency you promised to nobody. Every arrival is accepted, depth grows without a declared ceiling, and the delay is paid by clients who never consented to wait — invisible to capacity planning until client-side timeouts fire all at once. The bounded queue replaces the silent wait with three named outcomes: a service slot, a bounded seat, or an honest refusal.

Refusal is an answer

429 with Retry-After is the most misunderstood success in the API world. To the client it is a decision with a declared pause and its request id attached — the retry becomes computable instead of hopeful. To the operator it is a designed signal: a rising rejected counter says the offered load crossed the declared knee, which is exactly what capacity planning needs to know and exactly what an endless queue conceals.

The discipline extends to the client's side. The correct response to 429 is to wait the declared pause and retry the same logical request with the same id, backing off exponentially if refusals repeat. Immediate retries turn one refused request into a storm of refused attempts; the rejected counter climbs, and the gateway can see the storm only because refusals are counted. An unbounded queue hides the same storm as latency.

A leaving client stops paying

A closed socket is a decision by the client, and the gateway must honor it: stop the generation, journal the outcome as cancelled, and count the tokens that were produced for a reader who no longer exists. This is the Topic 06 preemption story in HTTP clothing — abandoned work must stop consuming — and it is the last, freest student function in the lab: a disconnect watcher specified by contract alone.

Streaming: the same mechanism, one frame later

Server-sent events deliver text while the engine decodes, and they change nothing about the pass. Admission, deadline, error map and identity hold frame by frame: a streamed response is still one request with one id and one journal row. What streaming tempts teams into is bypassing the queue — frames feel free, so admission feels optional. It is not. A frame delivered past the declared deadline is a promise broken in slow motion.

Mid-stream cancellation is the Episode 5 mechanism one frame later. A client gone at frame k triggers the same watcher, the same journal entry, the same waste count. No new machinery should be invented for streaming, and if your design grows one, that is a signal the pass was never really in charge.

Honest errors: the outcome map

Every terminal outcome maps to exactly one code with one next action. Invalid requests get 400, because the caps are public and the fix is known. Overload gets 429 withRetry-After, because the refusal is temporary and computable. An engine with no healthy worker gets 503, and the owner gets paged. A deadline gets 504 with the request id, because the client is owed both the verdict and the evidence. Everything else gets 500 without internal details — the client does not need your stack trace, and your stack trace does not belong on the wire.

The map is the terminal-outcome taxonomy of Topic 06 wearing status codes. The lab triggers two of the modes on demand — an invalid request and a flagged-down engine — and checks the observed status against the student's own map, with the journal as proof. Two drills cover the named modes, not the whole fault catalogue; the limitation is stated in the notebook and repeated here.

The negative rule does the heavy lifting: never 200-with-error-body. A 200 envelope around a failure passes shallow health checks, poisons the client's success path, and corrupts its retry logic silently. The status code is the first truth a client reads; the body explains what the code already decided. Teams that blur this split do not save work — they move the failure into someone else's monitoring, where it costs more to find.

Structured outputs: schema in, validated JSON out

Guided completion rides in the same contract: the request may carry a response schema, the engine constrains decoding toward it, and the gateway validates the reply against the same schema before answering. The validator is deliberately yours to write — a small checker for named fields, types and enums — because the validation failure is part of the product: a visible 422 with the exact violation path.

The drill's fixture breaks the schema on purpose: an enum value outside the declared set, a number shipped as a string. The honest answers are paths — $.priority,$.score — not a silent cast. Coercion would be a double lie: the gateway would claim a reply matches the contract the client programs against, and it would hide a model behavior problem the product team needs to see. The violation path is how a contract stays true under a model that occasionally improvises.

Counters you planned

Five numbers run the gateway: accepted, rejected, cancelled, in-flight, and waste tokens. Each exists because a named decision needs it — capacity against arrival, backpressure health, abandonment accounting, live saturation, the price of leaving clients. The course rule is blunt: a metric you did not plan is a metric you will fake. So the metrics block plans the counters in the same block that plans the contract, and the snapshot is frozen into the journal with a feeds column: which decision each number informs.

The honest zero is part of the design. At snapshot time the cancelled counter reads zero — cancellations arrive only after the cancellation block runs. A zero with a known reason is data; a number decorated to look busy is noise. When you read any gateway dashboard, ask which zeros are explained and which are painted over.

Loading the pass

The Topic 06 closed-loop wave driver now knocks on the student's own gateway over real HTTP. Two waves — 8 and 24 clients — with every fourth client disconnecting mid-generation. The point is not the throughput number; it is reading your own admission decisions out of the journal: served, refused, cancelled shares per wave, compared against the Block-0 envelope that was frozen before any of it ran.

In the declared mock run the shape lands exactly where the arithmetic said: wave 24 shows roughly two thirds refused at the knee, cancellations only where the watcher runs, and the rest served. The table says mock on its face, and the exact percentages live in the run journal. When the wave table disagrees with the envelope, the follow-up is a named mechanism — a slow client start, a queue promotion race — not a silent re-roll. That is the same reading discipline as every freeze in this course.

Freeze the API contract

The chapter closes the way Topics 06 and 07 closed: with a frozen promise. The gateway SLO card declares the tail the gateway promises inside itself, the error budget, the rejection policy — who gets 429, with what pause, at which pool size — and the cancellation accounting. The memo is one paragraph a product owner and an on-call engineer can both read in thirty seconds, and both must be willing to sign.

The refusal clause is part of the promise, not an apology appended to it. A client reading the contract knows that refusals carry Retry-After and the request id, that cancellations are journaled with waste, and that no failure will ever arrive dressed as success. The deliverable is the signature discipline: named clauses, named owners, and a declared bridge — Topic 09 ships this gateway as an immutable image so the contract survives machine drift.

What the mock does and does not establish

The MockEngine is a declared synthetic worker: its latency knobs are written in the notebook, quoted on every figure, and never compared to vLLM. It exists so the whole gateway contract — validation, admission, refusal, cancellation, error mapping, structured outputs, waves — is exercisable in minutes on a free CPU. What it validates is the pipeline and the reading discipline, not engine magnitudes.

The limitations are stated, not hidden. Disconnect detection on the mock is best-case; real networks are noisier and detection latency varies. Two failure drills cover the named modes, not an exhaustive fault catalogue. The gateway is a single instance — horizontal scaling is a later topic. And the live vLLM behind this gateway is an owner-run demonstration with retained evidence; its numbers enter course materials only with that provenance.

Worked example: sizing the pass from Little's law

The queue is not a guess; it is arithmetic you can defend line by line. The mock engine behind the lab declares a time-in-system of W = 0.47 s for a completion at the frozen seqs-32 profile — that number is written in the notebook, not measured. Little's law from Topic 06 says the queue depth L equals the arrival rate λ times W. The gateway runs four engine slots plus a four-deep waiting row: eight requests can be inside the pass at once, so the queue is full exactly when L reaches 8, which happens at λ = 8 / 0.47 ≈ 17.0 requests per second. That is the 429 knee: below it, refusals are a bug; above it, refusals are the design working.

The overload drill checks that this envelope is real. Twenty-four closed-loop clients arrive against eight slots; the journal shows exactly 8 completed and 16 rejected with 429 plus Retry-After — the arithmetic and the wire behavior agree. A junior engineer reads the 16 refusals as an outage. You should read them as the pass refusing orders it cannot cook on time, each refusal carrying the request id and a bounded wait suggestion. The alternative — admitting all twenty-four — would have hidden the same failure inside a two-second queue with no honest signal at all.

This is also why the mean lies. Average latency across the drill looks acceptable even while one request in three is refused, because the refused ones return instantly and drag the average down. The Topic 06 lesson — the tail speaks before the mean — becomes an API design rule here: the SLO is written per outcome class (completed p95, refusal share, cancellation waste), never as one blended average.

The illustrative tails figure above is the shape students already know from Topic 06: near capacity the mean barely moves while p95 explodes. The gateway turns that curve into a decision made at the door, in milliseconds, per request — which is the only place a decision can actually be made.

The curve behind the SLO

The gateway inherits its engine from Topic 07: the frozen seqs-32 profile that won the bounded search. It is worth remembering what that profile sits on. The measured T4 run of Topic 06 pushed the pinned 3B model through 29 → 208 → 306 → 311 tok/s across waves of 8/32/64/128 clients with zero timeouts; the gain rule put the knee at wave 32 in the anchor run, and the replicate flipped it back to 64 — the 32→64 doubling sat exactly on the fifty-percent bar. Three runs, one finding: quote the threshold and the run count.

The gateway does not change that curve — it stands in front of it. Validation decides who reaches the curve; admission decides how many ride it at once; the error map tells the client which part of the curve refused them. When the SLO memo says "p95 inside 2 s at up to 17 req/s", the number is defensible because the curve behind it has been measured, published with its limits, and argued about in the open.

And the profile itself was not the first fast option — it was the only SLO-eligible point on the Pareto front. The search table behind it is frozen, hashed, and inspectable. A contract is defensible when every layer under it — curve, front, freeze — is defensible in the same way.

The drills, line by line

Read the overload journal one row at a time. Rows r5 through r8: status 200, outcome completed — the four engine slots, each inside the declared 0.47 s. Row r18 arrives when all eight positions are taken: status 429, outcome rejected, Retry-After: 1. Rows r11, r13 and the rest interleave completions and refusals as slots free up — the pattern of a working admission policy, not of a overloaded machine. The one thing that must never appear in this journal is a 200 carrying an error body: that row would mean the pass cooked nothing but told the client dinner was served.

The cancellation drill is two runs of the same leaving client. Without the disconnect watcher, the orphan probe shows the generation running to its full sixty-four tokens — one client, one request at its 64-token cap: sixty-four token-slots of compute spent on a response nobody will read. With the watcher, the journal shows outcome cancelled and a wasted-token count of eight — the tokens between the disconnect and the cancel taking effect. The lesson is arithmetic, not morality: the watcher pays for itself the moment leaving clients outnumber patient ones.

The error drills each trip one clause of the map. An overlong body (a 600-character prompt against the declared cap) is refused at the door with 400 before it reaches the queue — validation is admission control. A stopped engine produces 503 with the request id, so the on-call can find the exact failed request in the journal. Both drills are triggered on demand in the lab; both prove the map, not the exception handler that happened to be written first.

One request, end to end, twice

Happy path. A client posts a completion with a prompt and max_tokens. The schema layer checks the caps — prompt within the declared limit, output cap at most 64 — and rejects anything else with 400 before a slot is touched. The request receives its id at the door; the id is stamped into the journal, the log line, and eventually the response header. The admission queue has a free slot, so the request is admitted immediately. The engine streams tokens; the gateway forwards them; the final frame carries usage. Total gateway time inside the declared envelope; one journal row; counters move by one.

Overload path. Same request, but all eight positions are already held. The queue is full, so admission refuses with 429, Retry-After: 1, and the request id — in that order, because the id is what makes the refusal auditable. The client retries after the pause or backs off; the gateway has spent no engine time on a request it could not serve. Compare the two paths and the design statement of the whole topic appears: the only difference is one decision at the door, made honestly, with evidence either way.

Run both paths through the wave driver and the shares land inside the frozen envelope: 75/0/25 percent completed/rejected/cancelled at wave 8; at wave 24 roughly a third completed and two-thirds refused, with the cancelled share jittering between runs. The envelope, not the individual numbers, is the contract — single-run jitter is expected, and the memo says so explicitly.

What each lab block proves — and what it deliberately does not

The lab is sequenced so that every block owns exactly one claim, and every claim has a falsifiable artifact. Block 0 owns the prediction: the contract table and the queue arithmetic are frozen into api-contract.json before any gateway code runs, which is what makes the later drill results comparisons rather than vibes. If the overload drill had come first, the envelope would have been fitted to whatever happened; written down first, it can lose — and a prediction that can lose is the only kind worth making.

Block 1 owns the build. The first working artifact arrives early: a bare pass-through gateway answering /health and one completion over real HTTP, long before validation, queues or error maps exist. That ordering is deliberate — students debug a known-simple system first, then add mechanisms one at a time, each behind a named function. By the time the admission queue lands, the difference between "the engine is slow" and "the queue made it look slow" is something they have already seen from both sides.

Block 2 owns the breaks. The disconnect drill, the overload drill and the two error drills are not demonstrations; they are attempts to falsify the Block 0 claims. Each drill ends with a journal comparison against the frozen envelope, and each has one deliberately wrong predecessor — the orphan probe runs without the watcher precisely so students can measure what the watcher saves. Errors as data is the course-wide rule; here it wears status codes.

Block 3 owns the measurement discipline: the same wave driver students met in Topic 06, now pointed at their own HTTP surface, with the journal classified into completed/rejected/cancelled shares per wave. The comparison against the envelope — not against a feeling — is the deliverable. The stretch block adds /metrics and the memo, and the memo is graded for named clauses, not for optimism: what the gateway promises, what it refuses, and what it will never dress up as success.

What the blocks deliberately do not prove: engine performance (the mock's timing knobs are declared, not measured), multi-instance behavior (one gateway process throughout), and security beyond identity (no authentication surface in scope). Saying what a lab does not establish is part of establishing anything at all — the same honesty rule the saturation curve, the Pareto front and the frozen profile were held to.

Reading the counters like the on-call engineer

The /metrics snapshot is short on purpose: accepted, rejected-429, cancelled, in-flight, and latency buckets. Each counter answers one operational question. Accepted counts the pass actually cooking; rejected-429 counts the door working; cancelled counts clients that left mid-order; in-flight is the live occupancy of the eight positions; the latency buckets show where completed requests land relative to the declared 0.47 s per-token envelope. A counter that answers no question is decoration, and decoration drifts out of truth silently.

Three readings from the snapshot deserve rehearsal. If rejected-429 climbs while in-flight stays at eight, the arrival rate crossed the 17 req/s knee — the system is healthy, the demand is past capacity, and the honest answers are scale up or say no faster. If cancelled climbs while accepted stays flat, clients are giving up before the first token — look at time-to-first-admission, not at generation speed. If in-flight sits below eight while rejected-429 climbs, something is leaking slots — an admission that never released is the gateway's own bug, and the journal's request ids are how you find it. None of these readings require engine expertise; all of them require the counters to exist. That is why observability is designed before the incident, in the same block as the contract, and why the stretch memo ends the topic by defending the SLO the counters are measured against.

Streaming, cancelation and the last frame

Streaming changes when the client learns things, not what the contract means. The server-sent-event frames forward tokens as the engine earns them, so perceived latency drops to the first token rather than the last. But the frames also move the cancellation problem one frame later: a client that closes the connection mid-stream is the same leaving customer as the one who vanished before the first token, and the same watcher must catch both. The lab proves the symmetry — the mid-stream cancel lands in the journal as cancelled with its waste counted, exactly like the pre-stream one, and the frame stream terminates with an honest terminal event instead of silence.

The last frame carries more than text. Usage — prompt tokens, output tokens, the request id — lets the client reconcile its own accounting against the journal, which is how billing disputes and bug reports become lookups instead of arguments. And because the frames are the contract's surface too, a structured-output request validates the assembled object before the terminal frame: a schema violation arrives as a visible error with the violation path, never as a confident wrong answer with status 200. The rule from the error map survives streaming unchanged: every terminal state the client can observe is either the promised payload or an honest refusal — nothing in between.

  3. Answer the 429 correctly. A client receives 429 with Retry-After: 1 and its request id in the body. Describe the correct client behavior, and contrast it with what the same client would experience behind an unbounded queue at the same load.
  4. Count the cancellation waste. With the declared mock knobs (0.15 s before the first token, 0.02 s per token, a 64-token request), a client disconnects at t = 0.50 s. Compute the wasted tokens with a working disconnect watcher and without one. What does each number mean on the books?
  5. A deadline is a promise to the client. A request waits in the gateway queue past its 12-second budget just as the engine frees up. The gateway could let it through and answer correctly 13 seconds after arrival. What does an honest gateway do instead, and what exactly does the client receive?
  6. Where the id must live. Name the four places the request id must appear, and explain what specifically becomes impossible when one of them is missing.
  7. Which counter moves first. The pool is full and a client with aggressive retry logic starts resending immediately on every 429. Which gateway counter moves first, what does the Retry-After header prevent, and what would a missing rejected counter hide?
  8. Read the violation path. The advertised schema requires label (string), priority (one of low, high) and score (number). A guided reply comes back as {"label": "payment", "priority": "urgent", "score": "0.9"}. Which violation paths fire, and why must the gateway answer 422 rather than silently coerce and answer 200?
Reveal eight answers and their limits
  1. Predict the code before the queue. 400 at the validation stage, before the request touches the queue. The cap is public and the request is well-formed JSON, so this is a semantic refusal, not a transport fault. A 200-with-error-body would be counted as success by every shallow health check and by the client’s own retry logic — the failure becomes invisible exactly when someone needs to count it. The status code is the first truth a client reads; the body only explains what the code already decided.
  2. Where does the knee land. Little’s law: L = λW = 12 × 0.47 ≈ 5.6 requests in flight on average. That is below the total of 8 positions (4 slots + 4 seats), so refusals have not begun yet — but on average more than the four service slots are occupied, which means the waiting line is regularly in use and queue waits appear. Refusals begin where L crosses 8: λ = 8 ÷ 0.47 ≈ 17.0 req/s. Past that knee, every extra arrival is refused with 429 instead of buying invisible latency.
  3. Answer the 429 correctly. The client treats 429 as a decision, not an accident: wait at least the declared second, then retry the SAME logical request with the SAME id, backing off exponentially if refusals repeat. Behind an unbounded queue the same client would have been admitted and simply waited — minutes of silent latency, no refusal to learn from, no signal to the operator, and a timeout eventually fired by the client rather than an honest answer from the gateway. The bounded queue turns a hidden wait into a computable decision; that is why 429 with Retry-After is an answer, not an apology.
  4. Count the cancellation waste. With the watcher: cancellation lands shortly after 0.50 s, and the waste is (0.50 − 0.15) ÷ 0.02 ≈ 17–18 tokens — what the engine produced after the first-token delay for a reader who was already gone. Without the watcher: the engine runs to completion and burns all 64 tokens for nobody, while the journal optimistically records a completed request. The difference is not cosmetic: waste is the price of leaving clients, and a service that does not count it will never know what cancellations actually cost.
  5. A deadline is a promise to the client. It returns 504 with the request id: the deadline was part of the contract, and a correct answer at 13 seconds is a breach wearing a 200. The client receives the timeout code plus the id, so it can decide to retry with evidence in hand. Letting the request through anyway would also poison the capacity signal — the gateway would look healthier than it is while clients experience promises being broken politely.
  6. Where the id must live. Reply header (the client correlates attempts), engine journal (the generation can be found and audited), error body (a refusal carries its own explanation key), and the metrics snapshot (counters can be drilled down by id class). Missing the journal id, a cancellation claim cannot be proven — you cannot show the generation stopped. Missing the error id, a 3 a.m. page has no anchor: the on-call sees a failure with no request to inspect. Missing the metrics id-class, waste and refusal patterns cannot be attributed to clients. Identity is what turns logs into evidence.
  7. Which counter moves first. The rejected counter climbs first — each immediate retry is refused again and counted again. Retry-After exists to break exactly this loop: it spaces the retries so backpressure throttles the client instead of the client amplifying the overload. Without the rejected counter, the gateway would show a modest accepted count and a mysterious latency tail, while the true offered load — originals plus retries — stays invisible; the operator would tune capacity against a number that hides the storm it is suffering.
  8. Read the violation path. Two violations: $.priority — "urgent" is outside the enum; and $.score — "0.9" is a string where a number is required. Both paths are reported in the 422 body together with the request id. Silently coercing would mean the gateway lied twice: it claimed the reply matched the schema the client will program against, and it hid a model behavior problem (enum drift, type drift) that the product team needs to see. The violation path is not bureaucracy — it is the difference between a contract and a rumor.
