Model quantization for production

Number formats, group metadata, calibration, real kernel support, memory budgets, paired quality and phase-specific speed.

The decision before the bit width

Imagine the owner of a single-GPU API says, “The model barely fits; switch to four bits and we will serve twice as many users.” That proposal contains at least four separate claims. The weight payload might shrink. The full process reservation might or might not shrink. The actual kernel path might be faster or slower at the intended batch shape. And the output might still satisfy the product's exact-format and semantic quality rules. A useful quantization experiment must test all four without moving the workload or changing the success denominator after seeing results. The Topic 03 instructor run offers a deliberately small counterexample: on one RTX 5070 Ti and pinned 0.5B model, FP16 and bitsandbytes NF4 both ran, but lower-bit weights did not make the tested path faster or reduce reserved memory.

This is not a failure of quantization as a field. It is a reminder that “four bits” names a storage representation, while a deployed request experiences a chain of packing, dequantization or quantized kernels, temporary tensors, KV, scheduling and output checks. A format that is excellent for a larger matrix or a different batch can be poor for a tiny batch-one model. We will keep the decision conditional rather than promoting one small smoke test into a general leaderboard.

What gets smaller?

A scalar integer quantizer maps a value to a code and a reconstruction rule, often with a scale shared by a group of values. The code may clip outliers; the scale and zero point (where applicable) also occupy memory. For an illustrative 3-billion-parameter model, four data bits per parameter are 1.5 billion bytes before metadata. If one FP16 scale serves each group of 128 parameters, scales add approximately 3,000,000,000 / 128 × 2 = 46.875 MB. That is neither the full model file nor live GPU memory: embeddings, non-quantized modules, allocator state, activations, and KV cache remain.

Likewise, W4A16, W8A8, FP8, NF4, and quantized KV are not interchangeable names. They change different tensors and may require different kernels or devices. AWQ uses activation awareness to protect salient weight channels; GPTQ uses approximate second-order information to compensate weight quantization. Neither name describes the bitsandbytes NF4 path in this course’s small paired lab. Check the vLLM quantization support documentation against the installed release and actual GPU before making a kernel-speed claim.

Worked scalar example: clipping is a quality decision

For an illustrative symmetric signed four-bit quantizer, choose representable integer codes from −7 to +7 and a scale s = 0.2. Reconstruct with q × s, and map an input value by rounding x/s then clipping to the code range. A weight x = 0.86 maps to round(4.3) = 4 and reconstructs as 0.8, error −0.06. A weight x = 1.8 wants code 9 but clips to 7 and reconstructs as 1.4, error −0.4. These are invented weights, not observed Qwen weights. The example isolates why outliers and scale choice matter: the same bit width can have different error profiles.

Grouping weights gives each group its own scale, often reducing error at the cost of metadata and implementation complexity. If one FP16 scale serves 128 weights, the scale term is two bytes per 128 weights, or 2/128 = 0.015625 byte per weight in the idealized representation. Four data bits are 0.5 byte per weight. Adding these two terms gives 0.515625 byte per weight before zeros, packing alignment, exceptions or non-quantized layers. Multiplying by three billion gives about 1.547 billion bytes, not exactly 1.5 billion. Even this improved arithmetic is not a file-size promise; metadata layouts and tensor exclusions vary by format.

A format is a path through kernels, not a suffix

W4A16 usually signals four-bit weight storage with higher-precision activations. W8A8 changes both weight and activation representations. FP8 uses a different floating-point trade-off, and quantized KV targets state retained across tokens rather than only parameters. NF4 is a nonuniform four-bit type used in the bitsandbytes path of this exercise. Those labels are not enough to know whether a GPU has a native fast kernel, whether weights are dequantized into a temporary buffer, or whether a serving engine falls back to a slower implementation. A format compatibility table is release- and hardware-sensitive, so verify the installed version and log the selected kernel path before crediting “quantization” for a speed result.

The methods also protect error differently. AWQ uses activation statistics to identify salient channels and scale them; GPTQ uses approximate second-order information when quantizing weights. These are not interchangeable knobs. Their papers motivate candidate designs, but they do not predict this 0.5B NF4 lab or guarantee a quality score on the student's API tasks. The correct provenance record names the model revision, exact quantization method, calibration set when applicable, runtime/engine release, device and selected kernels—not just “4-bit.”

The paired instructor run

The RTX 5070 Ti rehearsal loaded the same pinned Qwen2.5-0.5B-Instruct revision and tokenizer in FP16 and bitsandbytes NF4. It preserved four natural-EOS quality prompts and 12 fixed-24-token timing trials per format. Peak allocated memory fell from 1.174 GiB to 0.618 GiB. Peak reserved memory did not fall: 1.189 GiB for FP16 and 1.221 GiB for NF4. A statement about compressed parameter payload cannot be substituted for a statement about full process reservation. The run record includes versions, prompts, outputs, and raw timing trials.

Across those four prompts, nearest-rank per-prompt p95 fixed-length wall times ranged 0.54–0.81 seconds for FP16 and 1.05–1.28 seconds for NF4. There were only three trials per prompt, so that p95 is effectively a maximum, not a stable tail-latency estimate. The safe conclusion is narrow: this NF4 path was slower in this small, single-host smoke. It does not prove NF4 is slower on larger models, other kernels, batches, or devices. The next experiment would profile the actual quantized matrix path and repeat a production-shaped workload with enough trials.

What was paired, and what was not

The instructor exercise held the pinned Qwen2.5-0.5B-Instruct revision and tokenizer constant while comparing FP16 to bitsandbytes NF4 on one RTX 5070 Ti. It used four quality prompts with natural end-of-sequence generation and, separately, three fixed-24-token timing trials per prompt and format. The fixed-length timing avoids making a shorter generated answer look “faster” solely because it stopped early; the natural-EOS samples expose actual answer behavior. There were 32 successful generations across the two formats and no unexpected runtime failures. The sanitized JSON keeps the prompt, output, trial arrays, versions and resource samples together. This is a paired smoke protocol, not a blind quality study or service-load benchmark.

The two formats were not identical implementations except for bit storage. NF4 can introduce dequantization or a different matrix path. The measured difference therefore belongs to the format plus kernel plus workload on this host. That is the deployment object we actually care about, but it prevents causal attribution to bit width alone. To decide whether a slower path is due to kernel fallback, conversion overhead, shape inefficiency or a small model, profile the actual operators and vary one workload dimension at a time. Do not label the cause from a wall-time ratio without such evidence.

Worked calculation: a 47% drop is not “half the GPU”

The allocated difference is 1.174 − 0.618 = 0.556 GiB. Relative to FP16 allocated peak, 0.556/1.174 ≈ 47.4%. That sentence is supported by this measurement. The reserved difference goes the other way: 1.221 − 1.189 = 0.032 GiB, roughly 2.7% of the FP16 reserved value. “NF4 used half as much GPU memory” would erase the measurement boundary and be false for the reserved pool. A dashboard's device-wide occupied memory could include still other buffers and processes. The allocator may keep freed blocks to reuse rather than returning them immediately to the driver.

The idealized storage argument also leaves KV untouched unless KV itself is quantized. At greater context length or concurrency, KV may dominate the incremental capacity cost even after weights shrink. Conversely, if weights were the binding component and the real serving engine released reserve, lower-bit storage could permit a larger model or more active sequences. Neither inference follows automatically from this small batch-one notebook. The safe workflow is to calculate components, measure peak live and reserved memory under the actual request mix, and leave headroom for bursts and allocator variation.

The nearest-rank p95 trap with three trials

For three sorted durations a ≤ b ≤ c, nearest-rank p95 takes the element at ceil(0.95 × 3) = 3: it is simply c, the maximum observed trial. That definition is mathematically consistent and statistically fragile. It does not mean 95% of future requests finish below c, nor does it characterize a loaded serving system when trials are one at a time. The Topic 03 lab reports per-prompt p95 values as a compact teaching summary, but it also exposes the three raw durations and explicitly limits inference. If a product asks for a tail-latency SLO, collect many independent requests under the declared concurrency and report errors and output lengths beside the percentile.

A tiny output difference can be a hard failure

Both formats answered a simple integer task with 45. On an exact lowercase-color task, FP16 produced blue while NF4 produced Blue.. If the product requires exact lowercase text without punctuation, this pair is worth investigating. It is not evidence of a population-level quality regression from four prompts. Neither format supplied exactly three comma-separated measurement verbs, and both one-sentence capacity answers hit the 24-token cap before completion. Those failures warn us about the tiny model and test design as well as the quantizer.

A proper decision uses held-out prompts paired by input, explicitly scored format contracts, invalid-output counts, uncertainty, and workload-specific latency and memory headroom. A strict JSON or safety rule may be a hard gate, while a softer quality margin needs a larger sample. Freeze the rule before seeing candidate outputs. Do not silently drop truncated or invalid responses from the denominator.

Semantically close can be product-wrong

On the course's exact lowercase-color prompt, FP16 returned blue and NF4 returned Blue.. A human can see the same color. A downstream parser with the declared rule “one lowercase word, no punctuation” can reject the NF4 string. That is a real failure of this observed output against this strict rule, not proof of a systematic NF4 accuracy loss. The arithmetic task returned 45 for both. The three-verb prompt failed the exact comma-separated constraint for both, and both one-sentence capacity answers reached the 24-token cap. In those cases the model, prompt, cap or scoring rule may be the dominant problem; blaming the quantizer would be lazy.

Design a quality study before reading candidate outputs

Start with product failures, not a generic average score. If an API must emit valid JSON, predeclare a parser and schema. If it must cite retrieved facts, specify groundedness adjudication. If it must never emit a disallowed phrase, specify how to count the rare failure and what sample size would be informative. Freeze the prompt set, decoding parameters and scoring rules before opening FP16 and candidate outputs. Pair outputs by the same input so differences are attributable to the candidate path as much as possible; randomize or blind manual review where subjective judgments matter. Keep invalid and truncated outputs in the denominator, because dropping them can make a format look artificially safe.

A held-out set should reflect the deployment distribution and contain hard buckets: exact-format, arithmetic, long context, multilingual input, safety and domain-specific tasks as appropriate. A broad semantic average can hide a catastrophic regression in one hard contract. Conversely, a tiny set of four deliberately tricky prompts can highlight failure modes but not estimate their prevalence. Report both per-bucket counts and uncertainty; identify which rules are hard release gates and which admit a margin. The course's blue/Blue. pair is a teaching example of a hard-format check, not a complete acceptance set.

Speed, cost and capacity are different objectives

A candidate can be slower per request yet useful if it fits a larger model or supports enough more concurrent sequences to improve completed-output goodput under the target SLO. A candidate can also be faster in one isolated kernel and worse in full-service cost because of dequantization, CPU work, failed outputs or repeated retries. State the objective in deployed units: successful requests per dollar under a quality floor, successful output tokens per second under p95 and failure constraints, or the largest model that fits with headroom. Do not optimize checkpoint bytes as a proxy unless the product genuinely pays for storage rather than serving.

Consider an illustrative target of 100 successful requests per minute with less than 1% invalid JSON and p95 under two seconds. A quantizer that cuts allocated memory in half but doubles wall time and raises invalid JSON to 3% fails the contract unless an alternative batching configuration reverses those outcomes. A different product whose binding constraint is fitting a much larger model might make a different decision. These numbers are an invented decision example; the actual Topic 03 smoke has neither 100-request/min load nor a measured JSON rate.

A conditional rollout decision

For this particular 0.5B smoke, “hold NF4 as the default” is defensible: allocated bytes improved, but reservation did not and response time worsened. Another workload could justify lower-bit weights if it is capacity-limited and the kernel path improves under its batch shape. Before shipping, verify the format on the actual device, repeat enough paired requests, inspect quality-sensitive buckets, and retain a rollback route. The goal is the fastest feasible service under quality, error, and memory constraints—not the smallest file.

A quantized rollout needs a reverse path

Keep an FP16 or otherwise validated baseline available when possible, and record the candidate's exact model, tokenizer, quantization artifact, calibration data, engine release and device. Roll out to a bounded slice, compare both hard-format failures and latency/resource distributions under comparable requests, and define a rollback trigger before exposure. If a severe invalid-output bucket appears, a lower average latency should not override the hard gate. If the allocator grows over repeated load cycles, the single-run peak from a notebook is not enough. The course does not perform this production rollout; it teaches what evidence the decision would require.

Do not silently swap a quantized model into the judge reference or student baseline because it looked promising in Topic 03. The grading reference is a separate, verified contract. Any change to its implementation or measurement method requires a provenance-complete recalibration by the course operator; private operator instructions are not a student-facing dependency. The public lesson is simply that teaching comparisons and graded thresholds are distinct evidence streams.

Exercises and answer reasoning

  1. Compute the ideal weight-code payload and FP16-scale metadata for an illustrative 3B-parameter model at four bits with groups of 128. Which live-memory terms are still missing?
  2. Calculate the relative change in peak allocated and reserved memory from the pinned FP16/NF4 run. Which sentence is justified: “allocated fell” or “the process used half as much VRAM”?
  3. With three sorted wall times, where is nearest-rank p95? What can it not establish about future p95 under load?
  4. Score the blue/Blue. pair under a strict lowercase-no-punctuation contract and under a semantic color contract. Why are those different product decisions?
  5. Write one falsifiable next experiment to distinguish a slow NF4 kernel path from a model-size or batch-shape effect. Name the profiler view and the full-service outcome you would remeasure without instrumentation.
Check the reasoning
  1. Four-bit codes use 3B × 0.5 = 1.5B bytes; FP16 scales add 3B/128 × 2 = 46.875M bytes in the idealized scheme. Zeros, alignment, exceptions, other modules, KV, activations, allocator reserve and runtime buffers remain.
  2. Allocated fell by 0.556 GiB, about 47.4% of the FP16 value. Reserved rose by 0.032 GiB. Only the first sentence matches its measurement boundary; no device-wide halving was observed.
  3. ceil(0.95×3)=3, the maximum of three. That sample does not establish a stable tail quantile or a loaded API SLO.
  4. The NF4 string fails the exact-format rule; both outputs identify the same color semantically. The product contract decides which difference matters, while four prompts cannot estimate its frequency.
  5. A useful answer pins model and tokenizer, checks actual NF4 operators with a device/system profile across at least two batch/model shapes, predicts contrasting kernel signatures, then repeats full-service latency, quality, failures and peak memory under the unchanged target workload. One notebook wall-time ratio alone cannot identify the cause.
