The green port that proves too little

Picture an operator who has launched a local model server. The process has not exited; port 8000 accepts connections; a monitoring page says “healthy.” A student client sends a chat request and receives 404. Another sends a long conversation and receives 400. A third sees several streaming content fragments and then a disconnect without a terminal marker. These symptoms have different owners. A listening socket proves almost none of the promised chat contract: not model-name agreement, not template rendering, not context admission, not final completion, and certainly not behavior under load. Chapter 01 taught us to separate clocks and failure populations; here we separate API, engine and GPU boundaries.

The pinned Topic 04 instructor smoke on the RTX 5070 Ti lets us inspect several of those boundaries without inventing a production outage. It used one pinned Qwen2.5-0.5B-Instruct snapshot and vLLM 0.29.0, served locally as topic04. Positive chat and streaming probes completed; a wrong served name returned 404; a 2,329-token rendered prompt against a 2,048-token cap returned 400. The evidence covers five single-client probes, not a 64-client capacity test. We will make the inference from each probe deliberately narrow.

The name the client actually sends

The instructor’s bounded vLLM 0.29.0 run served pinned Qwen2.5-0.5B-Instruct as topic04 on localhost. GET /v1/models advertised topic04; that was the string the SDK had to send in its model field. Sending a different served name returned HTTP 404. The cheapest discriminating probe for “model not found” is therefore the model-list route, not a GPU profile or a restart. The vLLM serve reference documents the server flags; check it against the installed version rather than assuming a current web page exactly describes an older run.

Chat adds a tokenizer/template boundary. JSON role messages are rendered into model-specific tokens; template markers and history consume context. A completions route may work even when chat fails, and a model-list route says nothing about either generation path. vLLM’s OpenAI-compatible server documentation lists the supported routes and caveats. Record the tokenizer revision together with the weights and the rendered prompt-token count.

The model has three names and one pinned body

The source model ID is Qwen/Qwen2.5-0.5B-Instruct. The actual weights and tokenizer came from immutable revision 7ae557604adf67be50417f59c2c2f167def9a775 in the local cache. The API-facing served name was topic04. These strings have different jobs. The client does not need to know the local snapshot path; it does need to send the API name that GET /v1/models advertises. In the smoke record, the advertised list contained topic04. A client that sends another model string receives 404 before a slow GPU investigation is warranted. The run record keeps the served name and revision together, so “the server was up” cannot silently mean a different checkpoint.

Version pinning is not ornamental. A mutable model identifier can later resolve to changed tokenizer files or template behavior even when application code is unchanged. A reproducible deployment records weight revision, tokenizer revision, engine/runtime release, precision and launch arguments. The smoke's WSL2 environment used a V1-runner/native-sampler fallback for host compatibility; that local workaround is not a universal launch recommendation. The vLLM 0.29.0 CLI reference helps find flag semantics, but the recorded vLLM 0.29.0 run and installed help are the authority for this specific experiment.

The JSON message is not the prompt token count

A chat request carries roles and content in JSON. The model consumes token IDs produced after applying its chat template, including role delimiters, possible system instructions, conversation history and generation marker. Counting whitespace-separated words in the JSON body is not a context check. The same visible text can render differently under another tokenizer or template revision. For an over-context investigation, capture the model/tokenizer revision and the rendered token count, not only the raw character count. The pinned 2,329-token negative probe is useful precisely because its rendered count is recorded alongside the 2,048-token server limit.

Separate route success from template success. A model-list route can return 200 while chat fails because the served name in the request is wrong, a template is missing or incompatible, the rendered input exceeds the configured limit, or generation fails after admission. A plain completion request may bypass some chat-template behavior. The cheapest next probe depends on the status: list models for name mismatch, inspect rendered tokens for 400, inspect server/worker logs for generation failure. Restarting everything loses the causal clue and may create a cold-start delay.

The historical ordinary HTTP request

The ordinary historical probe asked a specific question. Keep that question visible before discussing “a request.” The request used POST http://127.0.0.1:8000/v1/chat/completions and JSON content. The SDK’s base_url ended in /v1, and the SDK appended the chat route. A doubled /v1/v1, the wrong port, or the wrong method fails at a different boundary from an unknown served name. In a local smoke, inspecting the exact method, URL and body is often more informative than restarting a healthy model.

temperature=0 requests deterministic-style selection for this smoke, while max_tokens=48 limits the output. A cap does not ask the model to pad to exactly 48 tokens. The model may emit an end marker earlier, and its response may violate the instruction even when generation finishes normally. Nor does the same temperature guarantee identical text across different hardware, kernels, model revisions or server releases. A reproducibility record needs the whole configuration and exact input, not one sampling parameter.

The measured notebook constructed this body from one user message. The tokenizer’s chat template can add its default system message and role delimiters before producing integer IDs. The request JSON itself contains no system entry. That does not imply that the model sees no system text. A local check uses tokenizer.apply_chat_template(messages, tokenize=True, add_generation_prompt=True) from the same immutable snapshot. When requesting text first, avoid adding a second set of special tokens during a later tokenization pass. Preserve the exact rendered string, IDs and tokenizer revision together whenever making a claim about that particular input.

What each probe rules out—and what it leaves open

The ordinary response's usage field recorded 41 prompt tokens and 29 completion tokens, 70 total. Its content was a short definition of an API server and its finish_reason was stop. That is more informative than “HTTP 200”: it shows content and a normal completion reason for one request. It still says nothing about whether the definition is sufficient for a student, whether a different prompt will succeed, or whether the server can handle many clients. In an API smoke, success means the declared route/identity/template/response path works for the probe, not that the model is production-qualified.

A stream has a lifecycle, not just fragments

Server-sent events (SSE) deliver a sequence of frames over one HTTP response. A client may see role or metadata frames before nonempty content; it may see several content deltas; then it expects a completion signal. In the historical 29 September raw probe, eleven JSON frames were parsed and the terminal [DONE] marker arrived. The SDK's separate streaming probe produced content with finish_reason=stop, first content at 0.053 seconds and total wall time 0.463 seconds. These are separate requests; 0.053 is first content observed by that client, not a universal model-token TTFT.

A proxy can buffer or coalesce frames, changing the client's first-content time without changing engine computation. It can also time out or close a stream after several deltas. The application should distinguish an intentionally complete answer from a partial one and avoid saving partial text as if it passed the same quality check. A retry after partial delivery needs its own idempotency and user-interface policy; repeating generation may produce different text. Chapter 01's observer-clock lesson applies again: capture server emission and client receipt separately before blaming decode.

One complete CPU example: bytes become text, lines and events

Server-sent events, abbreviated SSE, define a text framing format. The format does not imply that each network read contains one event, that each event contains one token, or that each token corresponds to one Unicode character. Separate all four units before writing a parser. A socket supplies bytes. UTF-8 maps bytes into Unicode text. Line endings divide that text into fields. A blank line dispatches an SSE event. Only then can an application interpret the event’s data as a JSON object or the API-specific terminal string [DONE]. The WHATWG event-stream specification defines framing; the pinned vLLM chat implementation defines its chat payloads.

The following request and stream are synthetic CPU fixtures. No model produced their content, timings or usage counters. Their purpose is to make every parser state inspectable without downloads, CUDA or a running service. The notebook embeds the same fixture JSON and standard-library parser. The question is deliberately different from the historical server smoke, so a reader cannot accidentally attach old GPU timings to it.

A chunk can end halfway through é

In UTF-8, é occupies the two bytes C3 A9, and ☕ occupies E2 98 95. One network read can end after C3; the next can begin with A9. Decoding the first read independently with strict UTF-8 fails because the sequence is incomplete. Decoding it with replacement mode may insert a replacement character and irreversibly damage the JSON string. An incremental decoder retains the unfinished byte prefix and combines it with the next read. The same reasoning applies to the three-byte coffee character, which the fixture deliberately splits after E2.

Chunk boundaries are accidental transport observations. A proxy, TLS record, OS buffer or HTTP client implementation can change them without changing the logical event stream. The classroom fixture supplies sixteen chunks to stress this fact. Joining every chunk first and parsing at EOF would recover the same final text, but would defeat streaming and make first-content measurements meaningless. A correct streaming client processes complete events as soon as enough bytes arrive while preserving every incomplete suffix for the next read.

Line buffering and event dispatch

SSE accepts LF, CRLF or CR line endings. CRLF may itself split between reads, so the parser needs to remember a trailing CR and avoid interpreting the following LF as an extra blank line. A line beginning with a colon is a comment. A field such as data: hello contributes hello to the event’s data buffer; the parser removes at most one optional space after the colon. Two data lines become one data value separated by newline. The next blank line dispatches the assembled event. Unknown fields do not become JSON content merely because they arrived on the same connection.

For example, data: {"choices":[], followed by data: "usage":{"prompt_tokens":13,"completion_tokens":4,"total_tokens":17}} and a blank line forms one JSON document with a newline after its comma. Calling json.loads on either data line independently fails. Conversely, a single network read may contain two whole events, and a parser that stops after the first loses data. The notebook tests both split and coalesced input. At EOF, the parser must not dispatch an event that never reached its blank-line terminator.

A minimal processing sketch is below. It names state rather than hiding it inside a library. The actual notebook implementation additionally validates JSON shape, choice index, byte limits, trailing input, usage fields and invalid UTF-8. Its scope is a single text choice. It does not implement browser reconnection, arbitrary event handlers, tools, audio, multimodal output or every provider’s stream dialect.

for byte_chunk in incoming_reads:
    decoded_text = utf8_decoder.feed(byte_chunk)
    for complete_line in line_buffer.feed(decoded_text):
        if complete_line is a comment:

        if complete_line is a data field:
            event_data.append(field_value)

Protocol completion, output quality and cancellation

Keep at least the accumulated content, finish reason, usage object, terminal-marker flag and error state. A role event can initialize metadata without appending text. A nonempty content delta appends exactly its string; trimming every delta would turn Café plus ☕. into Café☕.. An empty choices list can carry usage and must not trigger choices[0]. A finish reason can arrive before the final accounting event, so stopping immediately at finish discards legitimate trailing metadata. Under the course’s strict one-choice text contract, normal completion requires a recognized finish reason, terminal [DONE], valid stream shape and no recorded error.

finish_reason="stop" usually indicates the generation reached its stopping condition. finish_reason="length" indicates a cap stopped it. Either can terminate a syntactically complete stream, but a length-limited answer may be unacceptable for the task. A parser should retain the reason, while the application decides whether the answer satisfies its requirements. A calculator demanding one integer can reject fluent prose after a normal stop. A summarizer can reject a sentence cut in half after a length stop. A tool-calling application requires a different success predicate from this chapter’s text-only client.

The API may send an error object after HTTP headers already declared success. At that point, the server cannot revise the already transmitted status code. The pinned vLLM implementation can emit an error event and then [DONE]. Therefore the terminal marker alone cannot mean successful generation. Preserve the error even when DONE arrives afterward. A stream with plausible partial text and no DONE is likewise incomplete under this course contract. Saving that text as a fully accepted result corrupts both the user experience and the success denominator.

The correct timestamp depends on the question

For the synthetic fixture, the first data event arrives at 0.03 seconds but contains only the assistant role. First content arrives at 0.10 seconds, another content event arrives at 0.14, finish at 0.15, usage at 0.16 and DONE at 0.17. If send time is zero, first-content delay equals 0.10 − 0 = 0.10 s, or 100 ms. Terminal wall time equals 170 ms. An empty heartbeat at 10 ms does not become a first-token measurement merely because it is the first transport activity. These are illustrative client arrivals supplied by the fixture, not measurements of vLLM.

The 40 ms difference between the two text events is an inter-event interval. It cannot establish token latency because the two strings may each encode multiple model tokens. Even when the server exposes token IDs, buffering may group their client arrivals. To compute a mean of known token-arrival gaps, state that there are N observed token timestamps, use (tN−t1)/(N−1)(t_N-t_1)/(N-1)(tN​−t1​)/(N−1) (where t1t_1t1​ and tNt_NtN​ are the first and last token-arrival times), and retain the complete arrival sequence if studying jitter. With 40 tokens, first arrival at 0.40 s and last at 1.18 s, the illustrative mean is 0.78/39 = 0.020 s/gap. A DONE event at 1.20 s adds 20 ms of terminal processing; substituting it for the last-token timestamp mixes two quantities. Neither calculation isolates GPU decode.

A client timeout does not prove engine cancellation

A connection deadline limits establishing the route. A first-content deadline limits waiting for useful text. A read-inactivity timeout limits the interval without incoming transport progress. A total deadline limits the entire attempt. These clocks answer different questions and may expire at different times. An SDK timeout parameter is not automatically a whole-request wall budget; inspect its HTTP client semantics. Record the expired clock, preserve partial content with its incomplete status, and close the response in a cleanup path. Never substitute zero for an unavailable first-content time.

Closing the client stream is the first step in cancellation. The frontend and any proxy must observe the disconnect, propagate an abort for the relevant request, and release live engine state. A client-only fixture can prove that the application labels an attempt cancelled, but cannot prove that a real GPU worker stopped generating or released KV blocks. That needs engine-side active-request evidence, resource recovery and, ideally, a follow-up bounded smoke. The historical course run did not contain a cancellation experiment, so cancellation cleanup remains a proposed test rather than a measured success.

Browser EventSource adds automatic reconnect behavior around a GET request. This chapter uses an HTTP POST carrying a JSON generation request and reads its response as SSE. Copying EventSource’s reconnect policy blindly into this client can start another generation, duplicate text or replay tool side effects. A retry is a new attempt unless an explicitly supported application protocol proves otherwise. Keep its attempt ID and metrics separate. After partial display, decide whether to replace the old answer, offer a user-controlled retry, or visibly preserve the partial answer. Appending a regenerated answer to the first one is usually a bug.

Worked incident: healthy generation, delayed delivery

Consider an illustrative observation: direct loopback receives its first content at 100 ms and successive events afterward, while an external client receives all events near 900 ms. This pattern suggests buffering somewhere on the external path, but does not prove which component caused it. Compare the same prompt, model, sampling settings and request correlation fields. Inspect server emission spans and proxy configuration without subtracting unsynchronized wall clocks from different machines. Test the direct and proxied paths separately, with one bounded request each. If the proxy buffers by block, changing that policy and rerunning the paired test should change client arrival shape while leaving engine work comparable.

A successful local probe does not certify remote timeouts, authentication, TLS or cancellation propagation. Equally, a slow remote first-content time does not justify increasing GPU memory utilization before inspecting the route. Write the diagnosis as a falsifiable hypothesis: “The proxy holds events until its buffer flushes.” Evidence against it could be late engine emission even on the direct route. The purpose of the service map is to find this next discriminating measurement, not to assign every delay to the nearest unfamiliar component.

A useful negative test is an expected failure

The wrong-model and over-context probes deliberately produce non-2xx responses. They are not “failed lab runs”; they test that invalid input is rejected at a predictable boundary. For the wrong-model request, 404 points first to the served-name contract. For the 2,329-token rendered prompt against a 2,048-token cap, 400 points to validation of a declared size limit. The latter is better than allowing impossible work to consume GPU memory until an obscure worker error occurs. A 500-class error or transport disconnect on a valid request would be a different incident and should not be merged with these expected negatives in a “failure rate” denominator.

When writing automated checks, assert the status, the relevant response shape, and the reason the input should fail. Do not merely assert “not 200.” Otherwise a broken server that returns 500 for every request would pass the negative suite. Positive and negative probes belong together: model list, ordinary chat, stream completion, wrong identity and over-context jointly test a small observable contract. Their combined success is a strong smoke result and a weak capacity result—exactly the distinction the chapter intends to teach.

Context is a memory policy, not merely a string length

Count rendered tokens after applying the exact chat template, then add the requested output cap before judging a model-length limit. Long prompts also create KV state; a request-count cap alone cannot guarantee fit. The KV budget explorer shows the logical payload arithmetic, but it omits vLLM’s allocator and runtime reserves. The engine arguments document context and memory controls; the run record states which values this course actually used.

Worked context calculation: reject before expensive work

The server launch set --max-model-len 2048. The negative probe's chat template produced 2,329 prompt tokens. The prompt alone exceeded the configured limit by 2329 − 2048 = 281 tokens, so rejecting it with HTTP 400 was a valid, inexpensive outcome; no amount of queue patience could make that request fit the declared context. A different illustrative request with 1,800 rendered prompt tokens and a 512-token output cap asks for up to 2,312 total positions, also beyond 2,048, though its input alone fits. An application should make this distinction visible instead of telling every 400 caller only “bad request.” The first pair is measured; the second is a worked example.

A request-count cap is not a memory proof

The launch also set --max-num-seqs 4 and --gpu-memory-utilization 0.45. Four is an upper bound on simultaneously active sequences in that configuration, not an achieved client throughput or evidence that four maximum-length sequences were ever present. From the pinned 0.5B model config, 24 layers, two KV heads and a 64-dimensional head at two bytes per value give 2 × 24 × 2 × 64 × 2 = 12,288 bytes = 12 KiB of logical FP16 KV payload per retained token. Four hypothetical full 2,048-token sequences would hold 4 × 2048 × 12 KiB = 96 MiB of logical KV payload. This is not the service's allocated VRAM: model weights, runtime reservation, block accounting, graph buffers and other tensors remain.

The arithmetic also does not imply that a 45% memory-utilization target is “mostly unused GPU.” Engine flags control an allocator budget and runtime behavior; memory visible in a device monitor may include reserved pools. A cap of four sequences can prevent the instructor smoke from overcommitting a host but tells us little about a different model or a 64-client workload. To design a real admission envelope, measure peak live and reserved memory across the intended context distribution and check failures as clients increase. Chapter 02's KV calculation is a component ledger, not a license to set request count by division alone.

Diagnose the boundary before touching flags

Run it weekly without starting from zero

Keep pinned model snapshots and package environments in the project-local cache. Start only one bounded GPU process at a time on the instructor host, preflight available RAM and GPU headroom, and stop the service cleanly after tests. A clean process restart does not require deleting immutable model weights and downloading them again. Keep secrets, private prompts, and unsanitized logs out of public evidence. The course’s public submission example carries only student-facing artifacts.

Weekly repetition should reuse assets, not stale processes

A repeatable lab has two different kinds of state. Immutable model snapshots, pinned packages and declared benchmark inputs can be prefetched once into a durable project-local cache. Running servers, sockets, GPU allocations and temporary output files are disposable and should be recreated or cleaned between attempts. Deleting the whole cache to get a “clean run” forces a network download, adds nondeterminism and wastes the course window; retaining a dead worker to save startup time risks stale ports and memory. The instructor procedure verifies cached revisions in offline mode before launching one bounded GPU process at a time.

The Topic 04 smoke used loopback-only host 127.0.0.1, port 8000, FP16, a 2,048-token model length, at most four active sequences, a 0.45 GPU-memory-utilization target and eager execution. These settings protected and stabilized this one WSL2 teaching run; they are not production defaults to copy without measuring. The run completed in a bounded process, and the GPU and port were released afterward. If a later session finds the port still occupied or GPU memory above baseline, that is a preflight failure to investigate before starting another server, not a reason to stack a second process on the same device.

The launch command as a reproducibility record

vllm serve <PINNED_LOCAL_SNAPSHOT> \
  --served-model-name topic04 \
  --host 127.0.0.1 --port 8000 \
  --dtype float16 --max-model-len 2048 \
  --max-num-seqs 4 --gpu-memory-utilization 0.45 \
  --enforce-eager

<PINNED_LOCAL_SNAPSHOT> is an explanatory placeholder, not a literal shell path. The notebook resolves the verified local snapshot and passes arguments as a list, avoiding shell interpretation of a path. --served-model-name fixes the API identity. --host 127.0.0.1 binds to the loopback interface. --dtype float16 declares the model compute/storage choice supported by this run. --max-model-len 2048 establishes the context cap. --max-num-seqs 4 limits sequences processed in one iteration according to the vLLM 0.29.0 CLI reference; it is not four requests per second or a cap on every connected client. --gpu-memory-utilization 0.45 controls an executor memory budget. --enforce-eager chooses the eager execution path for this bounded teaching run.

These flags interact with model configuration, runtime defaults and hardware. A reported memory percentage is not the logical KV size, and a successful startup is not proof that every admitted workload fits. Save the installed runtime version and effective configuration beside the command. The historical WSL2 host used a V1-runner/native-sampler fallback. Keep that workaround scoped to the recorded environment instead of publishing it as a universal performance recommendation. Reusing an already matching package environment is appropriate; blindly reinstalling on every notebook restart wastes time and introduces a second failure source.

Health, readiness and the first successful request

Readiness is a decision for a particular consumer. A process existence check finds an early crash but does not demonstrate a listener. A TCP connection demonstrates reachability but may terminate at a proxy. A health endpoint in the pinned implementation checks engine health, while /v1/models exposes configured identities. Neither exercises the exact chat template and output contract. The notebook therefore follows a bounded readiness wait with identity verification and a small complete chat request. A health check is useful evidence without being a substitute for this sequence.

Bound the wait with a monotonic deadline. If the process exits, report the exit and local log path immediately rather than sleeping until the deadline. If readiness never arrives, terminate only the server process tree owned by this run and verify cleanup before another attempt. Preserve the first failure and its context. Repeatedly restarting a worker while discarding logs creates a loop that can consume RAM, leave stale ports and conceal the original error. A missing model snapshot should fail before server startup when the session is meant to run offline.

What a useful service artifact must let another reader check

The lab artifact is more than a screenshot of text. It identifies the model repository, immutable revision, tokenizer, served name, runtime versions and launch arguments. Each probe records its own request settings and observed outcome. A successful ordinary request retains content, finish reason, usage when provided and wall time. A streaming request retains first-content time, completion state and enough sanitized events to distinguish a full response from a partial one. Expected-negative probes retain the exact status and reason. Startup and cleanup evidence describe process and resource state separately from request latency.

For the new CPU path, retain the fixture version, reconstructed output and classifications of complete, partial, malformed and cancelled variants. They prove parser behavior, not a live endpoint. For the GPU path, students independently arrange a CUDA GPU and run the bounded smoke. A CPU-only replay cannot satisfy that requirement. Questions containing logs or repository access details belong in the private student repository’s Issue with @levshaazz; general questions without private data can use the public template’s Issues. Avoid placing API keys, local usernames, private prompts or environment dumps in the submitted public-facing excerpts.

A compatible API is not automatically a safe public API

The local smoke binds to loopback. Exposing an endpoint to students or the internet adds authentication, network policy, rate limits, tenant isolation, logging/privacy rules and abuse handling. An OpenAI-compatible request schema does not supply those protections on its own. Do not place an API key in a slide, notebook output, screenshot, URL query string or public repository. Redact private prompts and client identifiers before publishing traces. A reproducible teaching example can share model revision, workload shape, status codes and sanitized responses without revealing secrets or private grading inputs.

Also distinguish API compatibility from exact behavioral identity. Two servers may accept the same chat-completions JSON yet differ in supported optional fields, chat-template defaults, tool-call behavior, error bodies or token accounting. Pin the installed release and test the fields your application actually uses. The instructor smoke exercises a small core: model list, ordinary chat, streaming completion and two negative cases. A product that depends on tools, JSON schema, parallel calls or long context needs its own contract tests; passing this chapter's probes is a foundation, not certification of every OpenAI API feature.

Do not turn a five-probe smoke into a capacity claim

The historical 29 September non-streamed wall time of 0.748 seconds and separate streamed 0.463 seconds are observable, but they have no latency distribution. The stream's 0.053-second first content does not establish p95 TTFT. The server's four-sequence cap does not establish four requests per second, let alone behavior at 64 clients. For a capacity claim, declare an arrival process, input/output distribution, duration, deadline and success rules; sweep bounded load while measuring all attempts, goodput, successful latency distributions, rejects, timeouts and resource headroom. Preserve raw records and check teardown at each stage. That work belongs to the benchmark/serving-performance curriculum, not to this API-contract smoke.

This limitation is useful in incident triage. If a valid request intermittently times out, do not cite the 0.748-second smoke as proof that the model “should be fast.” Compare the actual workload and concurrent live-token state with the smoke. If the problem is a wrong served name, a long load test is wasted effort; if the model list is correct but p95 collapses at load, another isolated SDK hello-world is equally uninformative. Each probe should falsify a hypothesis at the appropriate layer.

Terms used in this chapter

Served model name
The API-facing identifier advertised to clients, independent of a local filesystem path.
Chat template
The model-specific rendering rule that places roles, message content and generation delimiters before tokenization.
UTF-8
A variable-width encoding of Unicode text into bytes. One character can cross network-read boundaries.
SSE event
A dispatched event assembled from text fields and a blank-line boundary. Its data is not inherently a model token.
Delta
An incremental update, such as a fragment of content or metadata. Append content exactly, preserving spaces.
Finish reason
The generation-level reason an output ended, distinct from the terminal transport marker.
First-content delay
The client interval from sending the request to the first nonempty generated text delta.
Readiness
An operational decision that this deployment can serve the declared client contract, supported by appropriate probes.
Cancellation
A request to stop an in-flight attempt. Client classification and actual server resource release require different evidence.
Smoke test
A small bounded test of a declared path. It can reveal broken integration without estimating capacity or quality over a population.

The next topic opens the engine boundary: how live sequences share KV blocks and how the scheduler admits work at iteration boundaries. Here the deliverable is the observable client and lifecycle contract that makes those later measurements interpretable.
