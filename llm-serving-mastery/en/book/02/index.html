Inference bottlenecks: KV cache, memory hierarchy, autoregression

Follow an exact prompt through every decoder-block operation, real tensor slices and the next token, then connect shapes and retained state to GPU bottlenecks.

This is a public reading draft under substantive revision. Use the slides, lab and pinned evidence alongside it.

A decoder has two different jobs: prefill the supplied prompt, then generate dependent output steps. Treating both as “GPU inference” hides the shapes, bytes, and timing boundary that an optimization must actually change.

Start with the exact message, not a box called “prompt”

Our small demonstration sends the following two messages to a pinned Qwen2.5-1.5B-Instruct model. Before revealing its answer, predict three things: does the GPU receive only the user sentence, does the first forward process one position or the whole prompt, and when does the first selected output acquire its own K/V? This is an actual recorded, greedy generation on the instructor GPU, not hand-written output. The replay and measurement record preserve the exact input and every selected token.

system: You are a helpful assistant. Reply with only the requested numbers.

user: Continue the sequence with three numbers: 2, 4, 6,

Observed answer, decoded with special tokens omitted:

8, 10, 12

The run selected 10 output tokens; stop reason: eos. Visible text and token count are not interchangeable: a stop/control token may have no visible text, and punctuation, spaces and digits can occupy separate token IDs. This is a model-behavior demonstration, not an answer-quality benchmark. The configured limit is 24 new tokens; a limit is not a promise that exactly that many will be generated.

Here that difference is visible without any abstraction: the answer has three numbers, but “10” is selected as 1 then 0, and “12” as 1 then 2. Each comma and space also has its own choice; ID 151645 ends the assistant turn. The output is ten IDs, not three number-sized operations. Spaces use token ID 220 (tokenizer piece Ġ); that marker is tokenizer notation, not a literal character added to the answer.

Inspect every exact input token ID, tokenizer piece and decoded text

A tokenizer piece is the tokenizer's stored notation; the decoded-text column shows what that single ID contributes. JSON quoting exposes spaces and newlines. Individual tokens can represent byte fragments in other prompts, so decoding a full prefix is the safe way to reconstruct text.

Reveal the output one forward at a time

In the first row, prefill processes all 42 input positions and chooses the first output ID. Every later row feeds the previously selected ID back as one new position. The table is drawn directly from the recorded replay; the cumulative text is decoded from the complete output prefix, not assembled by guessing how pieces join.

Final retained length is 42 + 10 − 1 = 51. The last selected token has not been fed through another forward, including when it is an EOS token. Selection alone does not compute its hidden states. The demonstration synchronizes and records each step to make this ledger visible; that observation protocol changes the loop and must not be treated as the uninstrumented v2 benchmark.

Why can 4,096 known positions finish before 31 dependent steps?

Now deliberately change experiments: the natural-text replay explains the dependency; the required protocol-v2 matrix isolates shape with repeated synthetic IDs and fixed output lengths. On the pinned RTX 5070 Ti, Qwen2.5-1.5B at B1/P4096/O32 had median prefill 163.7 ms [163.4–163.8] and subsequent 31-step decode 1,039.1 ms [763.9–1,154.4]. Each interval has five raw observations in the canonical v2 evidence. Thousands of known prompt positions took less wall time than a few dozen dependent generation steps. These synthetic inputs are not the short sentence shown above, and these medians are not a measured combined request duration.

The answer begins with the dependency graph. The prompt is known up front. Output tokens are not. Inside each GPU operation there may be enormous parallelism, but the next output token still depends on the previous one. That serial axis changes how much work can be batched and reused. It also changes what a profiler snapshot means: a kernel may be efficient and still sit inside a service dominated by sequential steps, launches, waiting, or data movement.

From text to a tensor: what actually enters the GPU?

Return to “Continue the sequence with three numbers: 2, 4, 6,” above. Before the decoder sees it, the recorded chat template adds the shown system text, role delimiters and control tokens, and the tokenizer maps that complete representation to integer IDs. A token can represent part of a word, punctuation, whitespace or a special marker. Counting words is therefore not an acceptable substitute for measuring tokenized length. By contrast, the required matrix deliberately bypasses realistic chat: it repeats a short token-ID pattern to produce exactly 128 or 4,096 positions. That makes the shape experiment reproducible, but it does not test retrieval quality, useful answer length or semantic diversity. Do not attach the natural prompt to the matrix's synthetic timings.

The input tensor has a batch axis and a sequence-position axis, conventionally written [B,S]. Its elements are integer indices, not semantic vectors. An embedding table with vocabulary size V and hidden width d selects one floating-point vector per ID, creating [B,S,d]. For our actual replay, B=1, S=42, d=1536: 1×42×1536=64512 values. At two bytes per FP16 value the logical output payload is 129024 bytes, or 126 KiB, for this tensor alone. This is arithmetic from the observed input shape and pinned model config, not an allocator reading. It does not count the embedding table, later activations or KV state. The same symbol “B” sometimes means bytes in systems writing and batch size in model equations; this chapter writes units explicitly to keep those meanings separate.

Transformer recap: follow the representation, not just the boxes

Our target is specific: explain how the last input position produces ID 23, the visible 8, and how feeding that ID back makes the following comma possible. The last input is position 41, the newline after the assistant role marker, not the user's digit 6. A causal language model predicts the next ID from the last processed position's contextual representation. That representation can already depend on every allowed earlier position, including the user's sequence and the system instruction. A newline embedding alone does not encode the answer.

We use two lenses and never mix their numbers. The real model has hidden width 1,536, 28 decoder blocks, 12 query heads, two KV heads, head width 128, an 8,960-wide gated MLP and vocabulary 151,936, from the immutable model configuration. The small arithmetic model below has three positions, width four, one attention head, MLP width six and five arbitrary output labels A–E. Its weights are invented so every multiplication fits on a page. It is not a compressed Qwen, not a trained model, and does not “understand” our prompt. Its complete weights and intermediate matrices are generated by the CPU-only notebook implementation and preserved in the recap evidence package.

The full pre-norm block has two bypasses and two additions

For block input X, first compute A = Attention(RMSNorm₁(X)), then H = X + A. The next branch computes M = MLP(RMSNorm₂(H)), then Y = H + M. Both additions are elementwise between tensors with the same [B,S,1536] shape. The original stream bypasses each branch; it is not replaced by a norm output, and the second residual adds to H, not back to the original X. These are the actual pre-norm ordering and two residual additions in the pinned Qwen2 implementation.

“Residual” names the additive update path, not a separate learned cache. It lets each sublayer add an update to the running representation and provides a direct route through the network. At inference these additions still read and write values; drawing the bypass is not decorative. Q/K/V and MLP weights belong to this particular block. Block 1 repeats the same kind of computation with different learned weights; it does not reuse block 0's parameters.

RMSNorm: reduce across features, independently at each position

Root-mean-square normalization computes r = sqrt(mean(x²) + ε), then zᵢ = gᵢ xᵢ / r. The mean runs over the hidden-feature axis, not over tokens or batch. The learned gain g has one value per feature; epsilon prevents a zero denominator. Unlike mean-centering LayerNorm, this formula does not subtract the feature mean. The pinned implementation accumulates the normalization calculation in float32 and casts back to the input type before applying its gain; that arithmetic boundary matters when comparing rounded examples with FP16 captures.

Use the toy's last row x=[1,2,3,4], gains all one and ε=0.000001. Squared values are [1,4,9,16]; their mean is 30/4=7.5. The denominator is sqrt(7.500001)≈2.738613; normalized output is [0.365148, 0.730297, 1.095445, 1.460593]. The width remains four. The two earlier rows are normalized separately; no token has mixed with another yet. Neural features are dimensionless numerical coordinates here, not seconds, bytes, probabilities or four named linguistic properties.

Three projections: different questions asked of the same normalized row

Compute Q=ZWq+bq, K=ZWk+bk and V=ZWv+bv. Our written matrices use W=[input features, output features]; PyTorch Linear stores the transpose, so its code performs x @ weight.T + bias. For output coordinate j, sum zᵢWᵢⱼ over input coordinates, then add the corresponding bias once per row. All rows use the same weights. These are learned projections, not a token table lookup and not three copies with interchangeable roles.

The toy uses Wq=I, bq=[0.1,0,−0.1,0]; Wk=diag(0.5,1,0.5,1), bk=[0,0.1,0,−0.1]; and Wv=I, bv=[0.05,0,0,−0.05]. Its last-row Q is [0.465148, 0.730297, 0.995445, 1.460593], K is [0.182574, 0.830297, 0.547723, 1.360593], and V is [0.415148, 0.730297, 1.095445, 1.410593]. For example k₀=0.365148×0.5+0≈0.182574. The real Qwen Q/K/V projections also have biases, but not these invented weights or values. Its attention output and MLP projections have no bias in the pinned implementation.

Reshape, transpose and grouped-query sharing

Real Q projection produces [1,42,1536]. Reshape the final width into 12×128 to get [1,42,12,128], then transpose the position/head axes to [1,12,42,128]. This changes indexing, not the learned values; an implementation may need a contiguous copy later. K and V project to width 2×128=256, giving [1,2,42,128] each after the same axis arrangement. In grouped-query attention, six Q heads share one KV head: Q heads 0–5 use KV head 0, Q heads 6–11 use KV head 1. Distinct Q heads can still yield different attention distributions.

The toy has only one head, so splitting and concatenating that head are identities; it demonstrates arithmetic, not GQA. The real cache retains two KV heads, not twelve duplicate copies. A backend may expand or otherwise handle shared K/V while computing attention; that working representation is not a reason to multiply the persistent cache formula by the Q-head count.

RoPE: position changes Q and K before they meet

Rotary position embedding rotates coordinate pairs in Q and K according to absolute position; V is not rotated by this operation. For a pair (a,b) at angle φ, the result is (a cosφ − b sinφ, b cosφ + a sinφ). In Qwen's split-half layout the pairs are (i,i+d_head/2), not adjacent indices. The toy's four coordinates therefore pair (0,2) and (1,3). Frequencies differ by pair; φᵢ=p/θ^(2i/d_head). Shared rotations encode relative-position information in later dot products without adding a separate position vector to V.

At toy position p=2, head width four and toy θ=10,000, the two angles are 2 and 0.02 radians. Last-row Q becomes [-1.098726, 0.700941, 0.008707, 1.474906], K becomes [-0.57402, 0.802921, -0.061919, 1.376926]. At position zero both angles are zero. Rotation preserves the pair's squared norm; it does not preserve every dot product when the two positions differ. Our pinned real model uses θ=1,000,000 and head width 128 instead. Those configuration values cannot be silently substituted into this four-dimensional toy.

Scores, causal mask, stable softmax and the weighted value sum

For query position i and source position j, calculate sᵢⱼ = dot(qᵢ,kⱼ)/sqrt(d_head). The scale is 1/2 in the toy and 1/sqrt(128) in the real model. A causal mask forbids j>i: future known prompt IDs must not leak into an earlier position's representation. Conceptually their scores become minus infinity before softmax. The JSON uses null for these forbidden scores, because JSON has no Infinity literal. Their probabilities are exactly zero in the toy.

Last-row toy scores are [-0.424078, 1.506342, 1.611894]; this last position may use all three keys. For stable softmax, subtract the largest score, exponentiate, then divide by the sum: αⱼ=exp(sⱼ−max(s))/Σₖ exp(sₖ−max(s)). Subtraction leaves the mathematical probabilities unchanged but avoids overflow. Here the resulting weights are [0.0643, 0.443182, 0.492518], summing to one. Row zero has only itself available and therefore has weights [1,0,0]. Normalization runs over allowed key positions for each query/head, not over hidden coordinates or heads.

The attention result is oᵢ=Σⱼ αᵢⱼvⱼ, a weighted vector sum, not a selected token and not a sum of key vectors. For its first coordinate, our last row computes 0.064300×1.464212 + 0.443182×0.05 + 0.492518×0.415148≈0.320776. The complete result is [0.320776, 0.986437, 0.630461, 1.296122]. This is the operation that mixes source positions. Projection, RMSNorm and the following MLP work on each position independently, although their inputs may already contain context mixed by attention.

Real attention has a conceptual score shape [1,12,42,42] for this prefill. Do not infer that an SDPA implementation must allocate the full matrix in device memory: fused kernels can compute the same result with tiled intermediate state. Similarly, showing an attention-weight row is a mathematical explanation, not a profile of the physical CUDA kernel.

Concatenate heads, project back, then add the original stream

After attention, transpose [B,H,S,d_head] back to position-major ordering and flatten the head/feature axes into [B,S,H×d_head]. Qwen's twelve 128-wide outputs become width 1,536. The learned output projection mixes head-derived features and returns the residual width. The operation is not an average over heads. In the toy, one-head concatenation does nothing and Wo=0.5I, so the last attention output becomes [0.160388, 0.493219, 0.31523, 0.648061].

Now perform the first addition: H=X+attention_output. For the last toy row, [1,2,3,4]+[0.160388, 0.493219, 0.31523, 0.648061]=[1.160388, 2.493219, 3.31523, 4.648061]. Both summands have width four. Omitting this addition would yield a different model, even if every Q/K/V and softmax calculation were correct.

A gated MLP is two branches, a nonlinearity, a product and a contraction

Normalize H with a second independently learned RMSNorm. Real [1,42,1536] then feeds two different linear projections: gate=Z₂Wgate and up=Z₂Wup, both [1,42,8960]. Apply SiLU(g)=g×sigmoid(g)=g/(1+exp(−g)) to the gate branch. Multiply it elementwise with the up branch; this is not another matrix multiplication. A final down projection maps width 8,960 back to 1,536. The gated structure is commonly called SwiGLU; SiLU supplies the swish nonlinearity, while the second branch supplies the values being gated.

The toy's last row after the second normalization is [0.366225, 0.786874, 1.046305, 1.466954]. Its last-position gate is [0.366225, 0.786874, 1.046305, 1.466954, 0.576549, 1.25663] and up branch is [0.183112, 0.393437, 0.523153, 0.733477, -0.420649, -0.420649]. Inspect coordinate zero: g≈0.366225, SiLU(g)≈0.216273, and multiplying by up≈0.183112 yields 0.039602. A gate is not a binary on/off switch; it need not lie between zero and one. Negative up values can produce negative products even where the gate is positive.

The full six-wide product is [0.039602, 0.212734, 0.405095, 0.874332, -0.155282, -0.411486]. The toy down projection returns [-0.005628, 0.037655, 0.060125, 0.177435]. Its second residual addition gives Y=H+down=[1.15476, 2.530874, 3.375355, 4.825495]. Width expansion creates feature interactions within one position; the MLP does not scan earlier token rows. Which operations preserve the position axis? Every operation in this paragraph does. Which operation mixed positions earlier? The attention-weighted V sum.

Twenty-eight blocks, final normalization, vocabulary logits, then one choice

The real representation traverses 28 separately parameterized blocks, in dependency order, then a final RMSNorm. A single request cannot execute block 27 before it has the required output of block 26; parallelism is inside operations, across heads/features/positions where allowed, and across independent sequences—not arbitrary reordering of layers. The last position's final hidden row is projected to 151,936 vocabulary scores. Our capture and the lab request only last-position logits with logits_to_keep=1; earlier prompt positions still undergo the decoder and build their K/V.

This checkpoint sets tie_word_embeddings=true: the vocabulary head shares the learned embedding weight, with no separate output bias. Input embedding looks up a vocabulary row; the output head compares a contextual hidden row against all vocabulary rows. Shared parameters do not make these the same operation, and it would be wrong to count the tied table twice as two independent weight allocations. Our toy starts from invented feature rows and uses an independent five-label head, so it does not demonstrate this parameter sharing.

In the one-block toy, final normalized last row is [0.35461, 0.777194, 1.036522, 1.481838]. Its five invented logits are [0.35461, 0.777194, 1.036522, 1.481838, 0.912541]; softmax probabilities are [0.107093, 0.163413, 0.211793, 0.330605, 0.187097]. Greedy chooses label D at index 3; it does not sample or choose the largest attention weight. Softmax is useful for explaining probabilities but is unnecessary for argmax because it preserves score order. Real Qwen's answer 8 comes from the real vocabulary/logits record below, not from relabeling toy D as 8. Probabilities are model distribution values under the stated logits/rule, not calibrated confidence that an answer is correct.

Mathematical attention reconstruction is a different kind of evidence

For query head 0 at position 41, the retained Q/K/V values allow a CPU float32 reference calculation over all 42 keys. It reconstructs a normalized attention row and weighted V sum; these are not observed weights inside the SDPA kernel. The largest reconstructed weight is about 22.28% at key position 3. A large attention coefficient alone is not a causal explanation of the model's answer: it is one head in one layer and the values/output projections matter too.

The selected weighted output's maximum absolute difference from captured native attention output is 0.00036168 in prefill, against the recorded tolerance 0.025. This checks numerical consistency under different precision/order; it does not prove a native score-matrix allocation, kernel duration or bitwise equality. The record also checks both residual additions, norm/projection slices, RoPE and the gated MLP rather than assuming that matching the final token validates every intermediate value.

Feed the selected ID back: one query position, a longer history

Immediately after prefill selected ID 23, KV still contains 42 positions. Embed that 8 at absolute position 42 and run all blocks again. Each layer computes one new Q, K and V; position-aware K and unrotated V append to that layer's history. The query is [1,12,1,128] while each retained K/V tensor becomes [1,2,43,128]. The query attends 43 allowed keys, including its own newly appended key. It does not merely look at the previous 42, and it does not recompute all 42 previous projections in the cached path.

Why retain K/V but not all Q? A later step needs the old positions as sources, so its new Q compares with saved keys and mixes saved values. Old queries answered earlier prediction questions and are not needed for that new weighted sum. The cache lives separately in each layer because each layer has different projections and representations. Q/K/V are not static token embeddings: the same token ID at a different context, layer or position can produce different projected values.

Across 28 layers, the logical FP16 K/V payload grows from 42×28 KiB=1,176 KiB to 43×28 KiB=1,204 KiB, exactly one 28-KiB position. After this second forward chooses the comma, that comma is again only a chosen ID; it has no K/V until the next forward. The small toy deliberately does not simulate tokenizer semantics, 28 layers or GPU execution; use the recorded real shape ledger to connect its operations to inference.

Use the operation map to ask a performance question

Dense Q/K/V, output, gate/up/down and vocabulary projections multiply activation rows by weights. RMSNorm and softmax include reductions over different axes; RoPE, residual additions and SiLU/product operate elementwise or on pairs. Attention mixes across the growing history, and K/V remains live for later steps. Reshape/transpose changes the view/layout and can entail copies when a consumer requires a particular layout. Which operations become separate kernels or fuse together depends on the selected backend; a mathematical box is not automatically one CUDA launch.

Flatten batch and new positions into M=B×S. The same 1,536-wide projection sees M=42 in our prefill and M=1 at the next step. In a constructed B8/P512 batch, it instead sees M=4096 and then M=8. Retained history changes attention's source axis, not the number of newly projected query rows. These shapes motivate bandwidth/compute hypotheses later in the chapter; they do not by themselves predict a millisecond ratio.

The first token is not a decode forward

Keep a tiny ledger before writing a timer. With prompt IDs x1…x4, prefill computes their K/V and logits for choosing y1. Immediately after the choice, the cache contains four positions, not five: choosing an ID does not compute its hidden states. Feeding y1 back creates its K/V and permits choosing y2; the cache now has five positions. Feeding y2 back permits choosing y3; the cache has six. The lab checks this invariant at runtime: after selecting O outputs, retained length is P+O−1. A conservative serving capacity plan may reserve P+O positions, but should say that it is a budget rather than a tensor observation.

Likewise, a 128-output answer has 127 post-first gaps. If their arithmetic mean is 22 ms, their total is exactly 127×22=2,794 ms. Adding the actual first-token interval gives a larger completion interval. If 22 ms were only the median gap, multiplication would not reconstruct the total. A small set of slow gaps could leave the median unchanged while making completion much later. The lab's mean decode step interval is total decode wall time divided by O−1; it is not a distribution of individually timestamped token events, and it is not a client streaming ITL measurement.

The serial token axis

At decode step t, the model cannot choose token t+1 until logits for t exist. Work within a step can be massively parallel, and multiple sequences can be batched, but the output-token dependency remains. Prefill instead processes many known prompt positions together. Thus long input with short output and short input with long output can stress different parts of the same GPU. FlashAttention is a concrete example of optimizing attention through IO-aware tiling; it is not a claim that all service delay lives inside that kernel.

Shape is a hypothesis, duration is evidence

For a fixed model, prefill with more positions often increases matrix sizes and attention work, while decode adds one new position at a time and reads retained state. That suggests a qualitative prediction: increasing prompt length should primarily enlarge prefill and KV; increasing output length should multiply decode steps. It does not predict a particular wall-time ratio. Fixed launch overhead, kernel selection, sequence padding, cache behavior, compilation and measurement noise all affect the observed ratio. In the pinned five-trial table, some decode medians even decrease with longer input. The right response is to preserve raw trials and investigate, not smooth them into a monotonic curve.

Ask what is held constant before comparing: model revision, tokenizer, precision, batch, generated-token count, warmup state and synchronization. A timing measured without synchronizing a CUDA device may record only kernel dispatch on the CPU, not completed device work. Conversely, a profiler can perturb execution and make an otherwise good timing unrepresentative. The course's phase exercise records synchronized measurements; its local profiler artifact is a learning tool, not a public production-latency claim.

A pair-count is not a wall-time model

In a simplified dense causal attention calculation, a prompt of length P has on the order of P²/2 valid query–key pairs. Increasing P from 128 to 4,096 multiplies that attention pair count by roughly (4096/128)² = 1024. Yet the v2 1.5B/O32 prefill medians change from 22.3 to 163.7 ms, about 7.34× rather than 1024×. There is no paradox. Attention scores are one component of a transformer layer; projections and feed-forward work scale differently, fixed overheads matter, the GPU can exploit larger shapes differently, and IO-aware kernels avoid materializing the full score matrix in slow memory. Pair count is a mathematical work term, not a prediction of service milliseconds. Preserve the five-trial ranges and the unresolved identical-shape variation described below; 7.34× is an observation of this run, not a law.

The first output is selected from the prefill logits, so O generated outputs require D=O−1 subsequent decode forwards. At decode query j=1…D, the current input token adds its own K/V and attends P+j positions. Summing per-head query–key pairs gives DP+D(D+1)/2. With O=256, D=255: a 512-token prompt gives 255×512+255×256/2=163,200 pairs; a 4,096-token prompt gives 1,077,120, exactly 6.6× as many. These are decode-only pair counts per head, not prefill work, HBM bytes, or a 6.6× wall-time prediction. Changing the definition of a “step” without changing the summation is an off-by-one error, not a harmless notation choice.

Batching changes the effective machine problem

At batch one, each decode step produces one new token for one sequence. If several sequences advance together, the same model weights may be used for multiple token computations in the iteration. That can increase useful work per weight byte moved, but it also raises live KV demand and may lengthen an individual request's decode cadence. “Higher aggregate tokens/s” and “better per-user latency” are distinct outcomes. Imagine four copies of our sequence-completion request advancing in four lanes: each iteration can choose four IDs, but no lane skips its dependency on its previous ID. That picture explains the counting; the measurements below use repeated synthetic IDs, not four measured natural-language requests.

Reconstruct the arithmetic: 31 / 0.8392 ≈ 36.9 tok/s; 124 / 0.7991 ≈ 155.2 tok/s. For one lane, divide milliseconds by 31, not by 124: 839.2 / 31 ≈ 27.1 ms versus 799.1 / 31 ≈ 25.8 ms. Aggregate median rate rises about 4.2×, but one sequence's average cadence does not improve 4.2×. The substantial overlap in the five-trial ranges also prevents a stable scaling claim. These are ratios of the reported middle observations, not a promise for your GPU or a distribution of individually timed token gaps.

Sequence lengths also differ inside a batch. A long prompt may demand a large prefill while short decode steps are ongoing; admitting it can interfere with active streams. Separating prefill and decode across resources is one architectural response studied by DistServe, but that paper is not evidence that our one-GPU course run uses disaggregated serving. The immediate diagnostic lesson is to record phase and request shape, then test the actual scheduling policy under the intended workload. A batch size copied from a paper or a benchmark with different output lengths is not a capacity plan.

Count live state before blaming compute

The pinned Qwen2.5-3B configuration has 36 layers, two KV heads, and head dimension 128. At two bytes per element, logical KV payload per token is 2 (K and V) × 36 × 2 × 128 × 2 = 36,864 bytes = 36 KiB. A worked population of 64 sequences with 512 prompt and 256 generated tokens each gives a conservative budget of 64 × 768 = 49,152 token positions, or 1.6875 GiB of logical KV payload.

That is not the process-memory reading. Weights, temporary activations, allocator reservation, graph buffers, block rounding, and fragmentation remain outside the formula. Nor is every token’s cache necessarily resident for the full request lifetime. The calculation is useful as a falsifiable lower-level component, not as an admission guarantee. Change the KV-head count in the KV budget explorer and observe the linear change while remembering these omissions.

Derive the units before reaching for a GPU monitor

One token contributes a key vector and a value vector to each transformer layer. With grouped-query attention, the number of KV heads—not the number of query heads—sets this particular payload. The pinned Qwen2.5-3B config provides 36 layers, two KV heads and 128 values per head. At FP16, each value is two bytes. Multiply 2 arrays × 36 layers × 2 KV heads × 128 values/head × 2 bytes/value. The head and value units cancel, leaving 36,864 bytes/token. Dividing by 1,024 gives 36 KiB/token. If someone substitutes decimal “36 KB,” the numerical error is small here but the habit becomes dangerous in a tight capacity budget.

For the worked 64-request population, each request budgets 512 input plus 256 generated positions. This is a conservative capacity allowance, not the exact final tensor length in the lab: the last chosen output has not been fed back, so the lab retains 512+256−1=767 positions per sequence. The budget reserves 768 positions per request and 64 × 768 = 49,152 across requests. Then 49,152 × 36,864 = 1,811,939,328 bytes, and division by 2³⁰ gives 1.6875 GiB. Notice how the units and population are explicit: logical payload for this hypothetical collection of live tokens. We did not measure a 64-client Qwen2.5-3B service in this calculation.

A full memory ledger has more than one line

For an idealized three-billion-parameter FP16 model, raw weights alone are about 3 × 10⁹ × 2 = 6 × 10⁹ bytes, or roughly 5.59 GiB. “Three billion” is rounded, and real checkpoint/module composition matters, so this is a back-of-envelope term, not a measured Qwen file size. At a particular instant, disjoint live tensors such as weights, KV, temporary activations and workspace contribute to allocated memory. Those allocated bytes are already inside the allocator's reserved pool; only its unused portion is additional pool space. Device-total accounting also includes allocations outside that pool and other processes. Do not add allocated to reserved, or assume independently observed maxima describe the same instant. A 16-GiB card showing 8 GiB apparently free at one instant is not proof that 8 GiB of additional live KV can be safely admitted: allocation granularity, peaks and concurrent work remain.

Now switch explicitly from the 3B transfer calculation to the measured 1.5B model. Its 28 layers, two KV heads and 128 values per head give 2 × 28 × 2 × 128 × 2 = 28,672 bytes = 28 KiB/token at FP16. The required matrix records that value from the actual configuration. The 3B figure of 36 KiB/token would be the wrong coefficient for this run.

Why can KV grow by (4223−4127) × 28 / 1024 = 2.625 MiB while the phase peak stays flat? The maximum occurs during a different live-object combination: in these rows, the recorded prefill peak already equals the overall peak. Extra final KV does not exceed that earlier maximum. We have not measured which particular temporary tensor caused the peak; this evidence establishes the timing boundary, not a complete allocation attribution. A peak is a maximum over time, not the size of the final cache.

Allocated bytes and reserved bytes also answer different questions: live allocated tensors are inside the allocator's reserved pool, not an extra pool to add on top. In these P4096 rows, the reserved peak is 3,586 MiB; adding it to 3,349.34 MiB would double-count live allocations. A between-cell device sample after releasing models was at most 333 MiB in the v2 rehearsal, far below the in-process peak. It cannot bound live execution. An admission rule needs worst credible live state, other device users and measured headroom, not an idle snapshot.

Weight compression and KV are separate levers

Quantizing weights may reduce the weight term but leave FP16 KV unchanged. Quantizing KV may change a different term and has its own quality and kernel constraints. Changing attention implementation can reduce temporary IO without changing the logical persistent KV formula. Increasing batch or sequence length can make weights a smaller share of total live memory even though the model file is identical. This distinction is the bridge to Chapter 03: “the model fits” is not a single yes/no property of a filename. It depends on the complete serving workload and the implementation that actually runs.

A roof is not a latency prediction

In an illustrative machine model with 60 TFLOP/s compute and 600 GB/s bandwidth, the ridge point is 60,000 / 600 = 100 FLOP/byte. A workload at 20 FLOP/byte has a bandwidth ceiling of 600 × 20 / 1,000 = 12 TFLOP/s, below the compute roof. Moving a point by changing reuse or precision is meaningful only if the real implementation changes bytes or operations. Launch gaps, queueing, kernel inefficiency, and memory capacity are absent from the simple roof. The original Roofline model explains the upper-bound interpretation; the explorer lets you vary intensity.

Derive the roof; then say what it cannot predict

Arithmetic intensity I is operations divided by bytes moved at a chosen memory boundary. If peak compute is C and sustainable bandwidth at that boundary is B, the simple attainable upper bound is min(C, B × I). The example uses decimal units consistently: 60 TFLOP/s = 60,000 GFLOP/s, 600 GB/s, so C/B = 100 FLOP/byte. Below that ridge, doubling useful arithmetic intensity could raise the bandwidth ceiling; above it, the compute ceiling dominates in this model. Neither statement says a real kernel will reach the roof.

Suppose the operation count for one illustrative kernel is one tera-operation and its intensity is 20 FLOP/byte. The simple roof would give a lower bound near 1 / 12 s ≈ 83 ms of idealized device execution. The measured service might take far longer because it waits in a queue, launches many kernels, moves data at a different level, samples tokens serially, or simply runs inefficiently. If a profiler says the kernel occupies only 10% of service wall time, a 2× kernel speed-up can reduce whole-service time by at most roughly 5% under an Amdahl-style fixed-remainder approximation. This is an illustrative calculation, not a measurement of the course kernel. It teaches where not to spend the next week.

Derive a decode hypothesis, then list the missing bytes

Let N_w be an approximate active dense-weight count and b_w the bytes per stored weight. For one decode row, the dense-weight estimate is about 2N_w FLOPs when a multiply and an addition count as two operations. If those weights stream once through the chosen memory boundary, traffic is about N_w b_w bytes. Their ratio is 2/b_w FLOP/byte, approximately one at FP16. For B token rows ideally sharing that weight sweep, the ratio becomes 2B/b_w. Batch one, four and 32 then give one, four and 32 FLOP/byte. This is a useful first-order hypothesis for weight reuse; it is not measured total-kernel intensity.

The cancellation of N_w in the ratio is instructive. A larger model still does more work and moves more absolute bytes; the ratio alone does not determine its latency. At the hypothetical 600 GB/s boundary, streaming 3×10⁹ two-byte weights takes at least 10 ms if that traffic assumption holds. But cache hits reduce transferred weight bytes, while K/V, activations, normalization and attention add other work. Kernel shapes can change achieved rates. A long-context decoder can therefore leave the simple weight-only regime even with the same model and batch. Name the model's omissions before using it to select an optimization.

Now interpret a batch experiment correctly. In a constructed example, B1 takes 1.0 s for 31 post-first steps; B4 takes 1.5 s for the same steps per sequence. Aggregate decode rate increases from 31/1.0=31 to 4×31/1.5≈82.7 tokens/s, while mean per-sequence cadence worsens from 32.3 to 48.4 ms. Neither result contradicts the other. The lab uses identical-length rows and a static batch, with no scheduler, queue, arrivals or padding imbalance. It isolates a shape/reuse comparison; it cannot establish a serving concurrency limit or predict p95 TTFT for mixed real requests.

Efficiency is not the same as a good schedule

A prefill that fills the GPU efficiently can still delay active decoders. Consider a deliberately simplified serial device schedule: three decode steps of 10 ms each would finish in 30 ms, but an 80 ms prompt operation inserted after the first step stretches that interval to 110 ms. “Bytes moved” needs an address

HBM traffic, cache traffic and host-device transfers are different boundaries with different bandwidths. A tiling method can reduce HBM reads by reusing values in faster on-chip storage without changing mathematical FLOPs. FlashAttention is an IO-aware attention design; its benefit must be evaluated at the actual sequence shape and implementation path, not inferred from the name of an installed package. A decode kernel that repeatedly reads model weights can have different reuse when many sequences share an iteration batch. The operational intensity you plot should therefore be calculated or measured for the actual kernel and boundary, not borrowed from an unrelated prefill benchmark.

Capacity is another separate constraint. Even a compute-efficient kernel cannot launch if the current live request state does not fit. And a service can be slow because its GPU is idle between launches, in which case both compute and memory roofs are generous but irrelevant. A productive prediction names its possible falsifiers: if the device timeline has large launch gaps, the roofline is not the first answer; if HBM bandwidth is far below its relevant ceiling while SMs are also underused, look for shape, occupancy or launch issues before pronouncing the workload “memory-bound.”

Follow a byte before optimizing an operation

Device memory is relatively large and distant from arithmetic units; on-chip storage is smaller and can support much greater reuse. CPU DRAM adds another location and a host-device transfer boundary. HBM and GDDR are different implementations of device memory, not synonyms for all GPU storage. L2 is shared cache, while shared memory and registers have more local ownership and limited capacity. The exact L1/shared-memory organization varies by architecture. The diagram is a reasoning map rather than a mandatory physical route for every load. Ask whether the value is already available near the consumer, whether many threads can reuse it, and whether bringing more state close reduces the number of resident thread blocks.

A tile is a block of a larger operation selected to fit and reuse data locally. If a weight tile is fetched once and used for several token rows before eviction, useful FLOPs per transferred byte increase. Merely enlarging an allocation does not create this reuse. Register pressure or shared-memory use can also reduce occupancy—the amount of simultaneously resident work—and sometimes expose latency that a smaller tile hid. “Use more on-chip memory” is therefore a design trade-off, not a universal prescription. The CUDA Best Practices Guide describes the underlying memory/access mechanisms; the course asks you to connect them to an actual shape and an observable consequence.

Coalescing concerns how nearby threads' memory requests combine into transactions. Four neighboring useful elements can fall within a compact footprint, whereas four scattered elements can require fetching several segments. Both programs may perform the same arithmetic and use the same logical tensor size, yet transfer different amounts of data. The drawing intentionally does not assert a universal transaction size; alignment, dtype, architecture and cache behavior matter. Effective bandwidth based on useful payload is a useful application metric, but a hardware traffic counter may see additional fetched bytes. A discrepancy between them is a reason to inspect access patterns, not to silently change the denominator.

A fusion example with bytes, not marketing language

Take three elementwise functions over N values. An unfused implementation reads input X, writes intermediate A, reads A, writes intermediate B, reads B and writes output Y. Ignoring cache effects, this is six transfers of N elements. If one fused kernel keeps the intermediates local, it may need only the initial read and final write: two transfers. At N=1,048,576 FP16 elements, the useful payload is 12 MiB versus 4 MiB. The mathematical result and operation count can be essentially unchanged while the data movement and launch count shrink.

That accounting does not promise a threefold time reduction. Perhaps the original intermediates already hit in cache; perhaps the fused kernel uses too many registers; perhaps arithmetic dominates; perhaps launch savings matter more than traffic. A valid experiment preserves the function, shape, precision and output check, then measures both implementations under one timing boundary. In a production service, it must also show that this region matters to the user-visible objective. Fusion describes removing boundaries, not removing required dependencies.

Why FlashAttention changes IO without removing attention

Dense causal attention conceptually combines a query with allowed keys, normalizes scores and uses the resulting weights to aggregate values. A straightforward implementation can materialize a large score matrix in device memory between those steps. An IO-aware tiled algorithm instead processes blocks and maintains running normalization/output state, avoiding that full intermediate materialization. The causal triangular picture still explains which positions may interact; it is not the allocation plan. The original FlashAttention paper makes IO movement central to the algorithm rather than treating memory as an afterthought.

“Exact attention” distinguishes this approach from an approximate attention rule, not from all floating-point rounding differences. It does not eliminate the model's persistent KV state, the cost of dense projections or the dependence between generated tokens. Also distinguish an API request from the kernel that actually ran: asking Transformers for sdpa does not prove a specific FlashAttention implementation was selected. PyTorch dispatch depends on hardware, dtype, mask and shape. The lab's focused traces provide evidence about the actual operator path for the two captured cases; another shape may select something else. This is why installing a package and showing its version is not a performance result.

Capacity, bandwidth, latency—and allocator behavior

A capacity bottleneck means the required live objects cannot coexist in available memory, or cannot do so with safe headroom. It appears as admission rejection, allocation failure, paging or a runtime's lower-than-expected active-sequence limit. A bandwidth bottleneck means useful work is limited by the rate of moving bytes at a chosen level; the program can fit perfectly and still spend most device time waiting for data. A latency bottleneck concerns dependent fetches whose waits are not hidden by enough independent work; fitting the tensors and having high aggregate bandwidth do not remove those dependencies. A separate fragmentation or reservation problem means logical payload calculations understate allocator behavior and reusable pools. Calling all these mechanisms “VRAM bottleneck” conceals the remedy. Weight quantization could improve capacity but slow a kernel; better batching could improve weight reuse but raise KV capacity pressure; changing allocator settings could alter reservation without changing the mathematical work.

Use the right observation for each claim. For capacity, collect peak allocated and reserved memory under the target live-token mix and count failures. For bandwidth, profile actual traffic and execution at the memory level in question and compare with a relevant achieved bandwidth—not only a vendor peak. For fragmentation, inspect allocation patterns over repeated arrivals/cancellations and the runtime's block management. A one-number GPU dashboard cannot identify which mechanism is responsible. This distinction sets up the quantization trade-off in Chapter 03: smaller representation is one possible lever, not a diagnosis by itself.

Why a wall clock can lie to a CUDA beginner

GPU calls are often asynchronous from the CPU's perspective. Timing only the Python call that launches work can measure dispatch overhead while kernels continue after the stopwatch stops. The usual teaching protocol warms the path, synchronizes before starting, launches the work, synchronizes before stopping and then repeats. This does not make the measurement perfect: synchronization changes overlap and a profiler changes execution. It makes the defined interval inspectable. Keep the request-level HTTP clock separate from the phase benchmark, and do not add independently measured medians as if they were one observed transaction.

Return to the exact prompt rather than an unlabeled stopwatch. Its per-step replay records the following two intervals around the same forward/selection. The wall interval includes completion synchronization; CUDA events mark an interval on the device stream, not a sum of kernel durations. Decoding text, printing the row, loading the model and chat tokenization are outside the timed forward. Per-step barriers and inspection make this a different observation protocol from the whole-loop v2 decode timer.

These are actual individual observations, not medians, p95 or a warm-path target. A similar wall/event value does not prove an absence of host launch gaps: a gap may occur between the two events as well. Use a time-ordered trace to attribute time to kernels. The prompt replay record explains warmup, stop conditions and instrumentation.

In the instructor rehearsal, one GPU process ran at a time under a 24-GiB memory scope, with immutable model snapshots already cached and offline mode enabled. These precautions avoid downloading on every clean run and bound host risk; they do not turn a five-trial batch-one phase timing into a fleet-level latency distribution. The record includes source revision, model revisions, versions, timestamps and per-trial arrays so a reader can scrutinize the result instead of accepting a slide label.

Five trials can start a question, not finish one

A median of five observations is robust to one extreme value compared with a mean, but it still has little information about tails. If the values were 25, 27, 28, 29 and 70 ms, the median would be 28 ms and the unusual 70 ms would remain operationally interesting. The published arrays let the reader inspect spread and shape order rather than accepting a lone median. For a confirmatory experiment, specify a warmup rule, interleave or randomize shapes to reduce order bias, collect enough independent runs for the decision's uncertainty, and report failures and memory peaks beside timing. The required sample size depends on the effect size and variation; an arbitrary “three runs” ritual is not a confidence argument.

Do not add median prefill from one set of runs to median decode from another and label the sum an observed end-to-end request. Both medians might come from different trials, and the real API includes tokenization, queueing, transport and post-processing. If you need an end-to-end claim, time actual complete requests under a pinned interface. If you need a phase explanation, use phase timers and profiler traces. The two measurements should reconcile qualitatively, but they answer different questions. This is the same evidence discipline established in Chapter 01: a number carries its observer and denominator with it.

Choose the next instrument

First isolate load, warmup, prefill, decode, and service waiting. If GPU kernels occupy only a small share of wall time, a detailed kernel profile may be the wrong first instrument; inspect CPU launch gaps and request traces. If one kernel dominates device time, inspect its shapes and memory behavior. PyTorch’s profiler can capture operators and allocations; NVIDIA’s Nsight Systems locates timeline gaps, while Nsight Compute interrogates a selected kernel. Profiling perturbs timing: validate any improvement again without instrumentation.

What a kernel profile can and cannot say

A kernel profile can reveal occupancy, memory transactions, launch configuration and instruction mix for a selected invocation. It cannot by itself tell whether the user waited in a queue for two seconds or whether the proxy buffered output. A system timeline can reveal that the GPU sat idle between decode launches, but it may not say which application decision caused the gap. A request trace can show long admission wait without explaining the later matrix-multiply efficiency. These are complementary views of a causal chain, not competing brands of one universal profiler.

For an illustrative case, suppose a request takes 800 ms end-to-end, of which 500 ms is queue wait, 200 ms is engine execution and 100 ms is transport/validation. Even eliminating half the engine work saves only 100 ms: end-to-end falls to 700 ms, a 12.5% improvement. If the objective is p95 TTFT under load, admission or capacity policy may have greater leverage. Change the numbers and the decision can reverse. The arithmetic is a budget exercise, not a claim about our measured server. This is why the student's analysis should name the chosen latency population and decompose it before announcing an optimization.

Make the next measurement discriminate hypotheses

Suppose a trace shows long decode time for a small model. Hypothesis A says repeated weight reads at batch one make the path bandwidth-sensitive. Hypothesis B says CPU launch gaps dominate. A kernel-only optimization would help A but barely touch B. Test A by comparing measured device occupancy, memory traffic and kernel duration across batch shapes; test B by checking the system timeline's gaps and CPU thread activity. Before running either tool, predict the contrasting signatures. If both signatures appear, quantify their wall-time shares before deciding which to fix first.

The pinned 1.5B phase run cannot adjudicate these two hypotheses alone. It has timing arrays and a local teaching trace, not a published, versioned per-kernel analysis with enough repeats for a production claim. A careful chapter should say “the phase data motivate profiling,” not “the phase data prove HBM saturation.” That boundary is intellectually productive: it tells students exactly which experiment they would run next.

What v2 changes—and why it is a new protocol

Version 2 requests only last-position logits during prompt processing. In the pinned model implementation, logits_to_keep=1 avoids projecting every prompt position into the full vocabulary when only the last distribution is needed to choose the next output. At P=4,096 and vocabulary size 151,936, a full two-byte logits tensor alone would contain 4096×151936×2=1,244,659,712 bytes, about 1.16 GiB. The last-position slice needs 303,872 bytes, about 297 KiB. This is tensor accounting for the vocabulary output, not a measured total-memory saving; the full prompt still passes through the decoder and creates KV. The pinned Transformers source makes this argument inspectable.

Each actual shape receives a full warmup path outside the trial timer. Shapes are shuffled within each of five rounds under a fixed order seed, limiting simple “all short cases first, all long cases last” bias. Models remain sequential to bound resource use. The caching allocator is not emptied between trials; freeing unused pools is a cleanup operation between models, not an invisible cold-start condition applied to every observation. Both synchronized wall and CUDA-event intervals are recorded. Because a Python-driven decode loop can leave gaps between launches, neither interval should be relabeled “sum of kernel execution time.” A separate kernel timeline is needed for that attribution.

These changes alter the experiment. The historical v1 medians remain useful for teaching uncertainty and phase interpretation, but comparing v1 with v2 cannot isolate the effect of last-position logits, warmup, ordering or any other single change. A causal speedup claim would require a matched A/B experiment changing one declared factor under a shared protocol. The course does not need another uncontrolled performance headline; it needs an experiment whose evidence can survive questions. Vocabulary you should be able to explain without a slide

Residual stream / pre-norm
The running hidden representation updated by elementwise addition / a block ordering that normalizes each branch input before attention or MLP, with an unchanged bypass feeding the addition.
RMSNorm / epsilon / gain
Root-mean-square normalization over one row's features / a small positive stabilizer inside the square root / learned per-feature scaling. The operation does not average tokens together.
Feature axis / head axis / position axis
Coordinates of one representation / independent query projections or shared KV groups / locations in a sequence. Reshaping features into heads does not create more sequence positions.
Bias / projection
A learned additive output-coordinate vector / a learned linear mapping between feature spaces. A shared bias is added to each position; it is not a cache or attention mask.
RoPE / causal mask
Rotary position embedding rotates paired Q/K coordinates / a rule preventing a query from using future positions. Position information and future-access restriction solve different problems.
Softmax / logits / greedy
A normalized exponential distribution along a declared axis / unnormalized scores / choosing the highest score. Attention softmax spans source positions; vocabulary softmax spans possible output IDs.
MLP / SiLU / SwiGLU
A multi-layer perceptron operating per position / the function x×sigmoid(x) / a gated MLP that multiplies a SiLU branch with a second linear branch before projecting down.
Concatenation / elementwise product
Joining head-derived feature coordinates into one wider row / multiplying matching coordinates. Neither operation should be confused with matrix multiplication or summing across positions.
Autoregressive dependency
The next output choice uses earlier chosen tokens; parallel arithmetic within a step does not remove that chain.
Prefill / decode
Processing known prompt positions and selecting the first output, versus later forwards that advance each live sequence by one new position.
GEMM / GEMV
General matrix–matrix / matrix–vector multiplication. The token-row dimension helps explain why prefill and small-batch decode may use different kernels.
Q, K, V
Query, key and value projections in attention. Retained keys/values let later queries reuse already-computed history.
MHA / GQA / MQA
Multi-head, grouped-query and multi-query attention: respectively equal query/KV head counts, groups of queries sharing K/V, and all queries sharing one KV head.
HBM / GDDR / DRAM
High-bandwidth memory and graphics double-data-rate memory are device-memory technologies; dynamic RAM also underlies host memory. Do not apply one boundary's bandwidth to another.
FLOP / FLOP/s
Floating-point work / work rate. “GFLOP” alone is not a throughput unit. State whether a multiply-add counts as two operations.
Arithmetic intensity / ridge
Work per transferred byte at a declared boundary / intensity where compute and bandwidth roofs intersect.
Allocated / reserved / peak
Live allocator tensor bytes / the allocator's pool including reusable space / the maximum of a specified counter since reset. These are not three disjoint memory terms.
Warmup / synchronization
Excluded setup executions / an explicit completion boundary. A warm path can still vary; a barrier changes the interval being measured.
SDPA
Scaled dot-product attention API/path. The requested API name does not uniquely identify the kernel selected for every shape.
Trace / profile
A time-ordered event record / attributed performance information. Categories and scope matter more than the file's name.

Questions that often reveal a missing boundary

“If batch four is faster than expected, did we beat the bandwidth law?” No law predicts your wall time from the weight-only approximation. Cache reuse, launch overhead, shapes and experimental variation can all matter. Preserve the raw trials and investigate the specific claimed mechanism. “Why do two identical prefill shapes have different medians when only requested output length changed?” Prefill does not know the future loop count in this lab's forward call. Differences can arise from ordering, runtime/host scheduling, allocator state and variation; future output length is not a causal explanation by itself. This is a particularly useful internal consistency check.

“Why not just synchronize after every token?” That would define a different decode loop and can change overlap and launch cadence. It may be useful for a separate token-level investigation, but cannot silently replace the current whole-decode timer. “Does a flat reserved-memory line prove a leak?” Not by itself: the allocator may retain reusable pool space while live allocated bytes recover. Check tensor ownership and repeated live-state growth. “Can I infer KV bytes from the model's advertised parameter count?” No; use layers, KV heads, head dimension and cache dtype. “Can the instructor's table replace my GPU run?” No; it is a reference for reasoning and artifact structure, not your submitted experiment.
