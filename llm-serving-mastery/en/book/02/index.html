Inference bottlenecks: KV cache, memory hierarchy, autoregression

Phase-specific tensor shapes, memory traffic, roofline reasoning, KV accounting, and profiler evidence.

A 32-fold input change that is not a 32-fold time change

Start with an observation, not a slogan. In the pinned RTX 5070 Ti instructor run, Qwen2.5-1.5B at batch one with a 32-token output had median prefill of 27.8 ms for 128 input tokens and 185.6 ms for 4,096 input tokens. The input grew by 4096/128 = 32, but median prefill grew by about 185.6/27.8 = 6.68. A separate pair with a 128-token output took roughly 4.45 and 4.39 seconds in decode, despite the same 32-fold input-length difference. Those numbers are not a universal scaling law; five trials per phase and shape are too few for that. They are a good puzzle: if one global “tokens per second” number explained inference, these two phase responses would be hard to describe.

The answer begins with the dependency graph. The prompt is known up front. Output tokens are not. Inside each GPU operation there may be enormous parallelism, but the next output token still depends on the previous one. That serial axis changes how much work can be batched and reused. It also changes what a profiler snapshot means: a kernel may be efficient and still sit inside a service dominated by sequential steps, launches, waiting, or data movement.

From text to a tensor: what actually enters the GPU?

Imagine a document assistant receiving a question and a long retrieved passage. Before the decoder sees anything, a chat template may add role delimiters and control tokens, and a tokenizer maps the resulting byte/text sequence to integer IDs. A token can represent part of a word, punctuation, whitespace or a special marker. Counting words is therefore not an acceptable substitute for measuring tokenized length. The lab deliberately bypasses a realistic chat workload: it repeats a short token-ID pattern to produce exactly 128 or 4,096 positions. That makes the shape experiment reproducible, but it does not test retrieval quality, useful answer length or semantic diversity.

The input tensor has a batch axis and a sequence-position axis, conventionally written [B,S]. Its elements are integer indices, not semantic vectors. An embedding table with vocabulary size V and hidden width d selects one floating-point vector per ID, creating [B,S,d]. For an illustrative B=2,S=128,d=896, that is 2×128×896=229,376 values. At two bytes per value it occupies 458,752 bytes, or 448 KiB, for this tensor alone. It does not count the embedding table, all later activations or KV state. The same symbol “B” sometimes means bytes in systems writing and batch size in model equations; this chapter writes units explicitly to keep those meanings separate.

One decoder block: projections, mixing and a residual path

The hidden representation entering a block is transformed by normalization, attention and a feed-forward network, with residual connections preserving a path from the block input to its output. In the pinned Qwen2 family, the model's own implementation and configuration—not a generic transformer cartoon—determine normalization, rotary position handling, projection widths and grouped-query heads. For the performance argument, three questions matter at each operation: what are the dimensions, which values must be fetched, and which earlier result must already exist? A dense projection multiplies token rows by a weight matrix; attention mixes information across allowed positions; the feed-forward portion performs more per-position dense work. These are different sources of arithmetic and traffic.

Write a projection as [M,d] × [d,d_out] → [M,d_out]. Flattening batch and newly processed positions yields M=B×S in a full prefill. With eight sequences of 512 prompt positions, M=4,096. In the next ordinary decode iteration, the same eight sequences contribute one new position each, so M=8. The retained 512-position history belongs in attention's K/V axis; it does not turn the new-query projection back into a 4,096-row projection. This is the concrete meaning of “same model, different workload.” A model filename alone leaves out the most important dimensions of the kernel problem.

After the final block, a vocabulary projection creates logits—unnormalized scores, one per vocabulary entry. Softmax converts them to a probability distribution; greedy decoding simply selects the largest score, whereas sampling uses a declared stochastic rule. For toy scores [2,1,0], softmax is approximately [0.665,0.245,0.090], and greedy selection chooses the first item. These toy values do not describe Qwen's real output. Once that token ID is chosen, it becomes an input to the next forward. This data dependence is the serial link; it is not a claim that one token requires only one operation or that the GPU lacks parallel work inside that forward.

The first token is not a decode forward

Keep a tiny ledger before writing a timer. With prompt IDs x1…x4, prefill computes their K/V and logits for choosing y1. Immediately after the choice, the cache contains four positions, not five: choosing an ID does not compute its hidden states. Feeding y1 back creates its K/V and permits choosing y2; the cache now has five positions. Feeding y2 back permits choosing y3; the cache has six. The lab checks this invariant at runtime: after selecting O outputs, retained length is P+O−1. A conservative serving capacity plan may reserve P+O positions, but should say that it is a budget rather than a tensor observation.

Likewise, a 128-output answer has 127 post-first gaps. If their arithmetic mean is 22 ms, their total is exactly 127×22=2,794 ms. Adding the actual first-token interval gives a larger completion interval. If 22 ms were only the median gap, multiplication would not reconstruct the total. A small set of slow gaps could leave the median unchanged while making completion much later. The lab's mean decode step interval is total decode wall time divided by O−1; it is not a distribution of individually timestamped token events, and it is not a client streaming ITL measurement.

The serial token axis

At decode step t, the model cannot choose token t+1 until logits for t exist. Work within a step can be massively parallel, and multiple sequences can be batched, but the output-token dependency remains. Prefill instead processes many known prompt positions together. Thus long input with short output and short input with long output can stress different parts of the same GPU. FlashAttention is a concrete example of optimizing attention through IO-aware tiling; it is not a claim that all service delay lives inside that kernel.

Shape is a hypothesis, duration is evidence

For a fixed model, prefill with more positions often increases matrix sizes and attention work, while decode adds one new position at a time and reads retained state. That suggests a qualitative prediction: increasing prompt length should primarily enlarge prefill and KV; increasing output length should multiply decode steps. It does not predict a particular wall-time ratio. Fixed launch overhead, kernel selection, sequence padding, cache behavior, compilation and measurement noise all affect the observed ratio. In the pinned five-trial table, some decode medians even decrease with longer input. The right response is to preserve raw trials and investigate, not smooth them into a monotonic curve.

Ask what is held constant before comparing: model revision, tokenizer, precision, batch, generated-token count, warmup state and synchronization. A timing measured without synchronizing a CUDA device may record only kernel dispatch on the CPU, not completed device work. Conversely, a profiler can perturb execution and make an otherwise good timing unrepresentative. The course's phase exercise records synchronized measurements; its local profiler artifact is a learning tool, not a public production-latency claim.

A pair-count is not a wall-time model

In a simplified dense causal attention calculation, a prompt of length P has on the order of P²/2 valid query–key pairs. Increasing P from 128 to 4,096 multiplies that attention pair count by roughly (4096/128)² = 1024. Yet the measured prefill medians above changed by only about 6.68×. There is no paradox. Attention scores are one component of a transformer layer; projections and feed-forward work scale differently, fixed overheads matter, the GPU can exploit larger shapes differently, and IO-aware kernels avoid materializing the full score matrix in slow memory. Pair count is a mathematical work term, not a prediction of service milliseconds.

The first output is selected from the prefill logits, so O generated outputs require D=O−1 subsequent decode forwards. At decode query j=1…D, the current input token adds its own K/V and attends P+j positions. Summing per-head query–key pairs gives DP+D(D+1)/2. With O=256, D=255: a 512-token prompt gives 255×512+255×256/2=163,200 pairs; a 4,096-token prompt gives 1,077,120, exactly 6.6× as many. These are decode-only pair counts per head, not prefill work, HBM bytes, or a 6.6× wall-time prediction. Changing the definition of a “step” without changing the summation is an off-by-one error, not a harmless notation choice.

Batching changes the effective machine problem

At batch one, each decode step produces one new token for one sequence. If several sequences advance together, the same model weights may be used for multiple token computations in the iteration. That can increase useful work per weight byte moved, but it also raises live KV demand and may lengthen an individual request's decode cadence. “Higher aggregate tokens/s” and “better per-user latency” are distinct outcomes. A scheduler must trade first-token wait, fairness, ongoing stream smoothness and memory headroom. The single-request phase table cannot tell us where a multi-request optimum lies; it intentionally isolates component behavior before queueing and scheduling are added back.

Sequence lengths also differ inside a batch. A long prompt may demand a large prefill while short decode steps are ongoing; admitting it can interfere with active streams. Separating prefill and decode across resources is one architectural response studied by DistServe, but that paper is not evidence that our one-GPU course run uses disaggregated serving. The immediate diagnostic lesson is to record phase and request shape, then test the actual scheduling policy under the intended workload. A batch size copied from a paper or a benchmark with different output lengths is not a capacity plan.

Count live state before blaming compute

The pinned Qwen2.5-3B configuration has 36 layers, two KV heads, and head dimension 128. At two bytes per element, logical KV payload per token is 2 (K and V) × 36 × 2 × 128 × 2 = 36,864 bytes = 36 KiB. A worked population of 64 sequences with 512 prompt and 256 generated tokens each gives a conservative budget of 64 × 768 = 49,152 token positions, or 1.6875 GiB of logical KV payload.

That is not the process-memory reading. Weights, temporary activations, allocator reservation, graph buffers, block rounding, and fragmentation remain outside the formula. Nor is every token’s cache necessarily resident for the full request lifetime. The calculation is useful as a falsifiable lower-level component, not as an admission guarantee. Change the KV-head count in the KV budget explorer and observe the linear change while remembering these omissions.

Derive the units before reaching for a GPU monitor

One token contributes a key vector and a value vector to each transformer layer. With grouped-query attention, the number of KV heads—not the number of query heads—sets this particular payload. The pinned Qwen2.5-3B config provides 36 layers, two KV heads and 128 values per head. At FP16, each value is two bytes. Multiply 2 arrays × 36 layers × 2 KV heads × 128 values/head × 2 bytes/value. The head and value units cancel, leaving 36,864 bytes/token. Dividing by 1,024 gives 36 KiB/token. If someone substitutes decimal “36 KB,” the numerical error is small here but the habit becomes dangerous in a tight capacity budget.

For the worked 64-request population, each request budgets 512 input plus 256 generated positions. This is a conservative capacity allowance, not the exact final tensor length in the lab: the last chosen output has not been fed back, so the lab retains 512+256−1=767 positions per sequence. That is 768 live tokens per request and 64 × 768 = 49,152 across requests. Then 49,152 × 36,864 = 1,811,939,328 bytes, and division by 2³⁰ gives 1.6875 GiB. Notice how the units and population are explicit: logical payload for this hypothetical collection of live tokens. We did not measure a 64-client Qwen2.5-3B service in this calculation.

A full memory ledger has more than one line

For an idealized three-billion-parameter FP16 model, raw weights alone are about 3 × 10⁹ × 2 = 6 × 10⁹ bytes, or roughly 5.59 GiB. “Three billion” is rounded, and real checkpoint/module composition matters, so this is a back-of-envelope term, not a measured Qwen file size. Add logical KV, temporary activations, attention workspace, allocator reservation, runtime/graph buffers and other processes before comparing with device memory. A 16-GiB card showing 8 GiB apparently free at one instant is not proof that 8 GiB of additional live KV can be safely admitted: allocation granularity, peaks and concurrent work remain.

Allocated bytes and reserved bytes answer different questions. An allocator may reserve a pool to reuse later; the pool can remain high after tensors are freed. A memory monitor can sample between code cells and miss the in-process peak entirely. The Topic 02 instructor run illustrates this: the between-cell GPU sample after releasing the 1.5B model was only 362 MiB, while the in-process 4,096-token case reached 4.20 GiB allocated and 4.65 GiB reserved. The sanitized run and operator note explicitly warn against treating the 362 MiB sample as peak use. An admission rule should be based on worst credible live state and measured headroom, not one idle snapshot.

Weight compression and KV are separate levers

Quantizing weights may reduce the weight term but leave FP16 KV unchanged. Quantizing KV may change a different term and has its own quality and kernel constraints. Changing attention implementation can reduce temporary IO without changing the logical persistent KV formula. Increasing batch or sequence length can make weights a smaller share of total live memory even though the model file is identical. This distinction is the bridge to Chapter 03: “the model fits” is not a single yes/no property of a filename. It depends on the complete serving workload and the implementation that actually runs.

A roof is not a latency prediction

In an illustrative machine model with 60 TFLOP/s compute and 600 GB/s bandwidth, the ridge point is 60,000 / 600 = 100 FLOP/byte. A workload at 20 FLOP/byte has a bandwidth ceiling of 600 × 20 / 1,000 = 12 TFLOP/s, below the compute roof. Moving a point by changing reuse or precision is meaningful only if the real implementation changes bytes or operations. Launch gaps, queueing, kernel inefficiency, and memory capacity are absent from the simple roof. The original Roofline model explains the upper-bound interpretation; the explorer lets you vary intensity.

Derive the roof; then say what it cannot predict

Arithmetic intensity I is operations divided by bytes moved at a chosen memory boundary. If peak compute is C and sustainable bandwidth at that boundary is B, the simple attainable upper bound is min(C, B × I). The example uses decimal units consistently: 60 TFLOP/s = 60,000 GFLOP/s, 600 GB/s, so C/B = 100 FLOP/byte. Below that ridge, doubling useful arithmetic intensity could raise the bandwidth ceiling; above it, the compute ceiling dominates in this model. Neither statement says a real kernel will reach the roof.

Suppose the operation count for one illustrative kernel is one tera-operation and its intensity is 20 FLOP/byte. The simple roof would give a lower bound near 1 / 12 s ≈ 83 ms of idealized device execution. The measured service might take far longer because it waits in a queue, launches many kernels, moves data at a different level, samples tokens serially, or simply runs inefficiently. If a profiler says the kernel occupies only 10% of service wall time, a 2× kernel speed-up can reduce whole-service time by at most roughly 5% under an Amdahl-style fixed-remainder approximation. This is an illustrative calculation, not a measurement of the course kernel. It teaches where not to spend the next week.

Derive a decode hypothesis, then list the missing bytes

Let N_w be an approximate active dense-weight count and b_w the bytes per stored weight. For one decode row, the dense-weight estimate is about 2N_w FLOPs when a multiply and an addition count as two operations. If those weights stream once through the chosen memory boundary, traffic is about N_w b_w bytes. Their ratio is 2/b_w FLOP/byte, approximately one at FP16. For B token rows ideally sharing that weight sweep, the ratio becomes 2B/b_w. Batch one, four and 32 then give one, four and 32 FLOP/byte. This is a useful first-order hypothesis for weight reuse; it is not measured total-kernel intensity.

The cancellation of N_w in the ratio is instructive. A larger model still does more work and moves more absolute bytes; the ratio alone does not determine its latency. At the hypothetical 600 GB/s boundary, streaming 3×10⁹ two-byte weights takes at least 10 ms if that traffic assumption holds. But cache hits reduce transferred weight bytes, while K/V, activations, normalization and attention add other work. Kernel shapes can change achieved rates. A long-context decoder can therefore leave the simple weight-only regime even with the same model and batch. Name the model's omissions before using it to select an optimization.

Now interpret a batch experiment correctly. In a constructed example, B1 takes 1.0 s for 31 post-first steps; B4 takes 1.5 s for the same steps per sequence. Aggregate decode rate increases from 31/1.0=31 to 4×31/1.5≈82.7 tokens/s, while mean per-sequence cadence worsens from 32.3 to 48.4 ms. Neither result contradicts the other. The lab uses identical-length rows and a static batch, with no scheduler, queue, arrivals or padding imbalance. It isolates a shape/reuse comparison; it cannot establish a serving concurrency limit or predict p95 TTFT for mixed real requests.

Efficiency is not the same as a good schedule

A prefill that fills the GPU efficiently can still delay active decoders. Consider a deliberately simplified serial device schedule: three decode steps of 10 ms each would finish in 30 ms, but an 80 ms prompt operation inserted after the first step stretches that interval to 110 ms. The diagram is not a measured trace and assumes no overlap. Its purpose is to separate kernel efficiency from request scheduling: the large operation can be individually efficient while violating another request's cadence. A scheduler may split or defer it, but that changes overhead, first-token wait and fairness. Topic 05 studies those scheduling mechanisms; this topic supplies the shape and time-budget vocabulary needed to evaluate them.

The corresponding measurement must include both populations. Timing the large prefill alone misses its impact on existing streams; timing only a single stream misses the arrival and admission policy. Do not use the isolated lab to claim that chunked prefill is better or worse. Use it to predict where interference might arise, then design a later mixed-workload test with client deadlines, request spans and explicit failure counts. This returns the physical model to the system boundary from Chapter 01.

“Bytes moved” needs an address

HBM traffic, cache traffic and host-device transfers are different boundaries with different bandwidths. A tiling method can reduce HBM reads by reusing values in faster on-chip storage without changing mathematical FLOPs. FlashAttention is an IO-aware attention design; its benefit must be evaluated at the actual sequence shape and implementation path, not inferred from the name of an installed package. A decode kernel that repeatedly reads model weights can have different reuse when many sequences share an iteration batch. The operational intensity you plot should therefore be calculated or measured for the actual kernel and boundary, not borrowed from an unrelated prefill benchmark.

Capacity is another separate constraint. Even a compute-efficient kernel cannot launch if the current live request state does not fit. And a service can be slow because its GPU is idle between launches, in which case both compute and memory roofs are generous but irrelevant. A productive prediction names its possible falsifiers: if the device timeline has large launch gaps, the roofline is not the first answer; if HBM bandwidth is far below its relevant ceiling while SMs are also underused, look for shape, occupancy or launch issues before pronouncing the workload “memory-bound.”

Follow a byte before optimizing an operation

Device memory is relatively large and distant from arithmetic units; on-chip storage is smaller and can support much greater reuse. CPU DRAM adds another location and a host-device transfer boundary. HBM and GDDR are different implementations of device memory, not synonyms for all GPU storage. L2 is shared cache, while shared memory and registers have more local ownership and limited capacity. The exact L1/shared-memory organization varies by architecture. The diagram is a reasoning map rather than a mandatory physical route for every load. Ask whether the value is already available near the consumer, whether many threads can reuse it, and whether bringing more state close reduces the number of resident thread blocks.

A tile is a block of a larger operation selected to fit and reuse data locally. If a weight tile is fetched once and used for several token rows before eviction, useful FLOPs per transferred byte increase. Merely enlarging an allocation does not create this reuse. Register pressure or shared-memory use can also reduce occupancy—the amount of simultaneously resident work—and sometimes expose latency that a smaller tile hid. “Use more on-chip memory” is therefore a design trade-off, not a universal prescription. The CUDA Best Practices Guide describes the underlying memory/access mechanisms; the course asks you to connect them to an actual shape and an observable consequence.

Coalescing concerns how nearby threads' memory requests combine into transactions. Four neighboring useful elements can fall within a compact footprint, whereas four scattered elements can require fetching several segments. Both programs may perform the same arithmetic and use the same logical tensor size, yet transfer different amounts of data. The drawing intentionally does not assert a universal transaction size; alignment, dtype, architecture and cache behavior matter. Effective bandwidth based on useful payload is a useful application metric, but a hardware traffic counter may see additional fetched bytes. A discrepancy between them is a reason to inspect access patterns, not to silently change the denominator.

A fusion example with bytes, not marketing language

Take three elementwise functions over N values. An unfused implementation reads input X, writes intermediate A, reads A, writes intermediate B, reads B and writes output Y. Ignoring cache effects, this is six transfers of N elements. If one fused kernel keeps the intermediates local, it may need only the initial read and final write: two transfers. At N=1,048,576 FP16 elements, the useful payload is 12 MiB versus 4 MiB. The mathematical result and operation count can be essentially unchanged while the data movement and launch count shrink.

That accounting does not promise a threefold time reduction. Perhaps the original intermediates already hit in cache; perhaps the fused kernel uses too many registers; perhaps arithmetic dominates; perhaps launch savings matter more than traffic. A valid experiment preserves the function, shape, precision and output check, then measures both implementations under one timing boundary. In a production service, it must also show that this region matters to the user-visible objective. Fusion describes removing boundaries, not removing required dependencies.

Why FlashAttention changes IO without removing attention

Dense causal attention conceptually combines a query with allowed keys, normalizes scores and uses the resulting weights to aggregate values. A straightforward implementation can materialize a large score matrix in device memory between those steps. An IO-aware tiled algorithm instead processes blocks and maintains running normalization/output state, avoiding that full intermediate materialization. The causal triangular picture still explains which positions may interact; it is not the allocation plan. The original FlashAttention paper makes IO movement central to the algorithm rather than treating memory as an afterthought.

“Exact attention” distinguishes this approach from an approximate attention rule, not from all floating-point rounding differences. It does not eliminate the model's persistent KV state, the cost of dense projections or the dependence between generated tokens. Also distinguish an API request from the kernel that actually ran: asking Transformers for sdpa does not prove a specific FlashAttention implementation was selected. PyTorch dispatch depends on hardware, dtype, mask and shape. The lab's focused traces provide evidence about the actual operator path for the two captured cases; another shape may select something else. This is why installing a package and showing its version is not a performance result.

What the historical protocol-v1 phase run did

On an RTX 5070 Ti, the instructor run timed pinned Qwen2.5-0.5B and 1.5B models at batch one. Each model had four input/output shapes and five synchronized trials per phase and shape. For 1.5B with 32 output tokens, median prefill rose from 27.8 ms at 128 input tokens to 185.6 ms at 4,096 input tokens. At 128 output tokens, decode medians were 4,454.5 ms and 4,389.6 ms for the same two input lengths. The raw arrays and environment are in the teaching evidence.

Do not force a monotonic story onto five samples: at 32 output tokens, the longer-input case even had a lower decode median (965.7 ms versus 1,116.3 ms). Decode timing here covers output_tokens − 1 autoregressive steps, not HTTP end-to-end time or successful-output goodput. These are historical protocol-v1 measurements. The required protocol-v2 lab now uses the same 32/128 output lengths plus a matched batch-four case, but changes logit handling, warmup, order and reported clocks. Those implementation differences prevent a controlled speedup comparison across versions.

Worked calculation: output length multiplies dependent work

At 128 input tokens, extending the requested output from 32 to 128 tokens changes the measured decode interval from 1,116.3 to 4,454.5 ms. The ratio is about 4.4545/1.1163 = 3.99. In this protocol, decode timing includes output_tokens − 1 steps, so the step-count ratio is 127/31 = 4.10. Those ratios are close, which is consistent with more dependent steps occupying more time, but five medians are not proof of a fixed per-step cost. Per-step work can grow with context, and dynamic hardware behavior may change it. If you report the result as “decode tokens per second,” disclose whether the numerator is 127 post-first steps or 128 total generated tokens.

The 32-output pair tells a different story: going from 128 to 4,096 input tokens raised prefill by about 157.8 ms while measured decode median fell by about 150.6 ms. Do not conclude that a longer prompt makes decode inherently faster. The raw five-sample arrays vary; shape- or cache-dependent effects and measurement noise could plausibly produce this small reversal. A follow-up needs more trials, controlled warmup, a device timeline and perhaps interleaved shape order. The causal hypothesis should be stated before collecting a confirmatory run.

A second model is a cross-check, not a controlled scale factor

The same instructor protocol also ran a pinned Qwen2.5-0.5B model. For 128 input and 32 output tokens, its prefill/decode medians were 25.3/721.2 ms, versus 27.8/1,116.3 ms for 1.5B. For 4,096 input and 128 output tokens, they were 73.5/2,921.7 ms versus 186.6/4,389.6 ms. The difference changes with shape and phase. It would be wrong to multiply every 0.5B latency by three because “1.5B has three times the parameters.” Architectural details, kernels, memory footprint, launch overhead and occupancy all intervene. The two models serve as a useful robustness check on the phase story, not a controlled experiment isolating parameter count alone.

Capacity, bandwidth, latency—and allocator behavior

A capacity bottleneck means the required live objects cannot coexist in available memory, or cannot do so with safe headroom. It appears as admission rejection, allocation failure, paging or a runtime's lower-than-expected active-sequence limit. A bandwidth bottleneck means useful work is limited by the rate of moving bytes at a chosen level; the program can fit perfectly and still spend most device time waiting for data. A latency bottleneck concerns dependent fetches whose waits are not hidden by enough independent work; fitting the tensors and having high aggregate bandwidth do not remove those dependencies. A separate fragmentation or reservation problem means logical payload calculations understate allocator behavior and reusable pools. Calling all these mechanisms “VRAM bottleneck” conceals the remedy. Weight quantization could improve capacity but slow a kernel; better batching could improve weight reuse but raise KV capacity pressure; changing allocator settings could alter reservation without changing the mathematical work.

Use the right observation for each claim. For capacity, collect peak allocated and reserved memory under the target live-token mix and count failures. For bandwidth, profile actual traffic and execution at the memory level in question and compare with a relevant achieved bandwidth—not only a vendor peak. For fragmentation, inspect allocation patterns over repeated arrivals/cancellations and the runtime's block management. A one-number GPU dashboard cannot identify which mechanism is responsible. This distinction sets up the quantization trade-off in Chapter 03: smaller representation is one possible lever, not a diagnosis by itself.

Why a wall clock can lie to a CUDA beginner

GPU calls are often asynchronous from the CPU's perspective. Timing only the Python call that launches work can measure dispatch overhead while kernels continue after the stopwatch stops. The usual teaching protocol warms the path, synchronizes before starting, launches the work, synchronizes before stopping and then repeats. This does not make the measurement perfect: synchronization changes overlap and a profiler changes execution. It makes the defined interval inspectable. Keep the request-level HTTP clock separate from the phase benchmark, and do not add independently measured medians as if they were one observed transaction.

In the instructor rehearsal, one GPU process ran at a time under a 24-GiB memory scope, with immutable model snapshots already cached and offline mode enabled. These precautions avoid downloading on every clean run and bound host risk; they do not turn a five-trial batch-one phase timing into a fleet-level latency distribution. The record includes source revision, model revisions, versions, timestamps and per-trial arrays so a reader can scrutinize the result instead of accepting a slide label.

Five trials can start a question, not finish one

A median of five observations is robust to one extreme value compared with a mean, but it still has little information about tails. If the values were 25, 27, 28, 29 and 70 ms, the median would be 28 ms and the unusual 70 ms would remain operationally interesting. The published arrays let the reader inspect spread and shape order rather than accepting a lone median. For a confirmatory experiment, specify a warmup rule, interleave or randomize shapes to reduce order bias, collect enough independent runs for the decision's uncertainty, and report failures and memory peaks beside timing. The required sample size depends on the effect size and variation; an arbitrary “three runs” ritual is not a confidence argument.

Do not add median prefill from one set of runs to median decode from another and label the sum an observed end-to-end request. Both medians might come from different trials, and the real API includes tokenization, queueing, transport and post-processing. If you need an end-to-end claim, time actual complete requests under a pinned interface. If you need a phase explanation, use phase timers and profiler traces. The two measurements should reconcile qualitatively, but they answer different questions. This is the same evidence discipline established in Chapter 01: a number carries its observer and denominator with it.

Choose the next instrument

First isolate load, warmup, prefill, decode, and service waiting. If GPU kernels occupy only a small share of wall time, a detailed kernel profile may be the wrong first instrument; inspect CPU launch gaps and request traces. If one kernel dominates device time, inspect its shapes and memory behavior. PyTorch’s profiler can capture operators and allocations; NVIDIA’s Nsight Systems locates timeline gaps, while Nsight Compute interrogates a selected kernel. Profiling perturbs timing: validate any improvement again without instrumentation.

What a kernel profile can and cannot say

A kernel profile can reveal occupancy, memory transactions, launch configuration and instruction mix for a selected invocation. It cannot by itself tell whether the user waited in a queue for two seconds or whether the proxy buffered output. A system timeline can reveal that the GPU sat idle between decode launches, but it may not say which application decision caused the gap. A request trace can show long admission wait without explaining the later matrix-multiply efficiency. These are complementary views of a causal chain, not competing brands of one universal profiler.

For an illustrative case, suppose a request takes 800 ms end-to-end, of which 500 ms is queue wait, 200 ms is engine execution and 100 ms is transport/validation. Even eliminating half the engine work saves only 100 ms: end-to-end falls to 700 ms, a 12.5% improvement. If the objective is p95 TTFT under load, admission or capacity policy may have greater leverage. Change the numbers and the decision can reverse. The arithmetic is a budget exercise, not a claim about our measured server. This is why the student's analysis should name the chosen latency population and decompose it before announcing an optimization.

Make the next measurement discriminate hypotheses

Suppose a trace shows long decode time for a small model. Hypothesis A says repeated weight reads at batch one make the path bandwidth-sensitive. Hypothesis B says CPU launch gaps dominate. A kernel-only optimization would help A but barely touch B. Test A by comparing measured device occupancy, memory traffic and kernel duration across batch shapes; test B by checking the system timeline's gaps and CPU thread activity. Before running either tool, predict the contrasting signatures. If both signatures appear, quantify their wall-time shares before deciding which to fix first.

The pinned 1.5B phase run cannot adjudicate these two hypotheses alone. It has timing arrays and a local teaching trace, not a published, versioned per-kernel analysis with enough repeats for a production claim. A careful chapter should say “the phase data motivate profiling,” not “the phase data prove HBM saturation.” That boundary is intellectually productive: it tells students exactly which experiment they would run next.

The required lab: a small experiment with an explicit stop rule

The executable notebook is the experiment contract, not an optional illustration. Protocol topic02-phase-v2 runs two pinned models sequentially: Qwen2.5-0.5B-Instruct and Qwen2.5-1.5B-Instruct. Each model has four batch-one cases—input 128 or 4,096 crossed with output 32 or 128—and one batch-four case at input 128/output 32. Five trials for each of ten model/case combinations give 50 raw trials. The B1/128/32 row is the matched control for B4/128/32. Output 512 and batch eight are optional extensions after the required core, not unannounced grading requirements. The previous slides' longer matrix has been retired; all three teaching surfaces now use this one bounded contract.

Before executing, write a directional prediction for prompt length, output length and batch size. Name both the held-constant quantities and an observation that could contradict the prediction. “The GPU is memory-bound” is too broad. “At fixed model, precision, input and output lengths, B4 should improve aggregate decode rate because token rows can share weight work; per-sequence cadence may worsen” is testable. It still does not assert a kernel mechanism without a trace. Freeze your prediction in the analysis file so the explanation cannot be quietly rewritten after seeing the numbers.

The notebook first resolves immutable snapshots from a persistent model cache. Only a missing snapshot in an online environment permits an initial download; the instructor rehearsal is offline. A fresh output directory must not mean a fresh model download. Next comes one small-model smoke, then the core matrix, then separate two-shape profiles. Each trial is checkpointed before checking allocation recovery. A failed run retains completed rows and a failure status; the validator refuses to call it complete. It also rejects missing or duplicated trials, wrong model revisions, nonfinite timings and incorrect step/rate arithmetic. Passing this CPU checker proves structure and consistency, not that someone really ran a GPU or diagnosed the right mechanism.

What v2 changes—and why it is a new protocol

Version 2 requests only last-position logits during prompt processing. In the pinned model implementation, logits_to_keep=1 avoids projecting every prompt position into the full vocabulary when only the last distribution is needed to choose the next output. At P=4,096 and vocabulary size 151,936, a full two-byte logits tensor alone would contain 4096×151936×2=1,244,659,712 bytes, about 1.16 GiB. The last-position slice needs 303,872 bytes, about 297 KiB. This is tensor accounting for the vocabulary output, not a measured total-memory saving; the full prompt still passes through the decoder and creates KV. The pinned Transformers source makes this argument inspectable.

Each actual shape receives a full warmup path outside the trial timer. Shapes are shuffled within each of five rounds under a fixed order seed, limiting simple “all short cases first, all long cases last” bias. Models remain sequential to bound resource use. The caching allocator is not emptied between trials; freeing unused pools is a cleanup operation between models, not an invisible cold-start condition applied to every observation. Both synchronized wall and CUDA-event intervals are recorded. Because a Python-driven decode loop can leave gaps between launches, neither interval should be relabeled “sum of kernel execution time.” A separate kernel timeline is needed for that attribution.

These changes alter the experiment. The historical v1 medians remain useful for teaching uncertainty and phase interpretation, but comparing v1 with v2 cannot isolate the effect of last-position logits, warmup, ordering or any other single change. A causal speedup claim would require a matched A/B experiment changing one declared factor under a shared protocol. The course does not need another uncontrolled performance headline; it needs an experiment whose evidence can survive questions. The complete v2 instructor record is linked in the following section, with raw arrays rather than only a selected median.

Resource safety is part of reproducibility

The new instructor rehearsal: complete artifacts, unresolved variability

The clean-source v2 rehearsal completed the smoke, all 50 core trials and both profiles in 190.248 seconds, using cached models offline. The maximum core allocated-memory peak was 3.271 GiB; after the process exited, device use returned to its initial 14 MiB. This verifies the bounded lab path on the instructor machine. It does not establish a stable performance baseline across machines or validate the cause of every timing difference.

The matched B1/B4 medians show higher aggregate rate for four sequences: 36.9 versus 155.2 post-first tokens/s at P128/O32. Yet their decode ranges overlap substantially, and the apparent median ratio exceeds four partly because the measured B4 interval is slightly shorter. Do not promote that ratio to a scaling law. More revealingly, the B1/P128 prefill median differs between O32 and O128 labels, 22.3 versus 64.6 ms, although future output length does not change the timed prefill forward. In the separately profiled 0.5B P128/O8 trace, 8,304 physical kernel events occupy a union of 33.331 ms within a 322.362 ms first-to-last-kernel span. The P4096/O8 trace has 8,400 events, a union of 82.421 ms and a 300.923 ms span. This is substantial time outside recorded kernel events, but not proof that all the remainder is idle: copies and other event categories are excluded, and the profiler itself changes execution. The next question is launch/host scheduling and event attribution, not an unsupported declaration of HBM saturation. Resource gates and recovery

Run one GPU process at a time. On the instructor host, an external memory-limited scope caps host RAM at 24 GiB with no additional swap allowance, and a wall timeout limits duration. Before and after notebook cells the runner requires at least 24 GiB host RAM available and at most 12 GiB device use. Inside the notebook, post-trial checks enforce host headroom, process-RSS growth and live-allocation recovery; peak allocated/reserved counters preserve an in-process view. Student environments have their own available capacity, so the notebook's portable checks are not a promise that every Colab instance can finish every shape.

If a run fails, keep the partial artifact and record the failed model/case, error class and available resource evidence. Inspect other GPU processes and retained tensor references. Do not raise the limits, shrink the matrix or relabel a smoke as a completed lab to obtain a green result. After fixing an identified cause, use a new attempt directory and explain the change; never overwrite the only failed evidence. A new attempt should reuse cached snapshots and the matching package environment. This discipline is just as important in a weekly course workflow as in production: twenty students' repeated evaluations are not twenty excuses to redownload the same model or leave stale processes behind.

Read the trace in four passes

First identify the scope. The required traces use the 0.5B model at B1, prompt 128 and prompt 4,096, with eight outputs each; they capture prefill plus seven decode forwards, not the full 128-output timing case. Second locate the named topic02_prefill and topic02_decode_7_steps CPU ranges and the corresponding CUDA activity. A host range is an annotation of code execution; without an explicit completion barrier at its end, it need not enclose every last device event it launched. Do not visually add unrelated host and GPU rows as if they were sequential.

Third distinguish framework attribution from physical kernel events. A PyTorch operator can launch one or several kernels, and user annotations can enclose many operators. The notebook's compact profiler summary is a ranked set of profiler entries, including operator, kernel and user-range representations; these rows are not disjoint time buckets and must not be summed into “total GPU time.” For actual kernel occupancy on the timeline, inspect CUDA kernel events and merge overlapping intervals at the desired boundary. A long operator name proves neither bandwidth saturation nor a specific end-to-end performance share. Record the event category, phase and input shape with every observation.

Fourth propose the next test. If the trace suggests launch gaps, a more detailed system timeline and CPU activity are useful; if one selected kernel dominates, inspect its shape and relevant hardware counters. If the device is fast but client first-content time is slow, return to request spans. Save both traces and two annotated observations in the private analysis. Rerun any proposed optimization without profiling before reporting an improvement. The trace is a diagnostic intervention with overhead, not the production latency oracle.

Vocabulary you should be able to explain without a slide

Autoregressive dependency
The next output choice uses earlier chosen tokens; parallel arithmetic within a step does not remove that chain.
Prefill / decode
Processing known prompt positions and selecting the first output, versus later forwards that advance each live sequence by one new position.
GEMM / GEMV
General matrix–matrix / matrix–vector multiplication. The token-row dimension helps explain why prefill and small-batch decode may use different kernels.
Q, K, V
Query, key and value projections in attention. Retained keys/values let later queries reuse already-computed history.
MHA / GQA / MQA
Multi-head, grouped-query and multi-query attention: respectively equal query/KV head counts, groups of queries sharing K/V, and all queries sharing one KV head.
HBM / GDDR / DRAM
High-bandwidth memory and graphics double-data-rate memory are device-memory technologies; dynamic RAM also underlies host memory. Do not apply one boundary's bandwidth to another.
FLOP / FLOP/s
Floating-point work / work rate. “GFLOP” alone is not a throughput unit. State whether a multiply-add counts as two operations.
Arithmetic intensity / ridge
Work per transferred byte at a declared boundary / intensity where compute and bandwidth roofs intersect.
Allocated / reserved / peak
Live allocator tensor bytes / the allocator's pool including reusable space / the maximum of a specified counter since reset. These are not three disjoint memory terms.
Warmup / synchronization
Excluded setup executions / an explicit completion boundary. A warm path can still vary; a barrier changes the interval being measured.
SDPA
Scaled dot-product attention API/path. The requested API name does not uniquely identify the kernel selected for every shape.
Trace / profile
A time-ordered event record / attributed performance information. Categories and scope matter more than the file's name.

Questions that often reveal a missing boundary

“If batch four is faster than expected, did we beat the bandwidth law?” No law predicts your wall time from the weight-only approximation. Cache reuse, launch overhead, shapes and experimental variation can all matter. Preserve the raw trials and investigate the specific claimed mechanism. “Why do two identical prefill shapes have different medians when only requested output length changed?” Prefill does not know the future loop count in this lab's forward call. Differences can arise from ordering, runtime/host scheduling, allocator state and variation; future output length is not a causal explanation by itself. This is a particularly useful internal consistency check.

“Why not just synchronize after every token?” That would define a different decode loop and can change overlap and launch cadence. It may be useful for a separate token-level investigation, but cannot silently replace the current whole-decode timer. “Does a flat reserved-memory line prove a leak?” Not by itself: the allocator may retain reusable pool space while live allocated bytes recover. Check tensor ownership and repeated live-state growth. “Can I infer KV bytes from the model's advertised parameter count?” No; use layers, KV heads, head dimension and cache dtype. “Can the instructor's table replace my GPU run?” No; it is a reference for reasoning and artifact structure, not your submitted experiment.
