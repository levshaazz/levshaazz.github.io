Before starting: the vocabulary you will actually use

You need Python, a basic understanding of an HTTP request/response, and the idea that a language model chooses a next token from a probability distribution. You do not need CUDA programming or Kubernetes to follow this chapter. A token is an ID in a tokenizer vocabulary, not necessarily a word or character. A sequence is one request's ordered input and generated tokens. A worker is the process or logical execution owner that runs model work; a replica is another independently serviceable model instance, which may itself use more than one GPU. We start with one worker on one GPU.

Prefill processes the known input and prepares attention state and next-token logits. Decode repeatedly advances the generated sequence. The KV cache retains attention keys and values from prior positions so the model need not recompute those projections at every step. It is not a cache of complete answers. Admission decides whether new work may enter; scheduling chooses which already eligible work advances. A queue stores waiting work; it does not provide extra compute. These are different responsibilities even if one Python process implements all of them.

A service-level objective (SLO) names a desired observable outcome over a declared population and window, such as “at least 99% of attempts complete within five seconds.” A deadline is the last acceptable completion time for a particular request. A timeout is an observer's decision to stop waiting; it does not automatically stop remote computation. Throughput counts completed work per time; goodput narrows that work to what the stated contract considers useful. The exact course T4 token-goodput definition is given below. Never assume a paper, benchmark and product use the same definition just because they share a metric name.

For a first reading, follow the measured incident, the request path, the clocks and the worked load examples; then answer exercises 1–4 before opening their reasoning. On a second pass, follow the architecture decisions and produce your own boundary trace. Each measured number names its run; constructed examples teach a calculation without pretending to be additional GPU evidence.

The 64-client incident

On a Tesla T4, the course sent 64 simultaneous chat requests in each of three waves to two serving paths using the same pinned Qwen2.5-1.5B-Instruct model in FP16. Each path received 192 attempts with a 60-second client timeout. The serialized baseline timed out on 154 attempts; vLLM timed out on none. Among successful attempts, p95 time to first token was 53.251 seconds for the baseline and 0.523 seconds for vLLM. The protocol and raw request records show both denominators. A percentile calculated only from the 38 baseline successes must never conceal the 154 failures.

The useful explanation is not “the GPU is faster.” The baseline held a single generation lock: an asynchronous HTTP frontend could accept sockets while generation remained serial. The lesson is to draw the gateway, admission decision, waiting queue, scheduler, worker, and response stream separately. The same experiment does not establish universal vLLM speed, a production SLO, or performance on another device.

Two experiments, not one blended story

We will use two measured records throughout this chapter. The first is the Tesla T4 burst comparison above: the pinned 1.5B model, FP16, eight fixed prompts, at most 128 output tokens, simultaneous closed-loop waves of 1, 8, 32 and 64 clients, three repeats at each point, and a 60-second client timeout. The intentionally simple pipeline had a single lock around generation. vLLM ran the same request interface and model revision, but the two runtimes did not promise identical hidden defaults or cold-start behavior. The second record is a much smaller Topic 01 exercise on an RTX 5070 Ti: one pinned 0.5B model request and a separate streaming-proxy request. They answer different questions. One is a burst-system demonstration; the other teaches how to name clocks at a request boundary.

It would be tempting to take the first request's 0.036-second first text chunk on the newer GPU and combine it with the T4's 64-client throughput to announce a wonderfully fast serving system. That would cross models, devices, runtimes, workload shapes and observers. We will instead keep a ledger: which run, which population, which clock, which successful work, and which failure produced each number. That habit matters more than memorizing either number.

Worked calculation: 154 failures are not a footnote

At 64 clients there are three waves, so the denominator is 64 × 3 = 192 attempts per server. For the serialized baseline, 192 − 154 = 38 complete requests. The failure fraction is 154 / 192 = 0.80208…, or 80.2% to one decimal place. The completion fraction is 19.8%. The reported 53.251-second p95 TTFT is therefore computed among only those 38 completions. It is not a percentile for the full attempted population. Replacing each missing TTFT with 60 seconds would manufacture a different statistic, not repair this one: the historical client reset ttft to null on any failed attempt, including failure after content had arrived. Missing TTFT therefore means not retained, not “no token arrived.” A 60-second timeout does not establish the first-content time.

Likewise, 1519.3 / 18.7 ≈ 81.2 compares the displayed rounded median goodputs at 64 clients; the source table reports an 81.1× ratio using unrounded values. Both are a same-protocol, same-device, selected-implementation contrast. Neither says that a single vLLM request is 81 times faster. At one client, the median goodput ratio is only about 3.3×, and the first serialized wave was cold. A single headline speed-up hides the shape of the work.

The source's tokens: 0 on a timed-out client record is a counting decision: no completed returned output is credited to goodput. It does not prove the GPU performed zero work before disconnect. To locate that work, we need owner-side traces and release events. This is where a performance table turns into an architecture question.

Who owns the wait?

  1. Client and edge: capture the request start, deadline, route, model name, and first visible content. A 200 status or open port proves little about completion.
  2. Admission: check estimated tokens, tenant policy, queue depth, and remaining deadline. An explicit early rejection can be more honest than letting impossible work time out.
  3. Scheduler: decide which live sequences advance. Scheduling changes both first-token wait and the decode cadence of requests already accepted. Orca studies iteration-level scheduling; vLLM/PagedAttention addresses efficient request-state management.
  4. Worker: tokenize, prefill, decode, sample, and free KV state on completion or cancellation. A disconnect that only closes the socket can leave costly GPU work alive.

Instrument each ownership boundary with an event and a release event. If the client sees a slow first chunk, its single timestamp cannot prove whether queueing, prefill, or a buffering proxy is responsible. Compare owner-recorded span durations; do not subtract wall clocks on unsynchronized hosts.

A request handler is not the serving system

Imagine a frontend that can parse 64 JSON bodies concurrently and immediately places each on an asynchronous task. If all those tasks call a generator protected by one lock, there is still only one active generation. An HTTP health check can stay green, TCP connections can stay open, and GPU memory can appear allocated while almost every client waits. “The API is async” describes the outer boundary; it says nothing about how many model sequences make progress. The measured T4 pipeline intentionally exposed precisely this failure mode. Calling it a general Transformers defect would be unfair: a different server could batch requests or use a different scheduler.

At each boundary ask a sharper question. What is the unit that enters—request, prompt token, sequence, decode step? What resource is scarce—CPU tokenization, queue slot, VRAM, bandwidth, kernel launches, or client deadline? Who chooses the next unit of work, and who notices cancellation? The answer often changes within one request. Prefill may be large parallel work; decode is a sequence of dependent steps. The queue can grow while the device is busy, or even while the device is underused because the CPU is failing to feed it. A system diagram is useful only when it makes those alternatives testable.

The client clock and the engine clock

A client can time an entire exchange from the moment it sends a request until it receives the terminal response. An engine can separately time admission wait, tokenization, prefill, individual decode steps and cleanup. These spans do not automatically add up across machines: timestamp origins may differ, retries may overlap, and proxy buffering may delay delivery after the engine produced output. Prefer a common trace ID, monotonic durations measured by each owner, and explicit event boundaries. If you have only client timings, report only client timings; do not pretend to know that the GPU was slow.

Three ways to get a slow first token

Consider three hypothetical traces with the same two-second client-observed first-content time. In trace A, admission waits 1.8 seconds and prefill takes 0.1 seconds. In B, admission is immediate but a long prompt spends 1.8 seconds in prefill. In C, queue and prefill each take 0.1 seconds, followed by 1.8 seconds of delivery/buffering. They have approximately the same client symptom and very different remedies. Queue tuning may help A; prompt or prefill optimization may help B; transport configuration is the right layer for C. The figures are constructed diagnostic examples, not measurements from the course GPU.

To distinguish them, record gateway receive, admission, engine start, first engine output and first client-visible content with a shared request ID. If clocks are not synchronized, compare durations within an owner or emit causal parent/child spans; do not subtract raw wall timestamps from different hosts. A useful incident report says “the time is in the queue” only after that separation is visible.

A waiting queue is a policy decision

A queue can be valuable: a short burst need not become a rejection if the service has headroom before deadlines expire. But a queue that accepts more work than can be completed converts overload into late failures. It also consumes memory for request objects and may hold client connections. An admission policy should therefore know the request's deadline and a conservative estimate of the work still ahead. A request with a 2,048-token prompt and 512-token output cap is not the same size as one with 64 and 32 tokens; counting only sockets hides that difference. The next chapters will give the KV and compute pieces of this estimate.

Do not claim an exact scheduling algorithm from the T4 table alone. The table supports a mechanism-level contrast: one generation lock allows only one active generation; the vLLM run completed a batchable wave at far higher goodput. An additional mechanism-check wave observed up to 64 running vLLM requests, but it was not part of the recorded comparison. Orca describes iteration-level scheduling, and the vLLM/PagedAttention paper explains how paged request state enables efficient sharing and scheduling. Those sources explain possible design mechanisms; the pinned run record establishes what this particular comparison actually measured.

One real request, four clocks

The Topic 01 instructor rehearsal used a pinned Qwen2.5-0.5B-Instruct snapshot on an RTX 5070 Ti. A 43-token input produced 63 output tokens. Local model load took 4.51 seconds; a warm non-streaming request took 1.395 seconds. A separate streaming-proxy request delivered its first nonempty text chunk after 0.036 seconds and completed in 1.293 seconds. It emitted 56 nonempty chunks for 63 tokens—direct evidence that a chunk is not necessarily a token. See the sanitized run with versions and raw fields.

These are separate single-request runs without a server queue. Do not subtract 0.036 from 1.395 to estimate decode, report the chunk time as token-level TTFT, or call either result p95. The same distinction governs every chart: define start, stop, observer, workload slice, success population, and failure treatment before comparing numbers.

Why 56 chunks cannot be reported as 56 tokens

The pinned Topic 01 record says 43 input tokens and 63 output tokens. Its streaming proxy counted 56 nonempty text chunks. A transport chunk is a delivery unit; a token is a tokenizer unit; a visible character sequence may span either boundary. The first nonempty chunk may contain several tokens, part of a token's displayed spelling, or text after buffering. It is therefore accurate to report “first nonempty text chunk at 0.036 seconds in one streaming proxy run.” It is not accurate to rename that number TTFT under a token-observer definition, nor to calculate ITL by dividing the remainder by 55 chunk gaps. The raw sanitized result keeps the fields distinct.

The 4.51-second model load is another boundary. Including it in a cold client request might be valid if that is how the service is deployed; excluding it is valid for a warm steady-state question. Mixing one cold request with warm requests and calling the result a single latency distribution makes both questions harder to answer. Record at least the model load, warmup state, tokenizer and model revision, input/output counts, request start and finish, and the observer of first output. On the instructor machine, the teaching notebook deliberately separates load and request timing.

Prefill and decode are different service demands

Given a known prompt, prefill can process its positions in parallel and populate initial key/value state. Decode cannot know output token t+1 until it has computed the logits and sampled or selected token t. Different requests can share a decode iteration, but each individual output chain remains sequential. This is why a request's input and output lengths matter separately. A long input and short output can concentrate work near the first token; a short input and long output can occupy the scheduler for many iterations. Topic 02 turns that intuition into phase shapes and measured phase timings.

The model still needs request state after the first token. KV cache grows with retained context, and a new decode step reads prior state. A server that accepts many live requests without accounting for tokens can hit a memory limit even if its request-count limit looks conservative. PagedAttention addresses allocation and sharing of KV blocks; it does not make KV cost zero. Nor can an iteration-level scheduler solve an overloaded input rate by itself: if demand persistently exceeds the service's attainable completed-work rate, some combination of waiting, shedding, scaling or deadline failure remains necessary.

A metric is a population plus a clock

TTFT, inter-token latency, end-to-end time and throughput are not interchangeable views of one stopwatch. In a streaming service, TTFT might start at client send and end at first visible token; an engine-side first-token time starts later and ends before transport. An ITL is one interval between adjacent tokens for one stream. Mean time per output token averages a set of such gaps; averaging again across requests requires a declared weighting rule. End-to-end latency includes the entire completion or a declared termination. Successful-output goodput counts delivered work over complete wall time; raw generation-token rate can be higher while customers receive little. Every dashboard should state those boundaries.

The success filter can reverse your intuition

Suppose a hypothetical service receives 100 requests. It finishes 20 quickly in 0.2 seconds and the other 80 time out after 60 seconds. A p95 computed on the 20 successful requests is 0.2 seconds and looks excellent. A second service finishes all 100 in 1 second. If you compare only successful-request p95, the first appears faster while being much worse for users. The right report shows success rate, failure types, successful latency, and perhaps deadline-attainment probability together. Do not place a timeout into the successful latency population as if it were a completed 60-second response; give the failed population its own metric.

The T4 data show a less contrived version of this trap. The serialized path's 64-client p95 TTFT is 53.251 seconds among 38 completions, but 154 attempted requests did not complete. Even if that successful p95 were far smaller, it could not rescue an 80.2% failure fraction. Conversely, vLLM's 0/192 observed failures in this bounded run do not prove zero future failures. Report the measured count and protocol, then design a sustained test before claiming an error-rate objective.

From a clock to a capacity hypothesis

For a worked model, not this measured GPU run, suppose stable arrivals average 8 requests per second and average time in the system is 0.5 seconds. Little’s Law gives average in-flight work L = λW = 8 × 0.5 = 4 requests. This is a consistency check, not a safe queue-size setting. It says nothing about a burst of 64 simultaneous arrivals, long-tail service time, output-length mix, or whether the GPU can hold their KV states. The original Little’s Law result assumes a stable system; overload violates the intuition people often attach to the average.

For a capacity experiment, fix the model revision, input/output distribution, timeout, arrival process, and scoring contract. Run increasing load, then report successful-output goodput, successful-request TTFT and end-to-end distributions, rejects, timeouts, and resource headroom side by side. A fast one-request generation is merely a starting point.

Worked calculation: Little’s Law cannot size a burst queue

Consider the illustrative stable system just described: λ = 8 completed requests/s and mean end-to-end time W = 0.5 s. The mean number of requests in the system is L = λW = 4. The units cancel correctly: requests/second times seconds leaves requests. Residence time has units of seconds, not seconds per request; the average is taken over requests, but that does not add a denominator to its physical unit. This is a statement about a steady average over a stable population. If a 64-request wave arrives at one instant, L = 4 does not mean only four requests can be present or that 60 should be rejected. It means the chosen average rate and delay cannot coexist with some other long-run mean concurrency without changing the workload or measurement boundary.

Now construct a second illustrative system whose sustainable completion rate is only six requests per second while arrivals average eight requests per second. The backlog grows by roughly two requests each second until admission or traffic changes; there is no stable finite mean waiting time to plug into the same comforting equation. Little's Law itself is not wrong—the steady-state premise is missing. In production, look for a bounded observation window, a stable arrival/completion balance and explicit abandoned requests before using the law as a consistency check. The original Little result gives the theory; a queue-capacity setting requires workload tails and deadlines that the equation does not supply.

Worked decision: can this request still meet its deadline?

Suppose a fictional API promises a five-second client deadline. An arriving request has already spent 0.2 seconds in transit and validation. The queue estimator predicts 3.9 seconds of wait, and the workload-specific service estimate is 1.4 seconds. The optimistic finish is 0.2 + 3.9 + 1.4 = 5.5 s, exceeding the deadline before the worker starts. Admitting it merely to time out later consumes a connection and possibly compute that could serve feasible work. A bounded, explicit reject can be better for both the user and neighboring requests—if the contract says what the rejection means and the client can back off. The estimates here are illustrative; they are not calibrated from our GPU run.

Such a decision needs a margin because service-time estimates are uncertain and output lengths vary. A short output cap may fit when a long one does not. A server may choose priority, fairness, a per-tenant queue, or a hard reject, but each policy has costs: rejecting too aggressively wastes spare capacity; admitting too freely hides overload behind late timeouts. For a real policy, record prediction error by request shape and compare outcomes around the decision boundary. The important separation is between capacity (can the system execute eventually?), deadline feasibility (can it execute in time?), and admission fairness (which tenant receives scarce time?).

Cancellation is a resource release protocol

When a client disconnects, the edge may detect it before the scheduler does. If the worker continues decoding, it still consumes GPU time and retains KV for tokens no user will read. A correct cancellation path must convey the request identity to every owner, remove or mark queued work, stop future decode steps when safe, release KV blocks and record whether the client saw a partial answer. Some work already in flight cannot be undone instantly, so “cancelled” should refer to a declared point in the lifecycle, not a magical rollback of completed kernels.

Think of a 60-second timeout in the T4 run. From the client record alone we know the attempt failed its deadline. We do not know exactly how much GPU work occurred before cancellation or how promptly memory was reclaimed. The run's naive server log and vLLM log are available for investigation, but the reported goodput deliberately counts only completed output. A production cancellation experiment would instrument disconnect, scheduler removal and memory release as separate events. It would also probe what happens if a stream disconnects after some visible chunks: the answer is partial, not completed.

A retry can be a second arrival, not a second chance

At overload, clients often retry after a timeout. If the first request is still queued or generating, a blind retry adds more demand and can worsen the original problem. For an illustrative 100-request burst where 40 time out and all 40 immediately retry once, the server receives 140 attempts for only 100 original user intents. If half of those retries time out again and retry once more, attempts rise to 160. Counting attempts without a stable idempotency key can make traffic look like user growth rather than policy amplification. A backoff with jitter and a retry budget can reduce synchronization; a server still needs to surface explicit overload and honor cancellation.

For text generation, retry semantics are not trivial. A stochastic response may differ on each run, and the client may have received partial text before losing the connection. The service must say whether retrying with the same request ID resumes, repeats, or creates a new generation. The simple T4 benchmark did not exercise this protocol. The chapter introduces it because a serving architecture that omits retries can appear healthy in a benchmark and collapse under real client behavior.

Fan-out moves the queue you forgot to draw

A user-visible request may call a router, retrieval system, safety classifier, main generator and post-processor. If they run sequentially, their delays accumulate; if some run in parallel, the slowest required branch gates completion. A local GPU benchmark measures only one piece. Consider an illustrative endpoint with 40 ms routing, 90 ms retrieval, 600 ms generation and 30 ms validation in sequence: the minimum component sum is 760 ms before network overhead and queueing. If generation is streamed but the post-processor buffers the entire answer, the client may see no early chunks despite a fast engine-side first token. When diagnosing a bad SLO, first draw the critical path and owner spans, then choose which component to profile.

Fan-out can also multiply failure probability. If a response requires all of three independent branches that each succeed 99% of the time, the idealized joint success is 0.99³ ≈ 97.0%. Independence is an assumption, and shared infrastructure failures make it optimistic. The example does not describe the course service; it shows why a generator-only success rate is not automatically an API success rate. A real service report should name which dependencies were included in the request's success definition.

Design the experiment that the T4 burst was not

The T4 waves reveal a dramatic batching and failure contrast, but they are not a sustainable-capacity curve. A capacity test needs an arrival process that can be maintained over time, a declared prompt/output distribution, warmup and measurement windows, and enough independent repetitions to see variability. Include both requests per second and token mix: ten short outputs may cost less decode time than one extremely long output, while a long prompt changes prefill and KV. Fix model and tokenizer revisions, engine version, GPU/driver, generation parameters, timeout and success criteria before comparing candidates. Collect attempts, completions, rejects and timeouts, not only successful latencies.

Increase offered load in bounded steps, letting the system reach a measurable state at each step; stop when headroom, error rate, deadline attainment or safety guardrails fail. Report the last acceptable point under the declared objective, not the highest number printed before the machine crashed. For a target such as “at least 99% of requests complete within 5 seconds,” count all attempts in the objective and state whether explicit rejects are failures. Successful-only p95 can then be shown as a diagnostic, not used to silently redefine success. This experiment should include a cleanup check: GPU memory, process state and ports must return to baseline after each stage.

A falsifiable incident checklist

  1. Confirm the symptom and population. Count attempts, completions, explicit rejects, timeouts and cancellations over the same window. State whether the p95 contains only successful requests.
  2. Locate the wait. Compare client send, gateway receive, admission, engine start, first engine output, first visible content and completion spans under one request identity.
  3. Separate workload shapes. Bucket input tokens, output cap and actual output tokens. Check whether one long-tail shape explains an apparently random latency jump.
  4. Check resource evidence. Observe queue length, running sequences, GPU utilization, memory reserved, KV allocation and CPU launch gaps. A single utilization percentage is not a diagnosis.
  5. Form two competing hypotheses. For example, “one lock serializes generation” predicts flat goodput with rising queue age; “proxy buffers output” predicts early engine output but late client visibility. State the measurement that would disprove each.
  6. Change one policy or implementation at a time. Re-run the identical contract, preserve raw records and check teardown. A faster successful p95 with more failures is not automatically an improvement.

Who owns the arrival clock?

An open-loop generator schedules arrivals independently of whether earlier requests have finished. For example, it intends to send at 0, 1, 2, 3 and 4 seconds. A closed-loop user sends, waits for a response or timeout, optionally thinks, and then sends again. Both are legitimate models. An interactive user who reads each answer is naturally closed loop. An externally driven stream of incoming jobs can continue arriving while the service slows and is better represented by an independent arrival schedule. Choosing one is a statement about the question, not a contest between good and bad benchmarks.

For a stable closed-loop population of N users, mean response time R seconds and mean think time Z seconds, completed cycles per second are approximately X = N / (R + Z). With 32 users, R = 0.8 s and Z = 0.2 s, the rate is 32 requests/s. If response time grows to 3.8 seconds while the users still wait before sending, the offered rate falls to eight requests/s. The server did not gain capacity; the test population slowed its own demand. “Concurrency 32” by itself therefore does not specify requests per second, token demand, a burst pattern or a sustained service objective.

The T4 experiment sends a finite simultaneous wave and waits for its outcomes. It is not the steady closed-loop population in that equation, and it is not an open-loop capacity experiment. To reproduce its meaning, preserve the wave protocol. To ask a new question about sustained independent arrivals, write a new protocol with a target schedule, duration, token mix, timeout and generator capacity. Record intended arrival times as well as actual sends: a saturated load generator can silently change the workload even when the server has spare capacity.

A missing request is not a fast request

Suppose the intended workload is one request per second. At time zero the service stalls for four seconds. A blocking single-client test waits and next sends at time four. It has no samples for the requests intended at times one, two and three. If it summarizes only the responses it happened to issue, the histogram answers a different question from “what happens to arrivals that keep coming during the stall?” This mismatch is called coordinated omission: the act of waiting coordinates the measurement schedule with the delay being measured.

Keep three events for a scheduled request: scheduled_send, actual_send and terminal, measured on the generator's monotonic clock. Then actual_send − scheduled_send is generator scheduling lag, terminal − actual_send is observed exchange duration, and terminal − scheduled_send includes lag relative to the intended workload. Publish the intended and achieved rates alongside both durations. If generator lag grows without bound, stop and fix the generator or explicitly report the unmet schedule; do not label it a clean server-capacity result.

HdrHistogram provides correction based on an expected sampling interval. Such a corrected latency distribution can expose omitted waiting under that model, but it cannot reconstruct whether real missing requests would have been admitted, rejected, cancelled or completed. Use an actual independent arrival test when those outcomes are the question. Do not “correct” the T4 wave into an invented stream of requests, and do not apply this accusation to a closed-loop user simulation that openly declares exactly that user model.

Why a little less headroom can mean a lot more waiting

For background, see MIT’s M/M/1 teaching note. A useful analytical counterexample is the M/M/1 queue: Poisson arrivals at rate λ, independent exponential service times with mean 1/μ, one server, an unbounded FIFO waiting room and a stable load λ < μ. The two M symbols denote memoryless arrival and service processes. This is a model of waiting, not a claim that batched GPU inference has exponential service or one-request-at-a-time execution.

Under those assumptions, utilization is ρ = λ/μ, mean response time is W = 1/(μ − λ), and mean queue wait is Wq = W − 1/μ. At μ = 10 requests/s, mean service is 0.1 seconds. At arrivals of five requests/s, response is 0.2 seconds and queue wait is 0.1 seconds. At nine requests/s, response is one second and queue wait is 0.9 seconds. At 9.5 requests/s, response is two seconds and queue wait is 1.9 seconds. The service did not become twenty times slower; waiting now dominates residence. These are means, not p95 values.

A real inference service violates several assumptions: service depends on input and output lengths, requests share iterations, caching changes work, finite queues reject, and memory pressure can force preemption. Use the model to reject the intuition that “95% busy is almost the same as 50% busy,” not to derive a production queue limit. Validate an operating envelope empirically. If a load sweep produces passing points at 2, 4 and 6 requests/s and failing points at 8 and 10, then six is the last tested passing point. The exact boundary between six and eight remains unresolved.

Attach an error budget and sampling plan to the boundary. Zero observed failures in 192 attempts is not proof that the true failure probability is zero. If attempts were independent with a fixed failure probability, the probability of observing none would be (1−p)192(1-p)^{192}(1−p)192; setting this to 0.05 gives a one-sided 95% upper bound of about 1.55%. The “rule of three” approximation gives 3/192 ≈ 1.56%. Shared burst failures violate independence, so even that simple calculation should not be sold as a production guarantee. It explains why a short clean demo cannot validate a stringent reliability SLO.

Compute a report from named events

Consider a constructed trace on one monotonic clock, in milliseconds: send 0, admitted 8, prefill starts 228, first content 323, last content 3117, terminal acknowledgement 3120. Assume the observer can attribute exactly 128 output-token events to this trace; if it sees only transport chunks, the token-gap calculation below is unavailable. The queue span after admission is 228 − 8 = 220 ms. Client first-content time is 323 − 0 = 323 ms. The 95 milliseconds from prefill start to first content contain any computation and delivery on that segment; without finer instrumentation it is not a pure GPU-prefill duration.

There are 127 adjacent-token gaps after the first of 128 output tokens. The interval from first to last content is 3117 − 323 = 2794 ms, so mean gap is 2794 / 127 = 22 ms. End-to-end time including terminal acknowledgement is 3120 − 0 = 3120 ms. The accounting is therefore 323 + 127 × 22 + 3 = 3120 ms. Omitting the final three milliseconds measures through last content instead of through the terminal event; multiplying 22 by 128 adds a nonexistent extra gap. With one output token there are no adjacent-token gaps, so mean ITL is undefined, not zero.

Do not average per-request means blindly. If a two-token response has one gap of 100 ms and a 101-token response has 100 gaps of 10 ms, the request-weighted mean of their means is (100 + 10)/2 = 55 ms. The pooled token-gap mean is (100 + 100 × 10)/101 ≈ 10.89 ms. Neither arithmetic operation is intrinsically wrong; they answer “average request's mean gap” and “average observed gap” respectively. Write the weighting rule beside the number. Likewise, p95 of individual ITLs is not p95 of per-request average ITL.

Goodput needs equally explicit nesting. In the illustrated minute, 120 responses complete, 110 meet correctness requirements, and 90 of those also meet all declared latency objectives. Completion throughput is 2 requests/s; correct throughput is about 1.83 requests/s; contract-satisfying goodput is 1.5 requests/s. Keep the window fixed and count original user intents separately from retry attempts. The T4 table uses completed-output-token goodput without this additional correctness-and-SLO filter; the word alone does not make the two definitions interchangeable.

Choose a topology from the constraint, not the fashion

Start with the simplest architecture that has an owner for each required guarantee. An offline worker consumes a backlog and writes completed results; it may prioritize total completion time and retryable checkpoints over interactive latency. A single interactive engine exposes a streaming endpoint and owns its admission, scheduling and local state. A gateway plus replica pool introduces routing, health and capacity distribution. These are logical shapes: a gateway can begin in the same process, and a worker may later be split across processes or devices. Every new boundary also introduces failure, observability and state-transfer obligations.

For a nightly document-labeling job with no interactive deadline, adding a streaming gateway does not solve the dominant problem. A bounded job queue, durable output IDs and restartable progress may matter more. For a small interactive assistant that fits on one GPU, a single engine plus a clear API contract can be the best first baseline. For independently arriving tenants whose combined load exceeds one worker, a replica pool can supply capacity, but only if routing and admission avoid concentrating work on one replica. In each case, first write the failure you need to tolerate and the workload you need to absorb; then add a component that owns it.

Requests are not equal-sized routing units

Imagine two identical workers each reporting two queued requests. Worker A has two 128-token prompts; worker B has two 4,096-token prompts. Both have queue length two, but queued input totals are 256 and 8,192 tokens, a 32× difference. This does not imply 32× runtime because batching, attention, device efficiency and output lengths matter. It does show why a least-request-count router can be blind to workload. Useful inputs include prompt tokens, output cap, running token state, queue age, predicted service demand and cancellation status.

Cache affinity adds another trade-off. Suppose worker A has a reusable prefix but predicts 300 ms queue wait plus 20 ms prefill. Worker B has no prefix but predicts 20 ms queue wait plus 120 ms prefill. Assuming all other costs equal, A's first-output subtotal is 320 ms and B's is 140 ms. A cache-only router chooses A; a queue-aware estimate chooses B. The 180 ms difference is illustrative. A real policy must include prediction error, cache validation, actual output work and the cost of moving or duplicating state. A high cache-hit rate is not itself a user latency objective.

Fairness is also a choice of unit. A FIFO queue can put a short request from tenant B behind many long requests from tenant A. Per-tenant queues, token budgets, priorities or weighted shares can change that order, but no mechanism is “fair” without a stated entitlement and a starvation rule. Compare per-tenant deadline attainment and rejected demand, not only global throughput. Giving every tenant one request slot can be grossly unequal when one slot represents thousands of tokens and another represents a dozen.

When separating prefill and decode might help

Prefill and decode have different work shapes and can interfere with each other's latency. Separating them into specialized workers offers independent scaling and scheduling, but it creates a KV-state transfer boundary. The decode worker cannot continue from a prompt it has not computed unless the necessary state is available. The DistServe paper studies this disaggregated design. It is an architectural option, not a default speedup for every model, GPU or network.

A useful first calculation is a transfer lower bound: transfer seconds ≥ state bytes / effective bytes per second. If a constructed request needs 1 GiB of state and the effective link delivers 25 GiB/s, payload transfer alone takes at least 40 ms. At 5 GiB/s, it takes 200 ms. Serialization, queueing, allocation, synchronization and recovery add to that bound. If separation saves only 30 ms of interference on this request, even the faster link cannot win that latency comparison. If it saves 500 ms under sustained mixed traffic, the architecture becomes worth testing. State size and transfer bandwidth here are teaching assumptions, not values measured on the course machine.

Then ask the reliability question: who owns the request if prefill finishes but transfer fails? Can the request be retried without exposing duplicated or contradictory partial output? Which queue owns its deadline? Does the original KV remain allocated until acknowledgement, and how is orphaned state reclaimed? A topology diagram that omits these ownership transitions has not specified a deployable service.

A rollout is a request lifecycle experiment

Liveness asks whether a process should be considered alive; readiness asks whether it should receive new traffic. Binding a TCP port is insufficient readiness when weights are still loading, kernels are being initialized, the advertised model identity is wrong, or a representative request cannot complete. Define a startup budget, validate the intended model and interface, perform bounded warmup, and only then allow admission. Repeatedly restarting a legitimately loading model because a probe budget is too short can prevent the service from ever becoming ready.

For a rolling replacement, reverse the admission decision before stopping the old worker: mark it unready or remove it from routing, allow propagation, stop admitting new requests, and drain accepted work under a finite deadline. Work that cannot finish must receive the declared failure/cancellation semantics; it must not disappear into an apparently successful truncated stream. Keep replacement headroom in the calculation. If a two-replica service needs both replicas at the current load, taking one out without traffic control can overload the survivor even if every individual shutdown handler is correct.

A Kubernetes Pod termination lifecycle supplies hooks and a grace period, but infrastructure does not automatically know when an LLM request has released all state. Verify that active streams finish or terminate explicitly, no new work enters the draining worker, in-flight counts fall, request-owned KV is released, and the process exits within its budget. A test can hold one long stream open, initiate drain, attempt one new request, and observe both outcomes. This is a bounded lifecycle test, not a reason to launch a high-concurrency benchmark.

Answer reasoning, not just answer letters

  1. 38/192 = 19.8% completed; 154/192 = 80.2% timed out. The TTFT percentile describes only the 38 completions, while failed attempts have no retained TTFT in this client's output. They may have received partial content before failing.
  2. One possibility is a long admission queue followed by fast prefill; another is early engine output delayed by a buffering proxy. Engine-start and first-engine-output spans, compared with first client-visible content under one request ID, separate the cases. Do not subtract unsynchronized host wall clocks.
  3. L = λW = 4 mean in-flight requests under stable conditions. A four-request mean says nothing about burst peak or the tail of service times; neither does it include deadlines or memory per live token.
  4. The optimistic 5.5-second finish misses the deadline, so a clear early rejection or deferral may be preferable to a late timeout. But the queue and service predictions have error, and fairness, output cap, retry semantics and neighboring requests matter.
  5. A defensible answer holds the pinned model, tokenizer, runtime and hardware constant; declares a sustained arrival process and token distribution; counts all attempts and failures; steps load with a hard resource/deadline stop; and verifies the GPU/process/port return to baseline. It records results as teaching capacity evidence only. It does not publish new grading bars without the separate judge calibration procedure.
  6. 32/(0.8+0.2) = 32 requests/s and 32/(3.8+0.2) = 8 requests/s. Waiting users create fewer new attempts. This is correct for that user model but not evidence that independent arrival demand fell.
  7. The intended sends at seconds one, two and three are absent. Retain scheduled send, actual send and terminal events; report generator lag and the achieved schedule. Missing requests are neither zero-latency completions nor known failures.
  8. First content is 323 ms; (3117 − 323)/127 = 22 ms mean token gap; E2E through terminal is 3120 ms. There are 127 gaps, not 128, and a 3 ms terminal tail. With only chunks, report chunk events and intervals; token-level ITL is unavailable.
  9. The estimated subtotals are 320 ms and 140 ms, so B is better by 180 ms under equal remaining costs. Different decode demand, stale queue estimates, transfer cost or cache uncertainty could change the outcome. No cache hit-rate slogan settles it.
  10. The payload lower bound is 200 ms, already greater than the 100 ms saving. This latency comparison does not justify the split. Improved overall capacity, isolation, specialized hardware, extra queueing and recovery costs need their own workload-based evidence.
  11. Stop new admission to the draining worker; the new request should route elsewhere or receive the declared reject. Let the active stream finish before the budget or terminate explicitly, then observe its state release and process/port cleanup. A closed socket without worker release is insufficient.
  12. The request-weighted mean is 55 ms; the pooled gap mean is 1100/101 ≈ 10.89 ms. Label “mean of two per-request mean ITLs” or “mean across 101 observed token gaps” respectively. Choose based on the question, not which number looks faster.
