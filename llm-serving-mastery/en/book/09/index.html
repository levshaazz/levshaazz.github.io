From a gateway to a production unit

Topic 08 left you with a gateway worth trusting: it validated inputs, refused overload with honest 429s, cancelled what clients abandoned. But the service lived in "works on my machine" land: whatever Python the host happened to have, pip installs at runtime, the cwd deciding what the app sees. In production this is not an inconvenience — it is an incident: a pod that behaves differently on different nodes has no contract.

This chapter turns the service into a production unit and answers four questions that cost real money in production. Speed: what does a rebuild cost after an edit, and why does a good build measure rebuilds in seconds. Size: what the megabytes of an image are made of, and which price you pay for each way of delivering model weights. Contract: does it survive the container boundary without a single change. And recovery: the pod died of memory — what the journal shows and how fast it comes back.

The course motif stays the same: the image is the blueprint of a mobile kitchen, the container is the kitchen at work, layers are its modules. V2 adds the fleet: a park of identical kitchens where one fell over, repaired itself, and was back in a second. The lab reproduces this cycle for real — with a tiny but genuine LLM in the container, on an ordinary laptop, no GPU.

Your first five minutes with Docker

If Docker is new to you, the lab starts with one command: docker run hello-world. It pulls a tiny image from a registry and runs it — the first artifact appears before any theory. Then the four daily commands: docker ps (what runs), docker logs (what it says), docker inspect (what it is), docker images (what you built). The whole lab journal is built on these commands: inside the notebook a guarded helper calls them, so every number lands in the journal instead of terminal history.

Agree on the words early. An image is an immutable blueprint: the application's filesystem with dependencies, stacked in layers. A container is an ordinary process on your machine, launched from that blueprint in isolation: its own filesystem, its own name, bounded resources — the same Linux kernel, no "little virtual machine". That is exactly where the seconds of start and restart this chapter measures come from. Production calls these blueprints pods and their failures CrashLoopBackOff; by the end of the chapter that vocabulary is yours.

An image is ordered layers

Every Dockerfile instruction produces a layer: a diff over the layer below, frozen into the image. An image is an ordered stack of these layers plus a manifest. This is not an implementation detail — it is the mechanism behind three behaviors you use daily: how builds become fast, how pulls become cheap, and how edits stay cheap.

A layer's build cache is valid only if that layer and every layer below it are unchanged. Change one file an early layer copied, and everything above rebuilds. The working rule: order instructions from most stable to most frequently changing. The lab freezes this order and three invalidation predictions into build-plan.json before the first build — the same predict-before-measure discipline as Topics 06–07, now about bytes instead of tokens.

Two build caches: layers and content

Compiling llama.cpp from sources takes minutes even on a fast machine, and it is the perfect proving ground for build speed. Two caches are often confused. The layer cacheremembers instructions: a layer does not re-run while its inputs are unchanged. Thecontent cache (a cache mount; ccache in the lab) remembers bytes: object files live outside the layers and survive compile-layer invalidation.

The lab measures three runs of one real compilation: a cold build with an empty ccache, a rebuild with zero edits, and a one-line patch with a warm compiler cache. Course records for this chapter: 142 s cold (10 vCPU), 0.4 s unchanged rebuild, 44 s one-line patch with warm ccache. The order of magnitude is the lesson: seconds versus minutes versus the full compile; on your machine you will record your own numbers and compare the magnitudes, not the exact values.

This block caught a genuinely live trap. The first Dockerfile draft omittedca-certificates: apt worked fine — it speaks plain HTTP to Ubuntu mirrors — whilegit fetch died with server certificate verification failed. CAfile: none; GitHub requires TLS. The tooling layer is a contract with the network: list everything the build will touch. The story became a level-B student exercise: find the three packages without which the tooling layer breaks its promises.

What ccache actually remembers

Why does a one-line patch cost 44 seconds — not 0.4 and not the full 165? The answer is in the compiler cache's design. Before compiling each translation unit, ccache hashes everything that affects the result: the compiler version, the flags, the preprocessed text of the file — including every header it pulls. Hash match: the object file comes from the cache. Miss: the file recompiles.src/llama.cpp is a heavy hub in the llama.cpp tree: its preprocessed text changes on an edit, and so does everything that includes it. So 44 seconds is the recompilation of affected units plus linking — not "everything again" (that would be ~165) and not "nothing" (the layer cache path would be ~0.5).

Three working rules follow. The compiler cache does not replace layer order: it speeds up the rebuild AFTER invalidation, while the layer cache avoids the invalidation entirely; they work on different events. The cache is environment-sensitive: changing the compiler or flags in the tooling layer empties it — which is why the tooling layer is pinned together with the base. And the cache is not an artifact: object files keep traces of build paths, so what ships in the runtime image is the linked binary, never the cache itself. All of this is testable in the lab: the third build run with a warm mount is an experiment over exactly these rules.

Frequently asked questions

Why not vLLM? The lab engine is chosen by one criterion: it must fit on a student laptop and come up in seconds. vLLM with its torch and CUDA stack is a 10.4 GB compressed image and minutes to start; llama.cpp with 0.5B Q4 is 1.18 GB and a second to /health. The production patterns — limits, OOM, backoff, restart economics — are identical; the scale is not, and the chapter says so honestly. The GPU image variant stays an owner demonstration.

Why a 400 m limit rather than, say, 700 m? Because the incident must be deterministic. At 700 m, a replica with ~760 MB resident sits in a gray zone: the outcome depends on how many pages were already touched, and on another machine it may never fire. 400 m is below any resident configuration — the kernel fires reliably, and the crash-loop curve is recorded the same way everywhere. The production lesson is the same: a limit that sometimes fires is worse than a limit you can reason about.

Why --memory-swap equal to --memory? The pair disables swap: without it, a container hitting the limit starts paging to disk — the incident becomes not an OOM but endless, slow breathing through swap. The incident's determinism costs one flag line.

Where is the GPU? Nowhere — and that is stated honestly. Layers, caches, sizes, the contract, limits, OOM and restarts know nothing about the accelerator. The GPU version of this topic is the same blueprint with a CUDA base, a vLLM pin and --gpus, and it is demonstrated by the owner with preserved evidence rather than executed by students.

What if a student has no Docker at all? The notebook stays green: every docker cell is guarded and prints an honest skip. Plan mode covers predictions, transcripts, journals and diagnoses; live numbers are collected on any Docker machine — in class, at home, or on any cloud runtime.

Lean means pinned, not pretty

The naive v0 of the lab works: a floating :server tag, root, no health declaration. It exists to become the baseline. Your v1 fixes four things, one line each. The digest pin:FROM ghcr.io/ggml-org/llama.cpp@sha256:… — a tag floats, a digest is exact bytes. A non-root user: a smaller attack surface. A HEALTHCHECK on /health: the daemon knows whether the service lives. And a deliberate choice of weight delivery — the next section.

The pin is not pedantry, and the lab proves it with a live fact: fresh llama.cpp builds replaced the --mlock and --no-mmap flags with --load-mode …. "It worked yesterday" breaks not only in image bytes but in the CLI underneath. Metadata layers (LABEL, HEALTHCHECK, USER) weigh zero bytes — pins and probes cost nothing in size and change everything in reproducibility. In the lab v0 and v1 build back-to-back and docker images shows identical sizes — the cleanest proof that security and pins are free.

Model artifacts: bake, mount, or download

For an LLM image the size accounting is brutal: the llama-server binary is single-digit megabytes, the Qwen2.5-0.5B Q4_K_M weights are 491 400 032 bytes. No matter what you do to the Dockerfile, the weights dictate the size — so the real question is not "how to shrink" but which price you accept for delivering the weights.

Bake (COPY into the image) gives a self-sufficient artifact, but every pull pays half a gigabyte extra. Mount (-v from the host) keeps the image lean but ties the fleet to one host disk. Download at start makes the network the dominant recovery term — the worst choice for the crash-loop scenario. The lab mounts by default (the fleet lives on one machine) and offers bake as an optional measurement: course record, the COPY layer adds ~491 MB, 1.18 GB → ~1.67 GB.

The third option — download at start — deserves an honest read, because it looks free and is not. The weights arrive at the moment the pod must already answer: the network becomes the dominant restart term, and in a crash-loop scenario it is paid on every bring-up. Its honest home is ephemeral nodes with a shared weight cache — where the first start on a node is expensive and the rest are nearly free. Choosing a delivery method is choosing WHERE the bill lands: in the pull (bake), in host dependence (mount), or at recovery time (download). Read the price table together with the restart curve of the incident block — it is one economics seen from two sides.

The size ledger: three orders of magnitude

docker history is the ledger, and it proves the arithmetic: an image's size is the sum of its layers. Course records line up the contrast this chapter exists for. Our from-source runtime image: 150 MB — only llama-server and runtime libraries; the compilers stayed in the builder stage. The upstream llama.cpp:server image: 1.18 GBunpacked. The published vllm/vllm-openai: ~10.4 GB compressed — the full torch and CUDA stack. The lab does not build vLLM; the number is the contrast. Multi-stage is the difference between seconds and minutes on every pull of every fleet machine.

The same ledger answers "what if we bake". The COPY layer with weights reads as +491 MB in history, and the price shows up twice: on every pull and on every start's extraction. In the crash-loop scenario of the next section that price becomes seconds of downtime — the size ledger and the recovery economics are one table.

Launch and probes across the boundary

The container lives in its own network spaces, and the road from the laptop is three flags.-p host:container — the port; -v host-path:/models/model.gguf:ro — the weights, mounted read-only; --memory — the wall the pod lives behind. Inside is a real tiny LLM: llama-server with Qwen2.5-0.5B, a 1024-token context, CPU.

The contract we verify was born in Topic 08: the gateway map — validation, the bounded queue, timeouts — remains the reference point against which "nothing changed" is measured.

The verification probe repeats the course contract from Topics 04/08: GET /health→ 200; POST /v1/chat/completions → non-empty reply text; usage.total_tokens→ a number above zero. Nothing in this contract changed because the server moved into a container — that is the entire point of an image: behavior no longer depends on the host. Course records: start-to-first-/health about one second, an "OK" reply to a one-word prompt in 0.15 s on CPU. Your numbers go into your machine's contract-journal.json.

Each probe maps to a failure class you will meet in production. /health returning anything but 200 means the process inside is not listening — wrong flags, wrong port mapping, or a crash loop in progress. A completion that returns but carries empty content means the contract's happy path broke — usually a rendering or template issue, which Topics 04/08 taught you to catch by reading actual bytes. Usage reporting zero tokens means accounting broke upstream of the reply. Three probes, three different suspects — and none of them care that the server sits in a container: across the boundary the contract is the only thing you can see, which is exactly why it must be strong.

The production incident: a pod with a wrong limit

Now the culmination — a production scenario, reproduced on your laptop. A replica runs with--memory 400m against a resident appetite of ~760 MB (491 MB of weights plus KV cache and buffers). The prediction is frozen before the run: what will the kernel do when the process touches a page past the wall? You know the answer from Topic 08 — except this time it is not the queue refusing, it is the cgroup.

Two facts are visible from outside: exit code 137 and the"OOMKilled": true field in docker inspect. 137 is 128 + 9: the kernel delivered SIGKILL, the strongest possible termination, delivered from outside the process. No traceback, no Python exception: the decision to kill was the kernel's, not the application's. The journal tail breaks off mid-model-load — the evidence of where the process crossed the wall.

The lab's determinism comes from --load-mode mmap+mlock: mmap file pages are evictable, and the container could keep living by breathing through eviction; mlock pins the pages in RAM, so the limit fires reliably. It is the same mechanism by which a production pod that ate its requests pays for its limit.

Crash loop and backoff: how the orchestrator refuses to finish you off

One OOM is half the story. The lab's pod runs with --restart=on-failure, and real production morphology begins: restart → OOM again → restart. The lab observation (course record): 5 restarts by 6.2 s, 7 by 12.3 s, 8 by 18.4 s, then a pause — the intervals grow. The orchestrator applies exponential backoff: docker from 100 ms to a 1-minute ceiling, Kubernetes from 10 s to 5 minutes, and calls it CrashLoopBackOff. The point is identical: do not hammer a dying pod, do not burn resources, do not flood the logs.

The measured restart curve is a diagnosis of configuration, not flakiness. It reads: the pod dies the same death every time (OOMKilled=true each time), so the cause is not transient but structural — the limit is below residency. The corresponding fix is not "restart it again" but recompute the limit.

Restart economics, term by term

After the fix — sizing: limit = resident memory with headroom (~1.5×; in the lab 762 MB measured → 1200 m). Then the "down → answering again" time is measured, and it itemizes into named terms — the same decomposition as cold-start economics, applied to an incident.

This chapter's vocabulary is the direct bridge to Topic 11: a container with a restart policy ≈ a pod with a controller; exit 137 with OOMKilled ≈ the pod's OOMKilled status; exponential backoff ≈ CrashLoopBackOff; --memory ≈ resources.limits; HEALTHCHECK ≈ liveness/readiness probes. Today you measured each of these mechanics on bare Docker — in Kubernetes you will read them as native.

How we caught the port ghost: debugging as part of the plot

The first draft of the lab carried a defect that became a lesson. The recovery cell attached to the same port 8099 where the Block-3 container was still living, and wait_healthyinstantly caught a stranger's replica answering. The journal recorded "0.0 s to ready", "0 B resident memory" and restarts that never happened. No magic: a health probe does not know WHO answers on the port — only that someone answered 200.

The diagnosis took one check: comparing artifact timestamps, the executed notebook version and live docker processes. The fix is three lines: the repaired replica gets its own port (port_host + 1), a warm-up call precedes docker stats sampling, and time-to-ready is recorded as measured — zero seconds is a valid measurement when it is yours. The student's moral: port isolation is not bureaucracy but the condition of honest measurement; and an "instant success" probe is a reason for suspicion, not celebration.

The same evening left two more entries in the "failures as data" collection. kill -9 1from inside a container does not kill PID 1: the kernel blocks fatal signals to a namespace's init from processes of the same namespace — simulating a crash "from inside" is pointless, a real OOM will do it properly. And a manual docker kill experiment showed something else: manually stopping a container disables its restart policy until the daemon restarts — the orchestrator distinguishes "it fell" from "someone stopped it by hand". Both traps now live in the diagnosis cell's transcripts.

The fleet memory budget: requests-and-limits arithmetic

A three-replica fleet on a laptop is already capacity planning — the same work production does with requests and limits. The lab's arithmetic: one replica with a 1024-token context eats ~760 MiB resident (course record; your machine — your docker stats). Three replicas: about 2.3 GiB, plus the weights' page cache, plus the daemon itself. A 3.8 GiB Docker Desktop VM fits this fleet without maneuvering room; at 6 GiB it is comfortable. Two sizing rules follow, and they transfer to k8s verbatim.

First: limit = resident × headroom. The headroom exists for named events, not superstition: context peaks (more tokens in a batch — more KV cache), allocator fragmentation, concurrent load spikes. The lab uses ×1.5: 760 MB → 1200 m. Less headroom — the crash loop returns; more — dead reserve nobody can occupy. Second: request ≈ observed resident, limit = request × headroom — in k8s, the difference between request and limit is exactly this: what the scheduler is guaranteed and what the kernel is allowed to take. The honesty check: if your limit never approaches peak residency, you do not know your load profile; if it has ever crossed it, you know it too well.

Security defaults, not security options

The economics of refusal are shared between Topic 08's queue and this topic's limit: an honest refusal beats silent degradation, whether it is a 429 in user space or a SIGKILL from the kernel.

Every v1 default is one Dockerfile line, and the whole fleet inherits each: the digest pin (byte-exact reproducibility), the non-root uid (a smaller blast radius), the HEALTHCHECK (the daemon knows the truth about liveness), the memory limit (admission control). The lab's live log adds the server's own honest warning: "no API key is set and CORS allows all origins" — production adds authentication, TLS and network policy, but those are policies around the image, not replacements for the defaults inside. Limits are Topic 08's admission control, moved from the gateway's queue into the kernel: an honest wall beats silent degradation.

Note the gradation of responsibility. The image is responsible for defaults being right and host-independent: uid, pin, healthcheck, limit. The orchestrator is responsible for limits being filled meaningfully: requests from measurements, limits with justified headroom. The application is responsible for reporting overload honestly before it gets stopped: the 429 queue from T08 is the first line of defense, the cgroup the last. Three levels, three different files in the repository, one philosophy: a declared refusal is cheaper than a surprise.

SBOM and the supply chain

An SBOM is the inventory of everything inside the image: OS packages, binaries, versions. One image — one document. Three questions it makes explicit. A floating base tag: :servertoday and in six months are different bytes; the digest is the antidote. Dependencies without boundaries: the source pin (LLAMACPP_SHA) and the weight pin (file name plus exact size) are versions with borders. Layers remember everything: a file deleted by a later instruction still lives in the earlier layer; a secret in a layer is a secret forever. docker historyreads what you "erased".

The diagnostic ladder: a full post-mortem of one death

Walk the incident the way an on-call engineer does — down the ladder from symptom to fix, skipping no rung. Symptom: monitoring shows one of the fleet's three endpoints flapping, anddocker ps shows the t09-inc container constantly restarting. The first reflex is not "restart it again" but a question: how many times has it already restarted?docker inspect answers with RestartCount — and watched over two minutes, the counter grows while the intervals between restarts double. Diagnosis one: crash loop. Cause: not yet.

Second rung — the process's last sortie. docker logs --tail 20 shows a short life: the server started, began loading the model, and went silent mid-load. The tail contains no exception and no traceback — there never were any: the application did not live long enough to understand anything. In parallel, docker inspect returns the two fields that together read as a verdict: "ExitCode": 137 and "OOMKilled": true. 137 is 128 + 9: shells encode signal deaths as 128 plus the signal number; signal 9 is SIGKILL, the one signal that cannot be caught. The sender is neither the application nor the runtime: it is the kernel's cgroup mechanism, protecting the node's memory from a process that crossed a declared wall.

Third rung — reconstructing the arithmetic. Why did the process cross the wall at all? The limit is 400 m; the 491 MB of weights load with mmap+mlock, meaning pinned in RAM; the context KV cache and engine buffers sit on top. Resident memory must exceed the limit before the first answer — death mid-load reproduces on every start. Not "sometimes", not "under load": the configuration guarantees the outcome. Such incidents are the cheapest to diagnose and the most annoying to operate: they fire on every deploy and read as flakiness until someone does the arithmetic.

Fourth rung — the fix and its proof. The limit is recomputed from a measurement, not a hope:docker stats on a healthy replica shows 760 MiB; headroom ×1.5 gives 1200 m. The container restarts with the new limit — and now the second half of the fix matters: theproof that the crash loop has ended. RestartCount stops growing; /health answers; repeat restarts settle in ~1.3 seconds. The journal records both numbers — before and after — with the named mechanism between them: "the limit was below residency; it is now above with headroom; the cgroup no longer fires". The four-rung post-mortem — symptom, evidence, arithmetic, proven fix — transfers to k8s without a single change: only the commands that pull each rung are different.

The backoff constants differ between docker and k8s, and the difference is telling. Docker grows from 100 ms to a one-minute ceiling: it assumes a local context, where a restarted process either recovers quickly or is visibly broken. Kubernetes grows from 10 seconds to five minutes: it assumes a cluster, where every dead cycle costs scheduler resources and shows in fleet-wide metrics. The morphology is identical — exponential growth with a ceiling; the constants express the price of a wrong restart in each environment. When reading an unfamiliar monitoring system, remember both orders of magnitude: intervals in fractions of a second are docker-like policy; intervals in tens of seconds and minutes are k8s. And the mount that delivers the lab's weights carries two deliberate details: an absolute path (a relative one is "works on my machine" land, the very ground this topic moves the service out of) and :ro — a container with write access to the weights is a container able to silently corrupt the shared cache every replica on the node divides.

The topic glossary

Image — an immutable artifact: ordered layers plus a manifest.Layer — the filesystem delta of one Dockerfile instruction. Layer cache — reusing a layer while neither it nor anything below changed. Cache mount — a directory outside the layers (ccache in the lab) that survives layer invalidation. Multi-stage — build in a builder stage; only artifacts are copied into runtime. Digest — the sha256 of the image's exact bytes; a tag floats, a digest does not. .dockerignore — what never enters the build context and is therefore never remembered by layers. HEALTHCHECK — the liveness declaration the daemon polls; in k8s, liveness/readiness probes. Non-root — the process runs under an unprivileged uid. The container boundary — port mappings, mounts and limits through which the laptop reaches the isolated process. Resident memory — what the process holds in RAM right now; read it with docker stats.Limit (--memory) — the cgroup wall; the kernel's admission control.OOMKill / exit 137 — the kernel's SIGKILL on limit violation; 128 plus the signal number. Crash loop — a pod dying repeatedly; backoff — the growing pause between restarts; in k8s, CrashLoopBackOff. Restart-to-ready — the time from "down" to "answering /health", itemized into extraction, weight loading, init and the first reply. Bake / mount / download — three ways of delivering weights, three prices. SBOM — the inventory of an image's contents. Pin — fixing a source version (commit, digest, file size) against floating tags.

What this chapter establishes — and what it does not

Establishes. A deployment unit that builds fast (layer cache plus cache mount), weighs honestly (a per-layer ledger, a deliberate weight-delivery price), keeps its contract across the boundary, and recovers in seconds after an honest production incident — with a journal tying every number to your machine and your build.

Does not prove. Seconds and megabytes are local and machine-dependent; the course never quotes them as engine benchmarks. llama.cpp with 0.5B Q4 shows production patterns, not production scale. No real Kubernetes was launched — only its vocabulary on Docker primitives. GPU images and the vLLM fleet remain owner demonstrations. One SBOM of one image is not a security certificate.

Check understanding and transfer

Answer before opening the explanations. The two-caches, restart-curve and recovery-terms questions each test transfer: reproducing the notebook is not enough if you cannot predict what changes under a different limit or a different delivery choice.

  1. Pick the layer order before you build. A Dockerfile must install dependencies and copy sources. Variant A copies everything, then runs the install. Variant B copies the dependency file, runs the install, then copies the sources. A developer edits one source file 20 times a day and touches dependencies once a month. Count the layer rebuilds per day in each variant.
  2. Which cache survives which change. A build takes minutes. Scenario 1: rebuild with zero edits. Scenario 2: change one line of sources. Run both scenarios without a cache mount, then with a warm compiler cache. What times do you expect in each of the four runs, and why?
  3. Why git died while apt was fine. A tooling layer installs build-essential, cmake and git but not ca-certificates. apt-get update works, then git fetch over HTTPS fails with "CAfile: none". Name the mechanism and the minimal fix.
  4. Sum the layers, price the pull. A from-source runtime image is 150 MB. The upstream llama.cpp:server image is 1.18 GB unpacked; the published vLLM image is about 10.4 GB compressed. How many seconds does a cold pull of each take on a 25 MB/s link, and what does this arithmetic say about a fleet?
  5. Bake, mount, or download. The model weights are 491 MB. Baking adds them to the image; mounting attaches them from the host; downloading pulls them over the network at start. Estimate the image size, the warm-machine start, and the price of each option in a crash-loop scenario where the pod must be back in seconds.
  6. Read the exit code. A replica with 491 MB weights and a 1024-token context runs with --memory 400m and --load-mode mmap+mlock. The container dies with exit code 137 and docker inspect shows "OOMKilled": true. Why 137 and not 1 — and why is mmap+mlock needed here?
  7. Read the restart curve. A pod with a restart policy keeps dying of OOM. Observation: 5 restarts by 6.2 s, 7 by 12.3 s, 8 by 18.4 s, then a pause. Why do the intervals grow, and what does Kubernetes do differently with the same behavior?
  8. Itemize the restart into named terms. After the sizing fix, restart-to-ready is measured at 1.07 s and 1.08 s across two runs. Name the terms of that time and explain which lab decisions made each term cheap.
  9. A tag is not a version. In March a team builds FROM ghcr.io/ggml-org/llama.cpp:server. In September they rebuild on a fresh machine and the image behaves differently: the fresh build does not know the --mlock flag, although nothing changed in their repository. Name the mechanism and the two-part fix.
Show the nine answers and their limits
  1. Pick the layer order before you build. In variant A the COPY layer changes on every source edit, and the install layer sits above it, so all 20 edits rebuild the dependency layer. In variant B a source edit rebuilds only the final COPY layer: the dependency layer and everything below it keep their cache hits. Per day that is roughly 20 reinstalls versus zero — the order IS the cache policy.
  2. Which cache survives which change. Scenario 1 without the mount: fractions of a second — the compile layer was not invalidated, the layer cache answered everything. Scenario 1 with the mount: the same, the mount adds nothing. Scenario 2 without the mount: a full recompile — editing sources invalidates the compile layer, and the layer cache has nothing to offer. Scenario 2 with warm ccache: minutes — object files live outside the layers and survive the invalidation. The layer cache remembers instructions; the content cache remembers object bytes; they protect against different events.
  3. Why git died while apt was fine. apt talks to Ubuntu mirrors over plain HTTP — no TLS needed, so the layer built fine. git fetch speaks HTTPS to GitHub and verifies the server certificate against a root CA bundle; without the ca-certificates package there is nothing to verify against, so the handshake is rejected. The fix is one package in the tooling layer. The broader moral: the tooling layer is a contract with the network — list everything the build will touch.
  4. Sum the layers, price the pull. 150 MB ÷ 25 MB/s ≈ 6 s; 1.18 GB ≈ 47 s; 10.4 GB ≈ 416 s ≈ 7 minutes. The difference is paid on every machine and every redeploy: across a 20-replica fleet, switching to the own runtime image saves minutes per node. Multi-stage is not aesthetics — the compilers stayed in the builder stage and never pay the pull tax.
  5. Bake, mount, or download. Bake: 1.18 GB → ~1.67 GB image, every pull pays half a gigabyte extra, but a restart does not depend on the host or the network. Mount: the image stays 1.18 GB, a restart reads weights from host disk — with a warm page cache that is nearly free. Download: small image, but the network becomes the dominant restart term — hundreds of megabytes over the wire at the moment the pod should already answer. For fast recovery on your own host, mount with a warm cache wins.
  6. Read the exit code. 137 = 128 + 9: the kernel delivered SIGKILL (signal 9) when resident memory hit the cgroup wall. Exit 1 would mean the application decided to fail; here the kernel decided. mmap+mlock is what makes the outcome deterministic: mmap file pages are evictable and the container could keep living by breathing through eviction; mlock pins the pages in RAM so the limit fires reliably — exactly like production, where a pod past its requests pays for the limit.
  7. Read the restart curve. The intervals grow because the orchestrator applies exponential backoff: 100→200→400→800→1600 ms, then seconds — it refuses to hammer a dying pod, burn resources and flood logs. Kubernetes calls the same behavior CrashLoopBackOff and grows from 10 s to a 5-minute ceiling; docker grows from 100 ms to 1 minute. Same morphology: the measured restart curve is a diagnosis of configuration (the limit is below residency), not flakiness.
  8. Itemize the restart into named terms. The terms: layer extraction (unpacking the image — the tiny metadata layers of v1 are free), weight loading (a mount over a warm page cache after the first run — nearly zero), server init plus the first /health (hundreds of milliseconds for a 0.5B Q4 on CPU). The size-block decisions — not baking weights, keeping the image lean — are paid back right here: size minimization IS recovery speed.
  9. A tag is not a version. The tag floated: the registry moved :server to a newer build, so September bytes differ from March bytes under the same tag; the CLI drifted too — flags moved into --load-mode. The fix: pin what you build from — the exact source commit — and what you consume — the image digest (FROM image@sha256:...). "It worked yesterday" breaks exactly here.
