Docker for LLM inference

The Topic 08 gateway becomes an immutable image: ordered layers as cache policy, a lean pinned multi-stage build, the same API contract probed across the container boundary, cold/warm startup economics measured on the student's own machine, deliberate failure drills (tag drift, memory-limit OOM), and an SBOM-backed supply-chain look. CPU images for everyone; the CUDA/vLLM variant is an owner demonstration.

This chapter follows the approved Topic09 arc. The lab runtime is the student's local Docker with CPU images; the GPU variant of the image (CUDA base, vLLM pin, --gpus) appears only as declared configuration and an owner-run demonstration. Every measured byte and second in the lab belongs to the student's own machine and build.

From a working service to a portable contract

Topic 08 left you with a gateway worth trusting: it validated inputs, refused overload with an honest 429, mapped engine failures to honest status codes, and cancelled what clients abandoned. But that service lived in "works on my machine" territory. It installed its dependencies at runtime, ran on whatever Python the host happened to have, and read its surroundings from the current directory. The contract it promised was enforced by code that depended on a machine you do not control.

This chapter closes that gap by changing the unit of delivery. The application becomes animage: an immutable artifact with pinned dependencies that runs the same way on every machine with a container runtime. The engineering virtues are concrete. Lean images, because every megabyte is paid on every pull. Deterministic builds, because the order of layers is the cache policy. Honest startup economics, because the cold path is counted term by term, not hoped away. And configuration that admits what the GPU actually is: a version matrix, not magic.

The course motif for the topic is the mobile kitchen. An image is the blueprint of a self-contained kitchen; a container is that kitchen running; layers are its modules, assembled bottom-up. Rearrange the modules and you have rebuilt the kitchen. The metaphor earns its keep in one place: the blueprint, not the chef, decides what the kitchen does. A service whose behavior depends on the host has no contract; an image is how the contract travels.

The naive image and the first proof

The lab does not begin with the beautiful Dockerfile. It begins with a deliberately naive one — full base image, code copied before dependencies, root user, no health declaration — and builds it. By the sixth executable cell of the notebook, that naive image has become a container, the health endpoint has answered through the host-to-container boundary, and the loop you will spend the chapter refining is proven: build, run, probe, journal. The first working artifact matters more than the first elegant one, because everything after it is a measurement against something.

The naive image also earns its keep as a baseline. Its size, its startup seconds and its cache behavior are the "before" of every claim the lab makes. When the lean rewrite arrives, the improvement is not asserted — it is the delta between two measured runs of the same journal. Every docker-invoking cell in the notebook is guarded: on a machine without the daemon it prints an honest skip line and moves on, so the notebook validates green in CI and in Colab while still running for real on any student machine that has Docker.

One boundary is declared up front. The production variant of this image — CUDA base, pinned torch and vLLM stack, --gpus at run time — exists in the course as configuration cards and as an owner-run demonstration with retained evidence. Students never execute it and never quote numbers from it. The mock engine inside the container keeps the whole loop CPU-only and honest: every measured number in your journal is measured on your machine, against your build, and the course never quotes it as an engine benchmark.

The smoke build also introduces the pattern that keeps the notebook honest everywhere it runs. Every cell that invokes the docker CLI first asks the daemon, with a short timeout, whether it is actually there. If it is not, the cell prints one explicit skip line — the same sentence every time — and does nothing else. There is no pretend progress, no synthetic output standing in for a measurement, no silent success. The plan-mode cells that remain (the frozen prediction, the staged application, the journals, the reference-matrix plot, the transcript diagnoses) execute everywhere, which is why the notebook validates green in CI and in a free CPU runtime while running for real in the lab. When you read a student notebook that claims results from a machine that could not have produced them, you are reading the defect this pattern exists to prevent.

An image is ordered layers

Each instruction in a Dockerfile produces a layer: a diff over the layer below it, frozen into the image. The image is the ordered stack of those layers plus a manifest. This is not an implementation detail — it is the mechanism behind three behaviors you will use daily: how builds get fast, how pulls get cheap, and how edits stay cheap.

The third behavior is the one that bites. A layer's build cache is valid only if that layer and every layer below it are unchanged. Change one file that an early layer copied, and everything above rebuilds. The practical rule follows immediately: order instructions from least to most frequently changing. System packages first, dependency manifests second, code last — so that the expensive dependency layer survives the twenty code edits of an ordinary day and only the cheap final layer rebuilds.

The lab makes you commit to this rule before you build anything. The first deliverable is a frozen plan: which of three candidate instruction orders you choose, and which edits you predict will invalidate which layers. The prediction is written into a JSON file with the rest of the plan before the first build runs — the same predict-before-measure discipline as the Topic 06 knee forecast, applied to a build system. Later, docker history reads the built image's actual layer stack, and the prediction meets its judge.

The cache-hit condition

Two consequences are worth stating plainly. First, the cache is a chain, not a set: there is no "partial" hit that skips a changed layer and keeps the ones above. Second, the condition makes the layer order a policy decision, not a style preference. An image whose expensive layer sits above a frequently edited file pays the full cost of that file's churn on every build; the same image with two instructions swapped pays it once a month. The lab's frozen prediction exists so that this consequence is something you assert before seeing it, and can therefore recognize as understanding rather than luck when docker history confirms it.

A warning in the same breath: the local daemon's cache is not the registry's cache, and neither is your CI's. The lab's claims about cache behavior hold for the local daemon it measured; a shared builder with different layer provenance may behave differently. Naming where a mechanism was observed is part of the claim.

The prediction exercise also has the quieter value it had in Topic 07: it slows you down at exactly the moment speed is dangerous. A build is fast; a build that silently reinstalls everything is also fast; the difference is visible only to someone who predicted which layers should have survived. When the frozen prediction and the built image disagree — a layer rebuilt that should have been cached, or a cache hit where you expected churn — the gap points at a mechanism you did not model: an instruction that embeds a timestamp, a COPY that catches more files than you meant it to, a base tag that moved. Each such surprise, written down, is worth more than a dozen builds that matched the plan, because it is the only one that taught you something the plan did not already contain.

Lean is a contract with the network

Every megabyte in an image is paid on every pull by every machine that fetches it, and again on every extract during a cold start. Lean is therefore not tidiness; it is a recurring cost you choose on behalf of your fleet. The lab quantifies this with a size accounting: the base layer, the dependency layer and the application layer are itemized with docker history and compared against the frozen plan, for the naive v0 image and for your lean v1.

The accounting produces the artifact this chapter is really about: a table where every layer carries a one-sentence justification. The slim base is there because the gateway needs libc and Python, not a compiler toolchain and five hundred system packages. The dependency layer is there because FastAPI and uvicorn are pinned — exact versions, no ranges. The code layer is there because it is the only layer that changes daily, which is why it is last. A layer that cannot be justified in one sentence is a layer to remove.

Pinning deserves its own sentence. A requirement like fastapi==0.115.8 is a promise that today's build and next quarter's build install the same code. A range is a lottery that redraws on every build. The shipped application's requirements file is fully pinned, and the lab's supply-chain stretch makes you articulate why the same discipline applies to the base image tag — and why, for real guarantees, a tag is still not enough.

Multi-stage builds and the honest context

A multi-stage build compiles in one image and ships another. The builder stage may carry a compiler, headers and the pip cache — hundreds of megabytes of machinery. The runtime stage starts from the slim base and copies only the installed artifacts and the code. Nothing that existed only to build the software rides along in the image that serves it. The gain is size; the deeper gain is surface: fewer packages, fewer binaries, fewer things that can be probed or exploited.

The second half of lean authoring never appears inside the image at all: the build context. Everything in the context directory is sent to the daemon on every build, and anything an instruction copied is frozen into a layer. A .dockerignore file is the list of things the context must never see — journals, virtual environments, version-control state, editor droppings. What the context never sees, no layer ever remembers. The lab makes you write this file yourself, because the failure it prevents (an image that quietly contains your results directory) is discovered only after it ships.

The same memory governs secrets. A credential added in one instruction and deleted in the next still lives in the earlier layer; docker history reads what you erased. The rule is absolute: no secret in any instruction, ever. Configuration travels in environment variables at run time, and the image carries none of it.

Run and probe across the container boundary

A running container lives in its own network namespace. To reach it, a host port is mapped to the container port; configuration enters as environment variables; a memory limit arrives as a declared wall. None of this changes the gateway's code — which is precisely the point. The Topic 08 probe suite (health, one completion, an overload burst expecting 429 withRetry-After) now aims at localhost:mapped-port, and it must passunchanged.

That "unchanged" is the test's whole meaning. The contract you specified in Topic 08 was a promise about behavior, not about where the behavior runs. If the suite passes without modification, the boundary between host and container has been crossed and the promise held. If a probe fails only inside the container, the image — its base, its dependencies, its configuration — is the suspect, not the contract. Debugging improves sharply the moment you trust the contract enough to suspect the packaging.

The probe results land in the journal like everything else: one row per probe with expected and actual status, stored in the attempt directory. The overload probe deserves a note of respect — its 429s come from the bounded queue inside the container, driven by the declared mock knobs, and its expected shares are documented in the teacher reference rather than left to student intuition.

The run itself is a student decision, and the notebook treats it as one. The flags that map ports, set the memory wall and pass the latency knob are completed by the student before the container starts, and an unfilled placeholder stops the run with an explicit message instead of launching something half-configured. This is a small mechanical example of a large operational rule: a command that would run with the wrong configuration should refuse louder than it runs. Every operator eventually meets the inverse — a service that started happily on defaults nobody chose — and learns to prefer the refusal.

The map above is what the boundary must preserve: validate, admit, serve, map — with the request id threading from the client through the journal to the reply. If a probe of the containerized gateway cannot reproduce this map request for request, the image did not ship the contract; it shipped something that resembles it. The probe suite from Topic 08 — health, one completion, the 429 overload drill — exists precisely to make that difference observable in minutes, not after an incident.

GPU isolation is configuration, not magic

Everything above runs on any machine with a container runtime, because the engine inside the image is a declared mock. The production question — how does this work with a GPU? — has a configuration answer, and it is worth learning as configuration precisely because it is so often taught as magic.

The GPU variant of the image is a matrix, not a flag. A CUDA base image compatible with the driver on the host; a torch build compiled for that CUDA version; a vLLM release compatible with that torch; and --gpus at run time to grant the container access to the devices. Any two cells of the matrix can disagree, and the failure modes are version errors, not logic errors. This is why the course ships the matrix as declared configuration cards, and why the demonstration of the working variant — built, run behind the same gateway, timed — belongs to the owner, with the evidence retained.

What students are responsible for is the discipline the matrix teaches: pin every cell of a compatibility matrix jointly, because they fail jointly. The same discipline reappears in the next section as the weights question, and again in Topic 10 where multi-GPU serving multiplies whatever unit you ship.

Model artifacts: bake, mount, or download

Weights turn the size conversation serious. A small language model is gigabytes; a serving image that bakes them in is gigabytes too. There are exactly three honest ways to get weights into a container, and each buys something and pays something.

Baked weights live in a layer of the image. The pull is heavy, but the cold start is the fastest possible — the artifact is already on disk when the process starts — and the running service has zero host coupling. The image pins the weights: hashable, reviewable, reproducible. Mounted weights stay on the host and enter at run time. The image is small, but the start now depends on a host path, and the artifact has escaped the version control of the image itself. Downloaded weights arrive at container start: the image is small, and every start pays a network download and inherits a network failure mode.

You cannot optimize size, cold start and coupling at once; the trade-off is the content. The figure's directions are declared, not measured — the lab ships the CPU mock with no weights at all, and the production envelope belongs to the owner demonstration. What you should take from the table is the shape of the argument: when someone proposes a deployment, ask which column they chose and whether they can name what it costs.

Startup economics: cold and warm, counted

Cold start is where packaging decisions become user-visible seconds. The lab counts it as named terms rather than a single number, because the terms have different owners and different fixes.

The figure shows the same decomposition as structure rather than seconds, deliberately: which term dominates decides which improvement is justified, and dominance is a property of your machine, your network and your image — not of the technique.

The lab's measurement discipline matches the course standard. Both paths are measured on your machine, with progress bars and a journal: cold is remove, create, start, watch the health endpoint; warm is stop and start the same container. The pull term is declared but never measured in the lab — it belongs to the network, not to your image, and a number that depends on someone's link speed has no place in a claim about packaging. What the journal records is the cold and warm wall time of your build, before and after one change.

Reading the result is where the decomposition pays. A cold start of forty seconds says nothing by itself; a cold start whose extract term is half the total says the image is heavy and the fix is size; a cold start dominated by init says the image is fine and the application is slow to begin serving. Two images with identical totals can demand opposite interventions, which is why the sum is never the deliverable — the terms are. The same reading discipline returns in production as startup analysis: services that feel slow to boot are diagnosed by exactly this decomposition, one term at a time, each with its owner and its fix.

Cut the dominant term

The improvement step is deliberately narrow: one change, one named mechanism, one re-measurement. The change the lab steers toward is the v0-to-v1 rewrite itself — smaller base, fewer layers, fewer installed packages — and the mechanisms are named in advance: extract shortens because the layer sum shrinks; interpreter and init shorten because fewer packages are imported. The prediction is written before the measurement; the delta either maps to the named mechanism or the claim is withdrawn.

This narrowness is the method. "We made it faster" is not an improvement claim; it is a mood. A claim names the term it attacked, predicts the direction and approximate size of the effect, and accepts the journal's verdict. When the prediction misses — the delta is smaller than predicted, or the warm path moved when only cold should have — the miss points at a mechanism you did not understand, which is the most useful thing a measurement can say. Teams that skip the attribution step accumulate changes they cannot reason about, and their startup time becomes a random walk with opinions.

The missing prediction is also the earliest warning of a regression factory. A team that changes images without recording which term each change was supposed to move will eventually ship one that quietly lengthened the cold path while shortening something nobody measured — and because no baseline attribution exists, the regression will be discovered by users, in production, at the worst possible moment of the week. The one-change-and-attribute loop is slower per change and faster per year: it keeps the causal bookkeeping that lets ten changes add up to an improvement rather than to a mystery.

The same loop scales beyond this lab. A registry closer to the fleet attacks the pull term; a prebaked artifact attacks a download term; a smaller base attacks extract; a leaner application attacks init. Each proposal is the loop again: predict, measure, attribute. The techniques are interchangeable; the discipline is not.

The queue-economy figure travels with the probes for the same reason. The 429 knee is not a property of the host Python or of the container — it follows from the declared engine latency and the slot count, so it must survive the boundary unchanged. A drift in the knee after containerizing is evidence of an accidental configuration change: fewer slots, a different queue cap, or an unpinned dependency that changed timing behavior. The figure is the expected reading; the probe journal is the actual one; the diff between them is the diagnosis.

Security defaults, not security options

Three defaults separate a container that ships from a container that should not. First, the process runs as a non-root user: a container is not a security boundary by itself, and a root process inside it is an invitation to every escape technique the runtime has not yet patched. Second, inputs are pinned — base image by tag and ideally by digest, dependencies by exact version — because an unpinned input is a supply-chain decision delegated to strangers. Third, the image carries no secrets: not in environment variables baked at build time, not in files deleted by a later instruction, not anywhere. Layer history is permanent; the eraser does not exist.

None of these defaults is expensive at build time, and all of them are expensive to retrofit after an incident. The lab folds them into the v1 Dockerfile where they cost one line each, and the drills section returns to them from the failure side: what a leaked tag, a floating dependency and a forgotten secret look like when they surface.

Two failure drills, deliberately

The lab breaks two things on purpose, because both failures are common, both are legible from the outside, and neither is a Python exception. The first is tag drift: a pull of a tag that does not exist. The daemon answers with exit code 1 and a manifest-unknown message — and the teaching point is that the same mechanism, pointed at a tag that exists but floats, silently changes your bytes instead of failing loudly. The pin, not the pull, is the fix.

The second is the memory-limit OOM. A container runs with a 64 MB cgroup limit and a process that allocates in chunks. When the wall is hit, the kernel kills the process with SIGKILL. There is no traceback, no exception handler, no chance to clean up: the container exits with code 137 — 128 plus the signal number — and the only evidence is the exit code and a log tail. Reading that evidence is a skill: 137 means the decision was never the process's; the limit, the allocation pattern and the kill are the whole story.

Both drills follow the same record format — cause, evidence, fix — and both land in the journal. On machines without Docker the drill cells print an honest skip, and the diagnosis function is exercised on recorded transcripts instead, with the expected outcomes of the live runs documented for the instructor. The diagnosis function is the chapter's last student exercise on purpose: by then you have seen enough of the machinery to write its classifier from a contract alone.

The recorded-transcript pattern deserves a sentence of method. A transcript is a capture, not a live run, and the notebook labels it as such next to the table it produces; on a machine with Docker the live journal is read alongside it, so the two sources of evidence sit in one table with their origin named per row. This is the course-wide distinction between toy, recorded and freshly measured data, applied to failures: the drill teaches the reading skill even where the failure cannot be reproduced, and the live run, when it exists, is checked against the classification rather than against memory.

A third lesson hides in the first drill's design. The nonexistent tag was chosen instead of a slow or flaky mirror because it fails deterministically: same command, same exit code, same message, on every machine. Deterministic failures are teaching instruments — you can write their expected outcomes down in advance, and a fix that only sometimes works is exposed immediately. Flaky failures resist exactly this treatment, which is why production practice pins what it can and turns nondeterminism into declared randomness where it cannot be removed.

Resource limits are admission control

It is worth pausing on what the two refusals in this chapter have in common. The bounded queue refused work in user space: 429, Retry-After, try later. The cgroup wall refuses in kernel space: SIGKILL, exit 137, no negotiation. Different enforcement points, identical engineering value — a declared limit with an honest refusal beats silent degradation.

This is the same principle as Topic 08's admission queue, one layer down. A service that accepts unbounded work degrades invisibly until it collapses; a service with declared limits fails loudly at its boundary, where the failure is attributable. Containers extend the idea to resources: --memory and --cpus are promises with teeth. The lab's OOM drill exists so that you have felt the kernel-side refusal at least once in a place where it was safe to feel it.

The operational moral generalizes. When you size a container for production, the limit is not a formality around the allocation — it is the container's admission control, and the exit code it produces is part of your observability. A fleet where 137s are frequent is a fleet whose limits or whose load model is wrong; the code will not tell you, the exit codes will.

SBOM and the supply chain

The stretch deliverable is an inventory. A software bill of materials lists every package in the image — operating system libraries, Python packages, versions — generated by a tool from the built image. One image, one document. Its value is not the file; it is the three questions the file makes impossible to dodge.

First: what does the base image tag actually pin? The inventory shows the packages that arrived with the base; rebuild months apart with a floating tag and the inventory changes while the Dockerfile does not. Second: what do unpinned dependencies cost? A range in a requirements file redraws a lottery on every build; the inventory of two builds makes the divergence visible. Third: what does the image carry that nobody justified? The inventory is the size accounting extended from bytes to names — and every entry that cannot be justified in a sentence is the same defect as an unjustified layer.

The lab keeps the stretch honest about its own limits: one tool, one image, local tags only. An SBOM is an inventory, not a security certification — it tells you what is inside, not whether it is safe. But "what is inside, with versions" is the precondition for every vulnerability answer you will ever have to give in a hurry, and producing it from a built image costs one command.

It is also the artifact that makes dependency upgrades a reviewable event instead of a gamble. When the next OpenSSL advisory lands, the question "are we exposed?" is a lookup in the inventory plus a pin bump, not an archaeology project across hand-configured hosts. Fleets that cannot answer it re-image everything and pray; fleets that can, patch the three images that actually contain the package. The difference is an hour of inventory discipline in a chapter like this one, practiced on an image whose contents you chose.

The fleet story

Step back from the mechanics and the chapter's real deliverable appears. One image, many machines, identical behavior — that sentence is the precondition for everything the rest of the course builds. Topic 10 scales engines across GPUs; Topics 11 and 12 schedule containers by the fleet. None of it works if the unit being multiplied can drift. Scaling multiplies whatever you ship: an immutable image multiplies a contract; a hand-configured host multiplies a hope.

The chapter's disciplines are the contract's fine print. Layers and cache policy make builds deterministic and cheap. Pinning makes rebuilds reproduce. Limits and health declarations make the runtime's promises explicit. The journal makes your claims about all of it checkable. And the guard pattern — honest skips where the daemon is absent — makes the whole story testable on machines that will never see a container, which is a property your CI will thank you for.

There is also a quieter transfer, from artifacts to arguments. Every habit in this chapter is a habit about evidence: the prediction frozen before the build, the layer justified in one sentence, the improvement attributed to a named mechanism, the failure recorded as cause, evidence and fix. Colleagues who have never built an image still feel the difference between a proposal that comes with this shape and one that comes with adjectives. The image is the exercise; the evidence discipline is the skill. When the fleet topics arrive you will apply it to schedulers and rollouts, and when you leave the course entirely you will keep applying it, because the world has no shortage of loud claims and a permanent shortage of receipts.

When you reach the fleet topics, you will find the same reflexes wearing new clothes: declared requests and limits in a scheduler, health probes as routing signals, immutable images as the unit of rollout and rollback. The names change; the principle — the unit of deployment is a promise, and promises need receipts — does not.

What this chapter does and does not establish

The lab's numbers are yours: image sizes, layer bytes, startup seconds, measured on your machine against your build. They are not engine benchmarks and do not transfer across machines, networks or base image updates. The engine inside the container is a declared mock with synthetic latency; it exists so that the packaging mechanics are learnable everywhere Docker runs, and its timings say nothing about vLLM. The GPU variant of the image is demonstrated by the owner with retained evidence; student materials carry it only as configuration. Registry operations beyond local tags, CI image pipelines, Kubernetes and multi-GPU scheduling are explicitly out of scope here.

What the chapter does establish is a loop you can repeat on any machine: predict a build's behavior before building, make the artifact lean and pinned, prove the application contract across the container boundary unchanged, count the startup path term by term, and turn two deliberate failures into recorded diagnoses. That loop — not any particular Dockerfile — is the transferable asset.

Check understanding and transfer

Answer before opening the explanations. Questions 3, 4 and 5 change one condition each: reproducing the notebook is not enough unless you can predict what changes next.

  1. Pick the layer order before building. A Dockerfile must install requirements and copy code. Option A copies everything, then runs pip install. Option B copies the requirements file, runs pip install, then copies the code. A developer edits one source file 20 times a day and touches requirements once a month. Count the layer rebuilds per day under each option.
  2. Sum the layers, price the pull. A lean image stacks a 130 MB slim base, a 45 MB dependency layer and a 2 MB code layer. A naive image uses a 1024 MB full base with the same app. How much does one cold pull of each cost on a 25 MB/s link, and what do you pay per redeploy?
  3. Cut the dominant startup term. A cold start measures 40 s pull, 12 s extract, 1.5 s interpreter and 0.8 s app init; a warm restart measures 2.3 s. The team switches to a slim base and cuts extract to 2 s. What is the new cold start, and which term should they attack next?
  4. Who pays for the edit. In a four-layer image the measured layer build times are: base 0 s (cached), pip layer 45 s, requirements COPY 0 s, code COPY 2 s. A developer edits one source file; later the same day they add one dependency. How long does each rebuild take?
  5. Read the exit code. A container runs with a 64 MB memory limit while its process allocates 10 MB chunks in a loop. The container exits with code 137. Why 137 and not 1, and roughly how many allocations survived?
  6. A tag is not a version. In March a team builds with FROM python:3.12. In September they rebuild on a fresh machine and the image behaves differently, although nothing in the repo changed. Name the mechanism and the two-part fix.
  7. Why the compiler does not ship. A builder stage with gcc and pip cache reaches 480 MB. The runtime stage needs the 45 MB of installed packages and the 2 MB of code on a 130 MB base. What does the shipped image weigh, and what does multi-stage buy beyond size?
  8. Two refusal mechanisms, one value. The mock gateway runs with a queue ceiling of 4 and a 16-request burst arrives, all faster than the service time. Separately, another container with a 64 MB limit allocates past it. How does each system refuse, and what do the two refusals have in common?
Reveal eight answers and their limits
  1. Pick the layer order before building. Under A, the COPY layer changes on every code edit, and the pip layer sits above it, so all 20 edits rebuild the dependency layer (and invalidate the cache for everything above). Under B, a code edit rebuilds only the final COPY layer: the requirements layer and the pip layer below it are unchanged, so their cache hits hold. Over a day that is roughly 20 dependency reinstalls versus zero — the order is the cache policy.
  2. Sum the layers, price the pull. Lean: 130 + 45 + 2 = 177 MB, so a cold pull takes 177 ÷ 25 ≈ 7 s. Naive: about 1024 MB, so 1024 ÷ 25 ≈ 41 s. The difference is paid on every machine that fetches the image and on every redeploy that cannot reuse the changed layers. This is why lean is a contract with the network, not an aesthetic preference.
  3. Cut the dominant startup term. New cold start: 40 + 2 + 1.5 + 0.8 ≈ 44 s; warm stays about 2.3 s because it never paid pull or extract. The dominant term is now the 40 s pull, which is network-bound — the next honest lever is a registry closer to the fleet or a prebaked artifact, not more image trimming. Improvement claims must name the term they cut.
  4. Who pays for the edit. The code edit invalidates only the top layer: about 2 s. The dependency edit invalidates the requirements COPY and everything above it: the 45 s pip layer plus the 2 s code layer, about 47 s. The once-a-month event costs a minute; the twenty-times-a-day event costs seconds. That asymmetry is exactly what the layer order is chosen to produce.
  5. Read the exit code. 137 = 128 + 9: the kernel delivered SIGKILL (signal 9) when the cgroup memory wall was hit, and the shell encodes a signal death as 128 plus the signal number. Exit 1 would mean the process itself failed and reported it. At 10 MB per chunk the process fits roughly six allocations (60 MB) before the seventh pushes past the wall and the kernel kills it — no Python exception appears because the kill decision was made by the kernel, not by the process.
  6. A tag is not a version. The tag floated: the registry moved python:3.12 to a newer patch build, so September bytes differ from March bytes under the same tag. The fix is to pin what you build from — an exact tag you control plus, for real guarantees, the digest of the reviewed image (FROM python:3.12@sha256:...), and to rebuild deterministically from a locked dependency file. "It worked yesterday" fails exactly here.
  7. Why the compiler does not ship. Shipped: 130 + 45 + 2 ≈ 177 MB; the 480 MB builder never reaches the registry or the hosts. Beyond size, multi-stage shrinks the attack surface: no compiler, no build cache and no build-time secrets ride along, and the runtime image is small enough that pulls and extracts stop dominating the cold start.
  8. Two refusal mechanisms, one value. The queue answers in user space: at most 4 requests are admitted, the rest get 429 with Retry-After — an honest, designed rejection the client can retry. The cgroup answers in kernel space: the process is SIGKILLed and the container exits 137. Both encode the same engineering value: a declared limit with an honest refusal beats silent degradation — the queue refuses work it cannot serve on time, the kernel refuses memory the container promised not to take.
