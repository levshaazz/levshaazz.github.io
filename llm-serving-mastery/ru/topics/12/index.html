Продвинутый Kubernetes: конкурентность пода и HPA

Один под уже обслуживает толпу — continuous batching держит GPU на 90 % при пустой очереди, поэтому утилизация — анти-сигнал, а честные сигналы — глубина очереди, давление KV и TTFT. HPA — одна формула: desired = ceil(replicas × metric / target), clamp, — под охраной инклюзивной полосы tolerance ±10 % и асимметричных окон: скейл-ап мгновенно, скейл-даун после 300 с по максимуму рекомендаций. Новый под платит 165 с загрузки весов, поэтому скейл-даун осторожен; дрель отказа считает, сколько стоит один потерянный под.

Результаты обучения

  1. Считать решение HPA: ceil(replicas × metric / target), clamp в [min, max] — и почему int() — классическая ошибка.
  2. Объяснять инклюзивную полосу ±10 % как защиту от флаттера.
  3. Читать окна 0/300 с как ценообразование риска: максимум рекомендаций за 20 тиков по 15 с.
  4. Выбирать сигнал сервинга (очередь, KV, TTFT) и аргументировать, почему утилизация GPU — анти-сигнал.
  5. Провести дрель отказа: 2×250 → 250 ток/с после kill; окно 503 на одной реплике; PDB против minReplicas.
  6. Сдать милстоун: HPA-эксперимент, модель ёмкости (ведомость × реплики) и инцидент-заметки.

Чек-лист приёмки

  • формула делает clamp после ceil; ошибки int() нет
  • края полосы инклюзивны: ratio 1.1 держит флот, причина названа
  • скейл-даун берёт максимум окна; граница окна ровно 20 тиков аргументирована
  • числа дрели названы: 500 → 250 ток/с, окно 165 с, случай 503
  • эксперимент воспроизводится из HPASim; инцидент-заметки ссылаются на дрель

Открыть первоисточники

  • Kubernetes · Horizontal Pod Autoscaling (алгоритм, tolerance, окна стабилизации) — Алгоритм HPA и его защиты в формулировке курса: desiredReplicas = ceil(currentReplicas × currentMetricValue / desiredMetricValue), полоса tolerance по умолчанию, которая сдерживает масштабирование, пока отношение рядом с целью, и окна стабилизации, гасящие флаттер. Страница даёт механизм; тики и числа лабы — заявленные учебные значения курса.
  • llm-d · Best Practices for LLM Autoscaling from the llm-d Ecosystem (KubeCon + CloudNativeCon NA 2026, Cloud Native AI + Inference Day) — Набор сигналов масштабирования, который защищает доклад: глубина очереди, утилизация KV-кэша, TTFT и насыщение запросами вместо грубой утилизации GPU, с проактивным масштабированием по этим сигналам. Курс берёт отсюда словарь для упражнения по выбору сигнала; собственные результаты доклада — не числа курса.
  • GKE · Tuning the HPA to run inference on GPUs (блог Google Cloud) — Пост в блоге Google Cloud «Save on GPUs: Smarter autoscaling for your GKE inferencing workloads» — выбор сигнала масштабирования для HPA инференса. Утилизация GPU — плохая метрика, потому что коэффициент занятости GPU не отражает нагрузку, которую реально видит сервер, а глубина очереди и размер батча на сервере отражают: очередь — для throughput, батч — для латентности. Только политика и словарь; пороги и графики поста не воспроизводятся.
  • KEDA · событийное автомасштабирование и scale-to-zero — Событийное автомасштабирование как вторая дорога к HPA: KEDA масштабирует нагрузку по числу событий, ждущих обработки, работает рядом с Horizontal Pod Autoscaler, а не вместо него, и умеет скейл-даун до нуля. Курс берёт отсюда словарь и добавляет к нему собственную оговорку про холодный старт.
  • vLLM production-stack · автомасштабирование через KEDA и маршрутизация с учётом KV-кэша — Продакшен-обвязка, которую курс называет, но не запускает: автомасштабирование через KEDA по метрикам Prometheus с HPA под ним и роутер, который ведёт каждый запрос на инстанс с наибольшей долей попаданий в KV-кэш. Только словарь; дрель курса репетирует арифметику HPA на заявленных числах, а не этот стек.
  • GKE · Обзор лучших практик инференса в GKE — Правило автомасштабирования из обзора, словами страницы (перевод): «Утилизация KV-кэша (например, vllm:gpu_cache_usage_perc): этот показатель часто оказывается лучшим ранним признаком роста латентности». HPA масштабирует по метрикам сервера инференса, а не по CPU или памяти — утилизация KV-кэша или текущий батч для латентности, глубина очереди для throughput, — и минимальное число реплик задано всегда. Только политика и словарь; имена метрик — примеры страницы, а не значения, которые курс измеряет.
