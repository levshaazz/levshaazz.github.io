От пустого репозитория до Round 01

Вы сдаёте приватный GitHub-репозиторий. Публичный пример поставляет файлы и CPU-проверки; приватный учебный репозиторий преподавателя не нужен. Джадж запускает ваш сервер по тегу, а не ваш Colab-ноутбук. Результат ноутбука — свидетельство обучения, а не очки в таблице лидеров.

1. Сделайте приватную копию, включая CI

Создайте новый пустой приватный репозиторий в своём личном аккаунте GitHub, без начального README. Не используйте Fork: форк этого публичного примера — не тот путь, что приватная копия. Затем выполните:

git clone https://github.com/levshaazz/llm-serving-mastery-submission-example.git my-serving
cd my-serving
git remote rename origin upstream
git remote add origin https://github.com/YOUR_LOGIN/YOUR_PRIVATE_REPO.git
git push -u origin main

Замените оба плейсхолдера на свой аккаунт и имя репозитория. Проходите аутентификацию в GitHub обычным образом; никогда не вписывайте токен в URL remote. Эти команды сохраняют историю примера и его проверки в .github/workflows/ и делают ваш приватный репозиторий целью для push. Они не публикуют ни один из тегов примера. В submission.yaml замените author на точный логин GitHub владельца. Сохраняйте неизменяемую ревизию модели, если вы намеренно не меняете модель. Закоммитьте свои правки.

Откройте Settings → Collaborators → Add people, пригласите levshaazz и дождитесь принятия. Затем зарегистрируйте URL репозитория в таблице курса. Регистрация, приглашение и читаемый репозиторий — три разных состояния.

2. Получите подтверждение доступа

При необходимости включите Issues в своём приватном репозитории. Откройте один Issue с заголовком Course readiness и упомяните @levshaazz. Попросите подтвердить доступ джаджа и укажите SHA коммита вашей ветки по умолчанию (git rev-parse HEAD). Преподаватель отвечает Access checked, с указанием проверенного коммита и времени, только после того, как джадж сможет читать репозиторий. Одного лишь принятого приглашения недостаточно — это ещё не то подтверждение.

Если приглашение всё ещё в ожидании и приватное упоминание не может достичь преподавателя, откройте общий Issue с просьбой о помощи с доступом в публичном примере. Скажите, что приглашение в ожидании; не вставляйте приватный URL, решение, лог, токен или персональные данные. Регистрационная таблица уже передаёт приватный URL преподавателю.

3. Пройдите CPU-проверки

Используйте Python 3.12 и установите uv. Из корня репозитория:

python scripts/validate_submission.py --root .
python -m unittest discover -s tests -v
bash -n prepare.sh serve.sh
uv lock --check

Отправьте коммит (push) и проверьте Actions → Submission contract именно для этого коммита. Локальные команды остаются рабочими, если GitHub Actions недоступен из-за квоты аккаунта; сообщите о проблеме с квотой в приватном readiness-Issue вместо того, чтобы выдумывать проходной результат CI. Выполняйте uv lock и коммитьте uv.lock только при изменении зависимостей. Не обновляйте lockfile при каждом запуске. CPU-проверки верифицируют упаковку и согласованность, а не качество модели, скорость или поддержку CUDA.

4. Добудьте GPU и держите две среды раздельно

Ответственность за поиск CUDA GPU лежит на вас. Colab не гарантирует ни GPU, ни конкретную модель, и курс не предоставляет слоты разработки на машине преподавателя. CPU-работу можно начинать сразу, но она не заменяет GPU smoke-проверку. Сообщайте о блокере до дедлайна; автоматического продления или освобождения нет. Инциденты с инфраструктурой преподавателя подчиняются опубликованной общекурсовой политике.

Ноутбук Topic 01 использует небольшую закреплённую (pinned) модель, чтобы научить измерениям. Пример для сдачи использует другую, более крупную референсную модель, чтобы пройти качественные гейты джаджа. Держите среды ноутбука и серверного пакета раздельно; не подменяйте модель сдачи лабораторной моделью лишь ради копирования её вывода. Локальная производительность на GPU не предсказывает ваш результат в таблице лидеров на RTX 5070 Ti.

Запустите ноутбук, на который ведёт ссылка из Topic 01 hub. Скопируйте получившиеся файлы из Colab в свой приватный репозиторий до того, как рантайм будет уничтожен:

evidence/topic-01-baseline.json
evidence/topic-01-reflection.md
evidence/topic-01-boundary-trace.md

В трейсе названы границы client, gateway, scheduler и worker. Помечайте события, которые вы не измеряли, как not observed; диаграмма — не разрешение выдумывать внутренние временные метки. Сохраните завершённый ноутбук без учётных данных и кэшированных весов. Изучите Topic 02 и сохраните его артефакты, как указано на странице темы. Держите JOURNAL.md как журнал изменений, измерений и несостоявшихся гипотез.

Темы 03–04 начинаются с предоставленной замороженной CPU-настройки, затем идут небольшие функции, принадлежащие студенту, численные механизмы и размеченные записанные данные модели. Установка может требовать сетевого доступа; CPU-работа не засчитывается как ваш собственный GPU-эксперимент. GPU-работа — по желанию (opt-in) после завершения CPU-части. Текущие стартовые проверки студента требуют 5 GiB запаса host/device; в процессе работы Topic03 требует 2 GiB host/1 GiB device, Topic04 — 2 GiB host/512 MiB device. Это измеренные профили конкретных нагрузок, а не исторический гейт оператора на 24 GiB и не гарантия бесплатной квоты Colab. Держите парные свидетельства natural-EOS/forced-length раздельно в Topic 03, а потоки complete/partial/failed — раздельно в Topic 04. После вашего собственного успешного запуска провалидируйте JSON перед сдачей:

python scripts/validate_topic02.py path/to/topic02-benchmark.json
python scripts/validate_topic03_pilot.py --validate path/to/topic03-pilot.json
python scripts/validate_topic04.py evidence/topic-04-service.json

Включите evidence/topic-03-decision.md и evidence/topic-04-analysis.md, как указано в ноутбуках. Прохождение этих CPU-валидаторов доказывает согласованность артефактов, а не производственное качество, скорость или оценку. Исторические артефакты 02/04 используют явно названные скрипты _historical.py; исторический 03 использует validate_topic03.py. Они не принимают текущие артефакты и не являются инструкцией установить старую среду. Держите джадж отдельно. Сохраняйте неудавшиеся попытки локально, останавливайтесь при давлении на ресурсы и никогда не удаляйте кэши моделей ради retry.

5. Запустите GPU streaming smoke

На Linux или в подходящей среде Colab выполните bash serve.sh из вашей копии для сдачи. Первый запуск может скачать закреплённую модель и зависимости; сохраните их кэши для последующих запусков. Во втором терминале, как только /v1/models готов, выполните:

python scripts/smoke_submission.py

Сохраните в журнале код выхода, SHA коммита, идентификацию GPU/рантайма и обезличенный вывод. Сервер должен отдавать имя модели submission, поддерживать streaming и заявленные параметры генерации. После теста остановите его. Локальный smoke необходим, но не устанавливает скрытое качество, устойчивость к нагрузке, консистентность canary или итоговую оценку. Вам не нужен judge seed: преподаватель хранит и применяет один и тот же защищённый seed к каждой сдаче внутри раунда.

6. Прочитайте вторничный результат

Преподаватель проверяет текущую ветку по умолчанию каждый вторник перед четверговым дедлайном. Для Round 01 это 6 октября 2026. Результаты разбираются вручную и возвращаются в вашем приватном Issue Course readiness. Конкретный час не обещается. Это будущие проверки, а не уже заработанные зачёты. Если к среде результата нет, запросите статус в этом Issue.

В ответе различаются access checked, startup/smoke passed, student fix needed и judge incident / not checked. В нём указан проверенный SHA и дан обезличенный диагностический вывод. Только startup/smoke passed подтверждает запуск на GPU джаджа для этого коммита. Он не запускает скоринг качества или скорости. Более поздние изменения требуют собственных проверок. Сырые логи сервера и приватные URL остаются приватными; преподаватель не публикует их на публичном портале.

7. Заморозьте и сдайте

Сверьтесь с каноническими дедлайнами. Закоммитьте весь исходный код, lockfile, журнал и требуемые свидетельства. Убедитесь, что git status чист, задуманный коммит прошёл ваши проверки, у джаджа есть доступ, а ваш приватный remote указан верно. Затем:

git push origin main
git tag round-01
git push origin round-01
git ls-remote --tags origin refs/tags/round-01

Последняя команда подтверждает, что тег существует на GitHub. Не перезаписывайте существующий тег вслепую; изучите его и, если сомневаетесь, спросите в приватном Issue. Не перемещайте тег после дедлайна. Сдача — это тег, а не запись в таблице, push в ветку, загрузка ноутбука или скриншот зелёного CI. Джадж захватывает тег через минуту после опубликованного дедлайна и фиксирует фактические время и SHA захвата. Даты коммитов не доказывают, когда тег был отправлен. Вторничная репетиция никогда не заменяет этот официальный снимок.

8. Оценки, вопросы и апелляции

Прочитайте все правила качества, задержки, длины, ошибок, canary и скорости до начала тюнинга. Зелёный CI и работающий сервер не гарантируют ненулевую оценку. Опубликованный референс — стартовая реализация, а не разрешение делать special-case скрытых тестов или кэшировать их ответы.

Общие вопросы — в Issues публичного примера. Индивидуальная диагностика и апелляции — в Issue в вашем приватном репозитории с упоминанием @levshaazz. Указывайте раунд, тег, SHA, опубликованный результат и конкретное расхождение; никогда не включайте токены или скрытые материалы джаджа. Пересмотренные результаты предоставляются в течение пяти календарных дней после дедлайна; запрашивайте пересмотр в течение трёх календарных дней после публикации. Ошибка джаджа не приносит студенту ноль и перезапускается в рамках политики инцидентов курса. Полную политику см. в syllabus.
