L10
Две печи, один пирог

Инференс на нескольких GPU: тензорный параллелизм

Одного GPU не хватает дважды: по памяти и по нижней границе времени шага. Тензорный параллелизм разрезает весовые матрицы точно (column/row-parallel со сборкой через all-reduce), платит названный такт синхронизации за каждый блок, двигает колено кривой времени шага и раскладывает ведомость памяти по каждому GPU. Лабораторная — объявленная CPU-симуляция с настоящим доказательством разреза на NumPy; маршрут multi-GPU vLLM — демонстрация владельца.

L11
Диспетчерская таксопарка

Kubernetes для LLM-сервинга: GPU Operator и Helm

Флот у вас уже есть — compose-движки с лимитами, журнал с хэш-цепочкой, shard-реплики. Kubernetes превращает ручной цикл в декларативное состояние: под наследует ведомость (16+4)/p + 1.5 ГиБ и холодный старт 165 с, бюджет startupProbe закрывает загрузку (5 × 40 = 200 с ≥ 165 с), rolling update с maxUnavailable 0 держит пол ёмкости, а Helm-релиз — это append-only история, где откат создаёт новую ревизию. GPU-словарь — Operator, time-slicing, MIG — остаётся честным словарём; лаба — это заявленная учебная модель кластера, не ваш кластер.

L12
Термостат

Продвинутый Kubernetes: конкурентность пода и HPA

Один под уже обслуживает толпу — continuous batching держит GPU на 90 % при пустой очереди, поэтому утилизация — анти-сигнал, а честные сигналы — глубина очереди, давление KV и TTFT. HPA — одна формула: desired = ceil(replicas × metric / target), clamp, — под охраной инклюзивной полосы tolerance ±10 % и асимметричных окон: скейл-ап мгновенно, скейл-даун после 300 с по максимуму рекомендаций. Новый под платит 165 с загрузки весов, поэтому скейл-даун осторожен; дрель отказа считает, сколько стоит один потерянный под.
