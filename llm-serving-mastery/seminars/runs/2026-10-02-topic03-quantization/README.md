# Topic 03: complete toy and paired real quantization smoke

`toy.json` is generated from `teaching/topic03_quantization.py`. Its weights, input
vector and byte layout are deliberately invented. It exposes scaling, nearest-even
rounding, clipping, signed integer codes, low-nibble-first two's-complement packing,
reconstruction and activation-weighted output error. This is **not** bitsandbytes
packing or NF4 execution. The separate NF4 table is a normalized nearest-code
explanation using the [pinned 0.50.2 lookup](https://github.com/bitsandbytes-foundation/bitsandbytes/blob/0.50.2/bitsandbytes/functional.py).

`capture.json` is a separate actual CUDA recording, not generated by the toy. It
contains the four literal prompts, exact locally rendered chats and input IDs,
natural-EOS outputs and selected IDs, and three forced-24-ID timing trials for
each prompt and each format. Both use the same immutable Qwen2.5-0.5B snapshot.
Protocol v3 preserves the v2 workload and adds explicit token accounting,
incremental checkpoints, memory recovery and contract validation.

## What the clocks and memory do—and do not—mean

- Request time is synchronized `generate` wall time, with a synchronized streamer
  callback identifying the first selected ID. It includes host overhead; it is
  neither an HTTP first-content clock nor pure GPU kernel time.
- The post-first proxy includes return overhead after the final callback. It is
  not the arithmetic mean of individually recorded token-emission gaps.
- One warmup per format is excluded. Cold model load is separate. Format order is
  fixed (FP16, then NF4), not randomized. Three-trial nearest-rank p95 is simply
  the observed maximum, not a reliable tail estimate.
- Allocated/reserved are PyTorch allocator counters, not full process or device
  VRAM. The resource samples also record device-used memory for safety, not as a
  synchronized per-request process-memory measurement.
- Natural-EOS quality samples are separate from forced-length timing samples.
  Never score a forced continuation as instruction following. Four hand-selected
  prompts are a smoke set, not a representative held-out quality benchmark.
- Actual `Linear4bit` modules prove that the NF4 treatment loaded; they do not
  identify a fast CUDA kernel or establish acceleration in another serving engine.

The immutable source commit and source/capture SHA-256 hashes are recorded in
`provenance.json`. Raw local logs/caches are excluded. No judge reference,
threshold, roster, hidden task or calibration seed is involved.

## Recorded execution

Completed once from clean source `7c23155bab5673c3f0406b805b8919b6140478a2`,
offline on the RTX 5070 Ti in 71.538 s including imports/loads. The effective
scope was 24 GiB RAM, no swap, with a 600 s external timeout and 45 s kill grace.
After the process exited, an independent device query reported 0 MiB and no
compute process. All 24 timing trials and eight natural samples are retained.

FP16 peak allocated/reserved: 1202/1218 MiB; NF4: 632.974609375/1250 MiB.
The lower NF4 allocated peak did **not** imply a lower reserved peak. The scalar
format case returned `blue` versus `Blue.`; the exact-token output/termination
records, not these two strings alone, support the paired discussion.

Transformers emitted its existing warnings about sampling settings ignored under
greedy decoding and inability to infer a padding mask when pad equals EOS. This
record uses single, unpadded sequences; inferred all-one attention is the intended
mask, not a padded-batch experiment. The generic SDPA sliding-window warning was
also retained; this pinned config has `use_sliding_window=false`. Warnings were
not hidden by rerunning or rewriting the measured record.
